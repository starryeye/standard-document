이 문서는 여러 OAuth 2.0 명세의 기존 audience(의도된 수신자) 값 요구 사항에서 확인된 보안 취약점을 해결하기 위해, OAuth 2.0에서 assertion을 이용한 client 인증과 assertion 기반 authorization grant의 audience 값 처리와 관련하여 RFC 7521, RFC 7522, RFC 7523 및 RFC 9126을 업데이트합니다.¶

1. 소개

여러 OAuth 2.0 명세에서는 authorization server(인가 서버)로 보내는 토큰(‘assertion’이라고도 함)을 사용한다. 이 토큰에는 의도된 수신자를 식별하는 하나 이상의 audience 값이 들어 있다. 토큰이 JSON Web Token(JWT) [RFC7519]이면, audience 값은 "aud"(audience) 클레임에 담긴다.¶

슈투트가르트 대학교의 보안 연구자 Pedram Hosseyni, Dr. Ralf Küsters, Tim Würtele는 OpenID Federation 명세 [OpenID.Federation]의 최종 확정 전 버전을 보안 분석하던 중, 여러 OpenID 및 OAuth 명세에 영향을 미치는 취약점을 발견했다. 이 취약점은 authorization server에 보내는 토큰의 audience 값이 모호해서 발생했다. 연구자들은 이 취약점을 알리기 위해 2025년 1월에 열린 임시 회의에서 OAuth 작업반에 취약점을 공개하고, 그에 대한 설명 [private_key_jwt.Disclosure]을 제공했다. 이들이 공격을 설명하며 발표한 논문은 [Audience.Injection]이다.¶

이 명세는 발견된 보안 취약점을 해결하기 위해 영향을 받는 OAuth 명세들을 업데이트한다. 구체적으로는 OAuth 2.0 authorization server에 보내는 토큰의 audience 값으로 종전에 허용되던 선택지를 없앤다. 3.3절([RFC8414])에서는 메타데이터를 가져온 client가 반환된 issuer 값을 검증하도록 요구한다. 메타데이터에 있는 다른 엔드포인트 값은 직접 검증할 수 없으며, 다른 엔드포인트로 보내는 토큰의 audience로 그런 값을 사용하면 공격 경로가 생길 수 있다.¶

이번 업데이트의 핵심은 [RFC8414]에서 정의한 authorization server의 issuer identifier(발급자 식별자) URL만 JWT client 인증 assertion의 audience 값으로 사용하도록 요구하는 것이다. 또한 authorization server는 자체 issuer identifier가 유일한 audience 값이 아닌 JWT client 인증 assertion을 모두 거부한다. [RFC8725]에서 정의한 방식에 따라 JWT client 인증 assertion의 명시적 타입도 정의한다. 이는 이번 업데이트 이전에 발표된 명세에 따라 만든 토큰과 업데이트를 반영한 명세에 따라 만든 토큰을 쉽게 구별하기 위해서다. 영향을 받는 각 명세의 구체적인 변경 사항은 다음과 같다.¶

OLD:¶

OAuth 2.0 3.2절 [RFC6749]에 정의된 token endpoint URL을 사용해 authorization server가 해당 assertion의 유효한 audience임을 나타낼 수 있다. 달리 규정한 애플리케이션 프로파일이 없으면, 명세를 준수하는 애플리케이션은 Simple String Comparison 방식으로 Audience 값을 비교해야 한다(MUST). 이 방식은 RFC 3986의 6.2.1절 [RFC3986]에 정의되어 있다.¶

code=n0esc3NRze7LTCu7iYzS6a5acc3f0ogp4&
client_assertion_type=urn%3Aietf%3Aparams%3Aoauth
%3Aclient-assertion-type%3Asaml2-bearer&
client_assertion=PHNhbW...[omitted for brevity]...ZT

"Assertions and Protocols for the OASIS Security Assertion Markup Language (SAML) V2.0" [OASIS.saml-core-2.0-os]의 2.5.1.4절은 <AudienceRestriction> 및 <Audience> 요소를 정의한다. authorization server는 자기 자신을 의도된 audience로 식별하는 값이 없는 assertion을 모두 거부해야 한다(MUST).¶

4. RFC 7523 업데이트

이 절에서는 "JSON Web Token (JWT) Profile for OAuth 2.0 Client Authentication and Authorization Grants" [RFC7523]를 업데이트하여 audience 요건을 강화한다.¶

3절 [RFC7523](JWT 형식 및 처리 요건)에서 audience 값을 설명하는 항목 3을 다음과 같이 교체한다.¶

OLD:¶

JWT에는 authorization server를 의도된 audience로 식별하는 값이 담긴 "aud"(audience) 클레임이 반드시 있어야 한다(MUST). authorization server의 token endpoint URL을 "aud" 요소의 값으로 사용해 해당 서버를 JWT의 의도된 audience로 식별할 수 있다(MAY). authorization server는 자신을 의도된 audience로 식별하는 값이 없는 JWT를 모두 거부해야 한다(MUST). 애플리케이션 프로파일에서 달리 정하지 않는 한, 이 규격을 준수하는 애플리케이션은 반드시(MUST) RFC 3986의 6.2.1절 [RFC3986]에 정의된 Simple String Comparison 방식으로 audience 값을 비교해야 한다. 5절에서 설명하듯이, 주어진 authorization server에 대해 audience로 사용할 정확한 문자열은 해당 authorization server와 JWT 발급자가 별도 경로로 구성해야 한다.¶

NEW:¶

JWT에는 authorization server를 의도된 audience로 식별하는 값이 담긴 "aud"(audience) 클레임이 반드시 있어야 한다(MUST). 이를 다음 두 경우로 나누어 적용한다.¶

  1. authorization grant의 경우, JWT assertion의 audience가 이를 받는 authorization server에 적합하도록 하는 것은 client의 책임이다. authorization server는 해당 서버의 issuer identifier 또는 token endpoint URL 중 하나로 식별할 수 있다(MAY).¶

  2. client 인증의 경우, "aud"(audience) 클레임의 유일한 값으로 반드시(MUST) authorization server의 issuer identifier [RFC8414]를 사용해야 한다. 이 규격을 적용하려면 authorization server에 issuer identifier가 있어야 한다(MUST). "aud" 클레임 값은 JWT의 audience로 의도된 authorization server의 issuer identifier만을 나타내야 한다(MUST). 따라서 해당 authorization server의 token endpoint URL을 audience 값으로 사용해서는 안 된다(MUST NOT). authorization server는 자신의 issuer identifier만을 audience 값으로 담고 있지 않은 JWT를 모두 거부해야 한다(MUST).¶

애플리케이션 프로파일에서 달리 정하지 않는 한, 애플리케이션은 반드시(MUST) 6.2.1절 [RFC3986]에 정의된 Simple String Comparison 방식으로 audience 값을 비교해야 한다.¶

3.2절 [RFC7523](client 인증 처리)에 다음 요건을 추가한다.¶

client 인증 JWT에는 "typ" 헤더 매개변수의 값으로 "client-authentication+jwt" 또는 이 규격의 프로파일을 정의하는 다른 규격에서 정한 더 구체적인 명시적 타입 값을 사용하여 타입을 명시하는 것이 권고된다(SHOULD).¶

명시적인 "typ" 값을 사용하는 JWT의 강한 타입 지정은 이번 업데이트 이전에 발행된 규격에 따라 만든 토큰과 이번 업데이트를 반영하여 만든 토큰을 구분하는 신호 역할을 한다. 다만 주된 보안 보호 효과는 강화된 audience 요건에서 나온다. client는 타입을 명시하여 이 문서의 요건을 준수함을 알릴 수 있다. 그러나 강한 타입 지정만으로는 [private_key_jwt.Disclosure] 및 [Audience.Injection]에 설명된 공격을 막을 수 없으므로, 서버가 타입을 명시하지 않은 JWT를 거부하는 것은 권고되지 않는다(NOT RECOMMENDED). 그렇게 거부하면 강화된 audience 요건은 이미 충족하지만 아직 명시적 타입 지정을 도입하지 않은 client와의 상호운용에 문제가 생긴다. 이 접근 방식은 보안 요건 준수 여부를 알리는 것과 실제 배포 여건 사이에서 균형을 맞추어, 강화된 audience 요건은 이미 충족하지만 아직 명시적 타입 지정을 도입하지 않은 client의 운영에 지장을 주지 않는다.¶

NEW:¶

JWT의 의도된 audience는 "https://authz.example.net"이며, 이는 authorization server의 issuer identifier다.¶

4.1. client 인증 JWT 예제

다음 예제는 client 인증 JWT와 이를 사용하는 토큰 요청이 어떤 형태인지 보여 준다.¶

5. RFC 9126 업데이트

이 절에서는 "OAuth 2.0 Pushed Authorization Requests" [RFC9126]을 업데이트하여 audience 요건을 강화한다.¶

2절 [RFC9126](Pushed Authorization Request Endpoint)에서 audience 값을 설명하는 마지막 단락을 다음과 같이 교체한다.¶

OLD:¶

기존 규격의 이력 때문에 JWT client assertion 기반 인증을 사용할 때 어느 audience 값이 적절한지 모호할 수 있다. 이 인증은 2.2절 [RFC7523]에 정의되어 있으며, 인증 방식 이름은 private_key_jwt 또는 client_secret_jwt이다(9절 [OpenID.Core] 참조). 이 모호함을 해소하기 위해 [RFC8414]에 따른 authorization server의 issuer identifier URL을 audience 값으로 사용하는 것이 권고된다(SHOULD). 상호운용성을 높이기 위해 authorization server는 자신의 issuer identifier, token endpoint URL 또는 Pushed Authorization Request Endpoint URL을 자신이 의도된 audience임을 나타내는 값으로 수락해야 한다(MUST).¶

NEW:¶

기존 규격의 이력 때문에 JWT client assertion 기반 인증을 사용할 때 어느 audience 값이 적절한지 모호할 수 있다. 이 인증은 2.2절 [RFC7523]에 정의되어 있으며, 4절에서 업데이트한 내용이 적용된다. 인증 방식 이름은 "private_key_jwt" 또는 "client_secret_jwt"이다(9절 [OpenID.Core] 참조). 이 모호함을 해소하기 위해 [RFC8414]에 따른 authorization server의 issuer identifier URL만을 audience 값으로 사용해야 한다(MUST). authorization server는 자신의 issuer identifier만을 audience 값으로 담고 있지 않은 이러한 JWT를 모두 거부해야 한다(MUST).¶

client 인증 JWT에는 "typ" 헤더 매개변수의 값으로 "client-authentication+jwt" 또는 이 규격의 프로파일을 정의하는 다른 규격에서 정한 더 구체적인 명시적 타입 값을 사용하여 타입을 명시하는 것이 권고된다(SHOULD).¶

명시적인 "typ" 값을 사용하는 JWT의 강한 타입 지정은 이번 업데이트 이전에 발행된 규격에 따라 만든 토큰과 이번 업데이트를 반영하여 만든 토큰을 구분하는 신호 역할을 한다. 다만 주된 보안 보호 효과는 강화된 audience 요건에서 나온다. client는 타입을 명시하여 이 문서의 요건을 준수함을 알릴 수 있다. 그러나 강한 타입 지정만으로는 [private_key_jwt.Disclosure] 및 [Audience.Injection]에 설명된 공격을 막을 수 없으므로, 서버가 타입을 명시하지 않은 JWT를 거부하는 것은 권고되지 않는다(NOT RECOMMENDED). 그렇게 거부하면 강화된 audience 요건은 이미 충족하지만 아직 명시적 타입 지정을 도입하지 않은 client와의 상호운용에 문제가 생긴다. 이 접근 방식은 보안 요건 준수 여부를 알리는 것과 실제 배포 여건 사이에서 균형을 맞추어, 강화된 audience 요건은 이미 충족하지만 아직 명시적 타입 지정을 도입하지 않은 client의 운영에 지장을 주지 않는다.¶

6. 운영 시 고려 사항

이 명세의 변경 사항은 서로 다른 버전을 구현한 client와 authorization server 간의 상호운용성에 영향을 준다. 특히 버전 간 호환성은 완전히 대칭적이지 않다. 이 명세를 구현한 client는 이 문서의 업데이트를 준수하는 authorization server뿐 아니라 이전 버전을 구현한 authorization server와도 상호운용된다. 그러나 이전 버전을 구현한 일부 client는 이 명세의 업데이트된 요건을 엄격히 적용하는 authorization server와 상호운용되지 않을 수 있다. 이 명세로 업그레이드하는 배포 환경에서는 도입이나 마이그레이션을 계획할 때 이러한 비대칭성을 고려하는 것이 좋다. 변경된 동작을 적용하는 authorization server보다 먼저 client를 업데이트하거나, 서버 업데이트와 조율하여 client를 업데이트해야 할 수 있기 때문이다.¶

7. 보안 고려 사항

다음 명세에 설명된 보안 고려 사항은 모두 이 문서에도 적용된다. "Assertion Framework for OAuth 2.0 Client Authentication and Authorization Grants" [RFC7521], "Security Assertion Markup Language (SAML) 2.0 Profile for OAuth 2.0 Client Authentication and Authorization Grants" [RFC7522], "JSON Web Token (JWT) Profile for OAuth 2.0 Client Authentication and Authorization Grants" [RFC7523], "OAuth 2.0 Pushed Authorization Requests" [RFC9126], "The OAuth 2.0 Authorization Framework" [RFC6749] 및 "JSON Web Token (JWT)" [RFC7519].¶

이 명세는 [RFC7521], [RFC7522], [RFC7523] 및 [RFC9126]에서 허용했던 audience의 모호성을 악용하는 공격을 방지하기 위해 assertion의 audience 값 처리 요건을 강화한다. 이러한 공격은 [private_key_jwt.Disclosure] 및 [Audience.Injection]에 설명되어 있다.¶
