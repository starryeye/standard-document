초록

이 명세는 OAuth 2.0 access token을 JSON Web Token (JWT) 형식으로 발급하기 위한 프로파일을 정의합니다. 서로 다른 공급업체의 authorization server(인가 서버)와 resource server(리소스 서버)는 이 프로파일을 이용하여 상호 운용 가능한 방식으로 access token을 발급하고 사용할 수 있습니다.¶

1. 서론

기존 OAuth 2.0 Authorization Framework [RFC6749] 명세는 access token에 특정 형식을 요구하지 않습니다. 이러한 방식은 여전히 많은 중요한 시나리오에 적합합니다. 다만 실제 시장에서는 많은 상용 OAuth 2.0 구현이 authorization server의 추가 관여 없이 resource server가 직접 파싱하고 검증할 수 있는 형식으로 access token을 발급하기로 했습니다. 이 접근 방식은 authorization server와 resource server가 같은 위치에 배치되지 않았거나, 운영 주체가 다르거나, 그 밖의 경계로 분리된 구성에서 특히 흔합니다. 이 문서를 작성하는 시점에 많은 상용 구현이 JSON Web Token (JWT) [RFC7519] 형식을 이용합니다.¶

공급업체별 JWT access token 상당수는 기능적 구조가 같습니다. 토큰 검증, scope(범위)와 entitlements 형태의 인가 정보 전달, subject의 신원 정보 전달 등 공통 사용 사례를 지원하는 데 필요한 정보를 JWT Claim으로 전달합니다. 차이는 대체로 같은 대상을 표현하는 Claim의 이름과 구문에 국한됩니다. 이는 공통 Claim과 검증 규칙을 표준화하면 비교적 쉽게 상호운용성을 확보할 수 있음을 시사합니다.¶

access token이 특정 정보와 연관된다는 전제는 상용 구현에만 나타나는 것이 아닙니다. resource indicators [RFC8707], OAuth 2.0 bearer token usage [RFC6750] 등 OAuth 2.0 계열의 여러 명세는 access token에 audience처럼 적용 범위를 한정하는 장치가 있다고 전제합니다. introspection 관련 명세들 역시 access token이 기본적으로 어떤 정보들을 담거나 적어도 그 정보들과 연관될 것으로 기대되는지 간접적으로 시사합니다.¶

이 명세는 앞으로 공급업체별 독자적인 JWT access token 구조를 대신할 수 있는 표준화된 상호운용 가능 프로파일을 제공하는 것을 목표로 합니다. 이 프로파일은 공통 필수 Claim과 선택 Claim을 정의할 뿐 아니라, 인가 요청의 매개변수가 발급되는 JWT access token의 내용을 어떻게 결정하는지, authorization server가 자신이 발급하는 JWT access token에 관한 메타데이터를 어떻게 공개할 수 있는지, resource server가 수신한 JWT access token을 어떻게 검증해야 하는지 명확히 제시합니다.¶

마지막으로 이 명세는 access token을 표현하는 데 JWT 형식을 별다른 고려 없이 적용할 때 생기기 쉬운 일반적인 실수와 안티패턴을 방지하기 위한 보안 및 개인정보 보호 고려 사항을 제시합니다.¶

참고: 이 문서와 [RFC7523]은 모두 OAuth2 프레임워크에서 JSON Web Token을 사용하지만, 두 명세는 목적과 작동 방식이 모두 다릅니다. [RFC7523]은 JWT Bearer Token을 사용해 access token을 요청하는 방법을 정의하는 반면, 이 문서는 access token을 JWT 형식으로 인코딩하는 방법을 설명합니다.¶

1.1. 요구사항 표기법 및 관례

이 문서에서 사용하는 키워드 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", "OPTIONAL"은 여기에 제시된 것처럼 모든 글자가 대문자로 표기된 경우에만 BCP 14 [RFC2119] [RFC8174]에 설명된 대로 해석합니다.¶

1.2. 용어

JWT access token:
JWT 형식으로 인코딩되며 이 명세에 기술된 요구사항을 준수하는 OAuth 2.0 access token.¶

이 명세에서는 The OAuth 2.0 Authorization Framework [RFC6749]에서 정의한 "access token", "refresh token", "authorization server", "resource server", "authorization endpoint", "authorization request", "authorization response", "token endpoint", "grant type", "access token request", "access token response", "client(클라이언트)"라는 용어를 사용합니다.¶

2. JWT access token의 헤더 및 데이터 구조

2.1. 헤더

JWT access token에는 반드시 서명해야 합니다(MUST). JWT access token에는 어떤 서명 알고리즘이든 사용할 수 있지만, resource server가 검증 정보를 더 쉽게 확보할 수 있도록 비대칭 암호 방식을 사용하는 것을 권고합니다(RECOMMENDED, Section 4 참조). JWT access token의 서명 알고리즘으로 "none"을 사용해서는 안 됩니다(MUST NOT). 자세한 내용은 Section 4를 참조합니다.¶

이 명세를 준수하는 authorization server와 resource server는 지원하는 서명 알고리즘에 반드시(MUST) RS256([RFC7518]에 정의됨)을 포함해야 합니다.¶

이 명세는 콘텐츠가 JWT access token임을 나타내는 데 사용할 수 있는 미디어 타입 "application/at+jwt"를 등록합니다. JWT access token은 JWT가 이 프로파일을 준수하는 access token임을 명시하기 위해 이 미디어 타입을 "typ" 헤더 매개변수에 반드시 포함해야 합니다(MUST). Section 4.1.9 ([RFC7515])의 "typ" 정의에 따르면 "application/" 접두사를 생략하는 것을 권고합니다(RECOMMENDED). 따라서 "typ" 값으로 "at+jwt"를 사용하는 것이 바람직합니다(SHOULD). 보안 고려 사항 절에서는 이 프로파일을 구현하는 resource server가 OpenID Connect ID Tokens([OpenID.Core]의 Section 2에 정의됨)를 access token으로 받아들이지 않도록 하는 일이 왜 중요한지 자세히 설명합니다.¶

2.2. 데이터 구조

JWT access token 데이터 구조에는 다음 Claim이 사용됩니다.¶

iss
REQUIRED(필수) — Section 4.1.1 ([RFC7519])의 정의를 따릅니다.¶
exp
REQUIRED(필수) — Section 4.1.4 ([RFC7519])의 정의를 따릅니다.¶
aud
REQUIRED(필수) — Section 4.1.3 ([RFC7519])의 정의를 따릅니다. authorization server가 요청에 따라 "aud" 값을 어떻게 결정해야 하는지는 Section 3을 참조합니다.¶
sub
REQUIRED(필수) — Section 4.1.2 ([RFC7519])의 정의를 따릅니다. authorization code grant처럼 resource owner(리소스 소유자)가 관여하는 authorization grant(인가 부여)로 얻은 access token의 경우, "sub" 값은 해당 resource owner의 subject 식별자에 대응하는 것이 바람직합니다(SHOULD). client credentials grant처럼 resource owner가 관여하지 않는 authorization grant로 얻은 access token의 경우, "sub" 값은 authorization server가 해당 client 애플리케이션을 나타내는 데 사용하는 식별자에 대응하는 것이 바람직합니다(SHOULD). 이 시나리오에 대한 자세한 내용은 Section 5를 참조합니다. 또한 "sub" 값의 할당 방식에 따라 개인정보 보호에 어떤 영향이 생길 수 있는지는 Section 6을 참조합니다.¶
client_id
REQUIRED(필수) — Section 4.3 ([RFC8693])의 정의를 따릅니다.¶
iat
REQUIRED(필수) — Section 4.1.6 ([RFC7519])의 정의를 따릅니다. 이 Claim은 JWT access token이 발급된 시각을 나타냅니다.¶
jti
REQUIRED(필수) — Section 4.1.7 ([RFC7519])의 정의를 따릅니다.¶

2.2.1. 인증 정보 Claim

이 절에 나열된 Claim은 resource owner가 관여하는 authorization grant의 맥락에서 발급될 수 있습니다(MAY). 이 Claim은 authentication server가 client에 인가 응답을 반환하기 전에 적용한 인증의 유형과 강도를 access token에 나타냅니다. 그 값은 고정되며, 주어진 인가 응답에서 파생된 모든 access token에서 동일합니다. 이는 응답에서 access token을 직접 얻었든(예: implicit flow), 한 번 이상 토큰을 교환한 뒤 얻었든(예: refresh token으로 새 access token을 얻거나 [RFC8693] 절차에 따라 한 access token을 다른 access token으로 교환하는 경우) 마찬가지입니다.¶

auth_time
OPTIONAL(선택 사항) — [OpenID.Core]의 Section 2에 나온 정의를 따릅니다.¶
acr
OPTIONAL(선택 사항) — [OpenID.Core]의 Section 2에 나온 정의를 따릅니다.¶
amr
OPTIONAL(선택 사항) — [OpenID.Core]의 Section 2에 나온 정의를 따릅니다.¶

2.2.2. 신원 Claim

resource owner가 관여하는 authorization grant에서는 상용 authorization server가 resource owner의 속성을 access token에 직접 포함하는 경우가 많습니다. 이렇게 하면 resource server는 introspection([RFC7662]) 또는 UserInfo([OpenID.Core]) 엔드포인트에 추가로 요청을 보내 응답을 받는 과정 없이 해당 속성을 인가나 그 밖의 목적으로 직접 사용할 수 있습니다. 이는 퍼스트파티 client가 자체 백엔드 API를 호출하는 경우처럼 client와 resource server가 같은 주체에 속하고 같은 솔루션의 일부인 시나리오에서 특히 흔합니다.¶

이 프로파일은 client가 JWT access token에 특정 Claim을 포함해 달라고 직접 요청하는 방법을 별도로 도입하지 않습니다. authorization server가 client의 client_id와 요청에 포함된 "scope" 및 "resource" 매개변수를 고려하여 특정 resource server에 어떤 추가 Claim이 필요한지 판단할 수 있기 때문입니다.¶

[RFC7519]에서 도입한 "JSON Web Token (JWT)" IANA registry의 항목이 추가 신원 속성의 의미를 잘 설명하고, 그 속성을 JWT access token에 포함하려는 경우에는 해당 Claim 이름으로 인코딩하는 것이 권장됩니다(SHOULD). JWT IANA registry에는 [OpenID.Core]의 5.1절에 나오는 Claim도 포함됩니다.¶

해당 Claim 이름이 충돌에 강하거나 access token이 비공개 하위 시스템에서만 사용될 예정이라면, authorization server는 (MAY) 기존 명세에 정의되지 않은 임의의 속성을 반환할 수 있습니다. 자세한 내용은 4.2절과 4.3절([RFC7519])을 참조하세요.¶

JWT access token에 resource owner의 속성을 포함하는 authorization server는 주의를 기울이고, 6절에서 설명하는 바와 같이 모든 개인정보 보호 요구 사항이 충족되는지 확인해야 합니다.¶

2.2.3. 인가 Claim

인가 요청에 scope 매개변수가 포함되어 있으면, 그 요청에 따라 발급되는 JWT access token에는 (SHOULD) 4.2절([RFC8693])에 정의된 "scope" Claim을 포함하는 것이 권장됩니다.¶

"scope" Claim에 들어 있는 각각의 scope 문자열은 모두 "aud" Claim이 가리키는 리소스에 대해 의미가 있어야 합니다(MUST). scope 문자열과 "aud" Claim이 가리키는 리소스의 관계에 관한 추가 고려 사항은 5절을 참조하세요.¶

2.2.3.1. 위임 시나리오 이외의 인가에 사용하는 Claim

많은 authorization server는 발급하는 access token에 [RFC7519]에서 설명하는 위임 시나리오의 범위를 넘어서는 인가 속성을 넣습니다. 대표적인 예로는 접근 대상 리소스와 관련하여 resource owner가 속한 역할과 그룹, 대상 리소스에 대해 resource owner에게 부여되었으며 authorization server가 알고 있는 권한 등이 있습니다.¶

JWT access token에 이러한 속성을 포함하려는 authorization server에는 다음과 같은 Claim 유형을 사용하는 것이 권장됩니다(SHOULD). 4.1.2절([RFC7643])에 정의된 "User" 리소스 스키마의 "groups", "roles", "entitlements" 속성입니다.¶

authorization server에는 (SHOULD) [RFC7643]에 명시된 지침에 따라 해당 Claim 값을 인코딩하는 것이 권장됩니다. 특히 "groups" 속성의 비규범적 예시는 8.2절([RFC7643])에서 볼 수 있습니다. "roles"와 "entitlements"에는 별도로 정해진 어휘가 제공되지 않습니다.¶

이 문서의 7.2.1절에는 [RFC7643]의 "groups", "roles", "entitlements" 속성을 이 프로파일에서 사용할 Claim 유형으로 등록하기 위한 항목이 나와 있습니다.¶

3. JWT access token 요청

authorization server는 [RFC6749] 및 이후 확장 명세에서 정의된 것 중 access token 발급을 목적으로 하는 모든 authorization grant에 대해 JWT access token을 발급할 수 있습니다.¶

요청에 [RFC8707]에서 정의한 "resource" 매개변수가 포함되어 있다면, 그 요청에 따라 발급되는 JWT access token의 "aud" Claim에는 요청의 "resource" 매개변수와 같은 값을 사용하는 것이 권장됩니다(SHOULD).¶

요청의 예는 다음과 같습니다.¶

위 요청에서 얻은 코드를 교환하면 아래와 같은 형식의 JWT access token이 발급됩니다.¶

JWT access token으로 부여되는 인가가 모호해질 경우, authorization server는 그 token을 발급해서는 안 됩니다(MUST NOT). 모호성이 발생할 수 있는 일반적인 사례와 이를 방지하기 위해 authorization server가 취할 수 있는 전략에 대한 자세한 내용은 5절을 참조하세요.¶

요청에 "resource" 매개변수가 없다면 authorization server는 "aud" Claim에 기본 resource indicator(리소스 지시자)를 사용해야 합니다(MUST). 요청에 "scope" 매개변수가 있다면, authorization server가 이를 바탕으로 "aud" Claim에 사용할 기본 resource indicator 값을 추론하는 것이 권장됩니다(SHOULD). 각 scope를 기본 resource indicator 값과 연결하는 방식은 이 명세의 범위를 벗어납니다. "scope" 매개변수의 값들이 서로 다른 기본 resource indicator 값을 가리키면, authorization server에는 (SHOULD) 4.1.2.1절([RFC6749])에 설명된 대로 "invalid_scope" 오류로 요청을 거부하는 것이 권장됩니다.¶

4. JWT access token 검증

검증에 필요한 데이터를 쉽게 가져올 수 있도록, 이 명세에서는 authorization server가 JWT access token에 비대칭 알고리즘으로 서명할 것을 권장합니다(RECOMMENDED).¶

authorization server에는 다음 방식을 권장합니다(SHOULD). OAuth 2.0 Authorization Server Metadata [RFC8414]를 사용하여, "jwks_uri"를 통해 resource server에 서명 키를 알리고 "issuer" 메타데이터 값을 통해 어떤 "iss" Claim 값을 기대해야 하는지 알립니다. 또는 OpenID Connect를 구현하는 authorization server는 (MAY) 같은 목적으로 OpenID Connect discovery [OpenID.Discovery] 문서를 사용할 수 있습니다. authorization server가 OAuth 2.0 Authorization Server Metadata와 OpenID Connect discovery를 모두 지원한다면 두 공개 방식으로 제공하는 값은 일치해야 합니다(MUST).¶

authorization server는 OpenID Connect ID Token(ID 토큰)과 JWT access token에 서로 다른 키로 서명할 수 있습니다(MAY). 이 명세는 JWT access token 서명에 사용되는 특정 키를 식별하는 방법을 제공하지 않습니다. authorization server는 authorization server(AS) 메타데이터 또는 OpenID Connect discovery를 통해 공개한 키 중 어느 것으로든 JWT access token에 서명할 수 있습니다. 보안에 미치는 영향에 관한 추가 지침은 5절을 참조하세요.¶

JWT access token을 받은 resource server는 다음과 같은 방식으로 이를 검증해야 합니다(MUST).¶

  • resource server는 "typ" 헤더 값이 "at+jwt" 또는 "application/at+jwt"인지 확인하고, 그 밖의 값을 담은 token은 거부해야 합니다(MUST).¶
  • JWT access token이 암호화되어 있다면 resource server가 등록할 때 지정한 키와 알고리즘으로 복호화합니다. 등록 시 authorization server와 암호화를 사용하기로 협의했는데 수신한 JWT access token이 암호화되어 있지 않다면, resource server는 이를 거부하는 것이 권장됩니다(SHOULD).¶
  • authorization server의 발급자 식별자(일반적으로 discovery 과정에서 가져옴)는 "iss" Claim 값과 정확히 일치해야 합니다(MUST).¶
  • resource server는 "aud" Claim에 자신을 나타내는 것으로 예상하는 식별자에 해당하는 resource indicator 값이 들어 있는지 검증해야 합니다(MUST). "aud"에 현재 resource server를 유효한 audience로 지정하는 resource indicator가 없다면 JWT access token을 거부해야 합니다(MUST).¶
  • resource server는 수신한 모든 JWT access token의 서명을 다음 방식으로 검증해야 합니다(MUST). 검증은 [RFC7515]에 따라 JWT의 "alg" 헤더 매개변수에 지정된 알고리즘으로 수행합니다. resource server는 "alg" 값이 "none"인 모든 JWT를 거부해야 합니다(MUST). 또한 authorization server가 제공한 키를 사용해야 합니다(MUST).¶
  • 현재 시각은 "exp" Claim이 나타내는 시각보다 앞서야 합니다(MUST). 구현자는 시계 간 오차를 고려해 일반적으로 몇 분을 넘지 않는 약간의 허용 오차를 둘 수 있습니다(MAY).¶

resource server는 (MUST) 3.1절([RFC6750])에 설명된 대로 오류를 처리해야 합니다. 특히 위에 나열한 검증 항목 중 하나라도 실패하면 authorization server의 응답에 오류 코드 "invalid_token"이 포함되어야 합니다(MUST). 이 요구 사항은 JWT access token에서 "Bearer" 외의 인증 방식을 사용하는 것을 막지 않습니다.¶

JWT access token에 2.2.3절에서 설명한 인가 Claim이 포함되어 있다면, resource server는 그 Claim과 그 밖에 이용할 수 있는 모든 맥락 정보를 함께 사용해 현재 호출을 인가할지 거부할지 판단하는 것이 권장됩니다(SHOULD). resource server가 이러한 검사를 수행하는 세부 방식은 이 프로파일 명세의 범위를 벗어납니다.¶

5. 보안 고려 사항

여기서 설명하는 JWT access token의 데이터 구조는 [OpenID.Core]에서 정의한 id_token의 구조와 매우 유사합니다. 이 프로파일은 [RFC8725]의 권고에 따라 유형을 명시하도록 요구합니다. 이를 통해 resource server는 JWT access token과 OpenID Connect ID Token을 구분할 수 있습니다.¶

authorization server는 client가 resource server에 혼동을 일으킬 수 있는 방식으로 "sub" Claim의 값에 영향을 주는 상황을 방지하는 것이 좋습니다. 예를 들어 authorization server가 client credentials grant로 발급하는 access token의 "sub" 값으로 client_id를 사용하기로 했다면, client가 임의의 client_id 값을 등록하지 못하도록 하는 것이 좋습니다. 그렇지 않으면 악의적인 client가 높은 권한을 가진 resource owner의 sub를 선택해, "sub" 값에 의존하는 resource server의 authorization 로직에 혼동을 일으킬 수 있기 때문입니다. 자세한 내용은 4.14절 ([OAuth2.Security.BestPractices])을 참조하세요.¶

서로 다른 JWT 간의 혼동을 방지하려면, authorization server는 같은 issuer가 서로 다른 resource를 대상으로 발급한 access token을 고유하게 식별할 수 있도록 "aud" Claim의 값으로 각 resource에 서로 다른 식별자를 반드시(MUST) 사용해야 합니다. JWT 간 혼동에 대한 자세한 내용은 2.8절 ([RFC8725])을 참조하세요.¶

authorization server는 모호한 authorization grant로 이어질 수 있는 요청을 처리할 때 특히 주의하는 것이 좋습니다. 예를 들어 요청에 resource indicator가 여러 개 포함되어 있다면, 그 결과 발급되는 JWT access token에 scope 문자열이 있을 경우 각 scope 문자열을 "aud" Claim에 나열된 resource 중 특정 resource와 모호함 없이 연결할 수 있도록 하는 것이 좋습니다. 이런 상황을 비롯해 모호성이 생기는 상황을 식별하고 완화하는 구체적인 방법은 시나리오에 크게 좌우되므로 이 프로파일에서 다루지 않습니다.¶

authorization server는 OpenID Connect ID Token과 JWT token에 서로 다른 서명 키를 쓰는 것만으로 특정 키가 유출되었을 때의 피해를 막을 수 있다고 보아서는 안 됩니다. resource server는 어떤 키가 JWT access token 검증에 쓰여야 하는지 알 방법이 없으므로, authorization server metadata 또는 OpenID Connect discovery에 게시된 키 중 어느 것으로 생성된 서명이든 수락해야 합니다. 따라서 공격자는 게시된 키 중 하나만 탈취해도 resource server가 유효하다고 받아들일 JWT를 생성하고 서명할 수 있습니다.¶

6. 개인정보 보호 고려 사항

JWT access token은 정보의 값 자체를 담고 있으므로, 암호화되지 않은 token에서는 client뿐 아니라 경우에 따라 최종 사용자도 token 안에 담긴 Claim 집합을 직접 들여다볼 수 있습니다.¶

client는 access token의 내용을 절대(MUST NOT) 확인해서는 안 됩니다. authorization server와 resource server는 언제든지 token 형식을 바꾸기로 할 수 있습니다(예를 들어 이 프로파일 대신 opaque token을 사용할 수 있습니다). 따라서 access token의 내용을 읽을 수 있다고 전제하는 client의 로직은 더는 작동하지 않으며, 이를 복구할 방법도 없습니다. OAuth 2.0 framework는 client가 access token을 opaque token으로 취급한다고 가정합니다. authorization server 관리자도 access token의 내용이 client에 노출된다는 점을 고려하는 것이 좋습니다. 특정 시나리오에서 client가 access token의 내용에 접근할 수 있다는 점이 개인정보 보호 문제를 일으킨다면, authorization server는 이를 방지하기 위한 명시적인 조치를 취해야 합니다.¶

최종 사용자가 JWT access token에 접근할 수 있는 시나리오에서는 개인정보 침해 없이 해당 정보에 접근할 수 있는지(예를 들어 최종 사용자가 단지 자신의 개인정보에 접근하는 경우), 아니면 기밀성을 보장하기 위한 조치가 필요한지 평가하는 것이 좋습니다.¶

client와 최종 사용자에게 정보가 유출되지 않도록 하는 방법으로는 access token 암호화, 민감한 Claim 암호화, 민감한 Claim 생략, 또는 이 프로파일 대신 opaque access token 사용 등이 있습니다.¶

어떤 시나리오에서든 JWT access token의 내용은 결국 resource server가 열람할 수 있게 됩니다. 어떤 내용이든 Claim 형태로 전달된다면, resource server가 그 내용에 접근할 정당한 권한을 부여받았는지 평가하는 것이 중요합니다. 예를 들어 어떤 형태로든 사용자의 동의를 얻었는지, authorization server를 운영하는 조직과의 정책이나 합의가 있는지 등을 확인할 수 있습니다. 가령 사용자는 2절(및 그 하위 절)에 열거된 필수가 아닌 Claim에 관한 정보를 특정 resource server에 제공하는 데 동의하고 싶지 않을 수 있습니다.¶

이 프로파일은 모든 JWT access token에 "sub" Claim이 들어 있어야 한다고 규정합니다. 이에 따라 resource server는 "sub" 정보로 수신한 요청과 인증된 principal에 대해 로컬에 저장된 데이터를 연결할 수 있습니다. 요청을 연결하는 기능이 설계상 필요한 시나리오도 많지만, authorization server가 이런 연결을 막고자 하는 시나리오도 있습니다. authorization server는 개인정보 보호 영향 평가에 따라 "sub" Claim의 값을 정하는 것이 좋습니다. 예를 들어 여러 resource server에 걸쳐 principal의 활동을 추적할 수 없게 해야 한다면, authorization server는 서로 다른 resource server용 JWT access token에 서로 다른 "sub" 값을 사용하고, resource server들이 공모하더라도 그 값들을 서로 연결할 수 없게 하는 것이 좋습니다. 마찬가지로 resource server가 같은 resource 내에서 principal의 활동을 연결하지 못하게 해야 한다면, authorization server는 발급하는 JWT access token마다 다른 "sub" 값을 할당하는 것이 좋습니다. 이에 맞춰 client는 resource server를 호출할 때마다 새 JWT access token을 받는 것이 좋습니다. 그러면 resource server가 호출마다 서로 다른 "sub"와 "jti" 값을 받아, 별개의 요청을 서로 연결할 수 없게 됩니다.¶

감사의 글

이 명세의 출발점이 된 요구사항은 운영 시스템에서 JWT 형식으로 발급한 수많은 access token 사례를 바탕으로 도출했습니다. Dominick Baier (IdentityServer), Brian Campbell (Ping Identity), Daniel Dobalian (Microsoft), Karl Guinness (Okta)가 각자의 제품과 서비스에서 발급한 샘플 토큰을 제공해 주신 데 감사드립니다. Brian Campbell과 Filip Skokan은 초기에 의견을 주어 명세의 방향을 잡는 데 도움을 주었습니다. OAuth Security Workshop 2019에서는 이 프로파일을 두고 오랜 시간 논의했으며, 여러 참가자가 아이디어와 의견을 보탰습니다. 다음 분들의 기여에 감사드립니다.¶

John Bradley, Brian Campbell, Vladimir Dzhuvinov, Torsten Lodderstedt, Nat Sakimura, Hannes Tschofenig 및 자유 토론에 적극적으로 참여해 주신 모든 분.¶

다음 분들은 IETF OAuth 2.0 WG 메일링 리스트와 제28회 Internet Identity Workshop (IIW 28)에서 초안에 유용한 의견과 통찰을 보태 주셨습니다.¶

Dale Olds, George Fletcher, David Waite, Michael Engan, Mike Jones, Hans Zandbelt, Vladimir Dzhuvinov, Martin Schanzenbach, Aaron Parecki, Annabelle Richard Backman, Dick Hardt, Denis Pinkas, Benjamin Kaduk, Dominick Baier, Andrii Deinega, Mike Jones 및 IIW 28의 자유 토론과 IETF OAuth 2.0 WG 메일링 리스트의 논의에 적극적으로 참여해 주신 모든 분. AD 검토를 맡아 주신 Roman Danyliw에게, SECDIR 및 GENART 검토를 맡아 주신 Joseph Salowey와 Roni Even에게, 그리고 IESG 검토를 맡아 주신 Francesca Palomini, Lars Eggert, Murray Kucherawy, Roberto Polli, Martin Duke, Benjamin Kaduk에게 감사드립니다.¶
