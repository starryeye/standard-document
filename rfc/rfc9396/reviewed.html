1. 서론

"The OAuth 2.0 Authorization Framework" [RFC6749]는 scope 매개변수를 정의한다. OAuth client(클라이언트)는 이 매개변수로 access token에 요청하는 범위, 즉 허용할 기능의 한계를 지정할 수 있다. 이 방식은 정적인 시나리오나 "resource owner(리소스 소유자)의 프로필을 읽을 수 있게 해 주세요"처럼 세분화되지 않은 인가 요청을 구현하는 데는 충분하다. 그러나 "가맹점 A에 45유로를 이체할 수 있게 해 주세요" 또는 "디렉터리 A를 읽고 파일 X에 쓸 수 있게 해 주세요"처럼 세분화된 인가 요구 사항을 명시하기에는 충분하지 않다.¶

이 명세는 새로운 매개변수 authorization_details를 도입한다. 이 매개변수를 사용하면 client는 JSON [RFC8259] 데이터 구조의 표현력을 활용해 세분화된 인가 요구 사항을 명시할 수 있다.¶

예를 들어 계좌 이체(여러 오픈 뱅킹 이니셔티브에서 "지급 개시"라고 부르는 거래)에 대한 인가 요청은 다음과 같은 JSON 객체로 표현할 수 있다.¶

이 객체에는 금액, 통화, 수취인 등 사용자에게 예정된 지급 내용을 알리고 동의를 받는 데 필요한 상세 정보가 들어 있다. authorization server(AS)와 해당 resource server(RS, 지급 개시 API를 제공하는 서버)는 함께 사용자가 동의한 내용이 준수되도록 한다.¶

오픈 뱅킹과 전자 서명 분야의 새로운 사용 사례에서 발생하는 문제를 종합적으로 살펴보려면 [Transaction-Auth]를 참조한다.¶

이 명세는 맞춤형 인가 요청을 지원할 뿐 아니라 여러 API에서 두루 사용할 수 있는 공통 데이터 유형 필드 집합도 도입한다.¶

1.1. 표기 관례와 용어

이 문서에서 키워드 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", "OPTIONAL"는 여기에 제시된 것처럼 모두 대문자로 표기된 경우에만 BCP 14 [RFC2119] [RFC8174]에 명시된 대로 해석한다.¶

이 명세는 "access token", "refresh token(리프레시 토큰)", "authorization server"(AS), "resource server"(RS), "authorization endpoint", "authorization request", "authorization response", "token endpoint(토큰 엔드포인트)", "grant type(그랜트 유형)", "access token request", "access token response", "client"라는 용어를 사용한다. 이 용어들은 "The OAuth 2.0 Authorization Framework" [RFC6749]에서 정의한다.¶

2. 요청 매개변수 "authorization_details"

요청 매개변수 authorization_details는 JSON 표기법으로 나타낸 객체 배열을 담는다. 각 JSON 객체에는 특정 유형의 리소스에 대한 인가 요구 사항을 명시하는 데 필요한 데이터가 들어 있다. 리소스 또는 접근 요구 사항의 유형은 아래에 정의된 type 필드가 결정한다.¶

type:
상세 인가 정보의 유형을 나타내는 문자열 식별자다. type 필드의 값은 이 필드를 포함하는 객체에 어떤 내용을 담을 수 있는지 결정한다. 이 값은 해당 AS의 범위 내에서 기술 대상 API에 고유하다. 이 필드는 필수다(REQUIRED).¶

authorization_details 배열은 선택적으로(MAY) 동일한 type의 항목을 여러 개 포함할 수 있다.¶

그림 2는 앞에서 제시한 예시 데이터를 사용하여 authorization_details의 payment_initiation 유형 예시를 보여 준다.¶

그림 3은 계좌 정보에 접근할 권한과 지급을 개시할 권한을 함께 요청하는 예시를 보여 준다.¶

type 필드의 값이 각각 account_information과 payment_initiation인 JSON 객체는 AS가 동의를 요청할 때 사용할 서로 다른 authorization_details 항목을 나타낸다.¶

참고: AS는 이후 각 RS가 이 데이터를 이용할 수 있게 한다(9절 참조).¶

2.1. 상세 인가 정보의 유형

AS는 type 매개변수의 값을 어떻게 해석할지와 type 매개변수가 객체에서 어떤 필드를 허용할지를 모두 결정한다. 다만 type 매개변수의 값은 대개 문서화되며, 개발자가 사용하도록 마련된 값이기도 하다. 따라서 다음 사항을 권장한다(RECOMMENDED). API 설계자는 혼동 없이 쉽게 복사할 수 있는 type 값을 선택한다. 예를 들어 어떤 글리프는 시각적으로 동일한 문자에 대응하는 Unicode 코드 포인트가 여러 개여서 개발자가 AS에서 정의한 것과 다른 문자를 입력할 수도 있다. 혼동을 줄이려면 값을 ASCII [RFC0020] 문자로 제한하거나, 데이터 유형 값 목록을 기계 판독 가능한 형식으로 제공하거나, 개발자에게 문서에서 직접 복사하여 붙여 넣도록 안내할 수 있다.¶

공개 표준에서처럼 애플리케이션이나 API가 여러 서버에 걸쳐 배포될 것으로 예상되는 경우, API 설계자는 자신이 관리하는 URI와 같이 자체적으로 관리할 수 있고 충돌 가능성이 낮은 네임스페이스를 사용하는 것이 권장된다(RECOMMENDED).¶

다음 예시는 구현에서 네임스페이스 https://scheme.example.org/를 활용해 충돌 가능성이 낮은 유형 값을 보장하는 방법을 보여 준다.¶

2.2. 공통 데이터 필드

이 명세는 서로 다른 유형의 API에서 사용할 수 있도록 설계된 공통 데이터 필드 집합을 정의한다. API를 정의할 때 이 공통 필드를 사용해야 하는 것은 아니다. 이 명세는 API 설계자가 활용할 수 있도록 이 필드들을 재사용 가능한 범용 구성 요소로 제공한다. 모든 필드의 허용 값은 특정 "type" 값에 해당하는 보호 대상 API가 정한다.¶

locations:
리소스 또는 RS의 위치를 나타내는 문자열 배열이다. 이러한 문자열은 일반적으로 RS의 위치를 식별하는 URI이다. 12절에서 설명하듯이, client는 이 필드를 사용해 특정 RS를 지정할 수 있다.¶
actions:
리소스에서 수행할 작업의 종류를 나타내는 문자열 배열이다.¶
datatypes:
리소스에 요청하는 데이터의 종류를 나타내는 문자열 배열이다.¶
identifier:
API에서 제공하는 특정 리소스를 가리키는 문자열 식별자이다.¶
privileges:
리소스에 대해 요청하는 권한의 유형이나 수준을 나타내는 문자열 배열이다.¶

서로 다른 공통 데이터 필드를 함께 사용하면 client가 요청하는 권한은 각 필드에 나열된 값의 모든 조합에 해당한다. 즉, 객체는 그 안에 나열된 모든 actions 값을 객체에 나열된 모든 locations 위치에서 객체에 나열된 모든 datatypes 유형에 적용하도록 요청한다. 다음 예에서 client는 read 및 write 접근을 요청한다. 두 접근 권한은 모두 고객의 contacts와 photos에 적용되며, 이 요청은 customer_information API를 대상으로 한다. 이 요청이 승인되면 client는 사진 읽기나 연락처 쓰기 등 API에서 정의한 권한을 어떤 조합으로든 행사할 수 있다고 본다.¶

client가 접근 권한을 더 세밀하게 지정하려면 여러 객체를 보낼 수 있다. 이 예에서 client는 동일한 API endpoint에서 read 권한은 contacts에 대해, write 권한은 photos에 대해 요청한다. 이 요청이 승인되어도 client는 연락처에 쓸 수 없다.¶

API는 자체 확장을 정의할 수 있으며(MAY), 해당 인가 객체의 type을 따라야 한다. API 설계자는 이 명세에서 정의한 공통 데이터 필드와 해당 API의 전용 필드를 함께 사용할 것으로 예상된다. 다음 비규범적 예는 서로 다른 가상의 API type 값 두 개에 공통 필드와 API 전용 필드를 함께 사용하는 방법을 보여 준다. 첫 번째 접근 요청에는 이 명세에서 정한 actions, locations, datatypes 필드뿐 아니라 API 전용 geolocation 필드도 포함되며, 이 전용 필드는 주어진 좌표에서 촬영한 사진에 대한 접근을 나타낸다. 두 번째 접근 요청에는 이 명세에서 정한 actions 및 identifier 필드와 API 전용 currency 필드가 포함된다.¶

이 요청이 승인되면, 앞의 예와 마찬가지로 발급되는 access token의 접근 권한은 두 API 각각에 대해 요청된 접근 유형의 합집합이다.¶

3. 인가 요청

인가 요청 매개변수 authorization_details는 인가 요구 사항을 지정하는 데 사용할 수 있다. 같은 목적으로 scope 매개변수를 사용하는 곳이라면 어디서나 쓸 수 있으며, 그 예는 다음과 같다.¶

  • [RFC6749]에 명시된 인가 요청¶
  • [RFC8628]에 명시된 기기 인가 요청¶
  • [OID-CIBA]에서 정의하는 backchannel 인증 요청¶

[RFC6749]에서 정의한 인가 요청의 경우, 구현자는 다음 방안을 고려할 수 있다(MAY). 흐름의 보안, 개인정보 보호, 신뢰성을 높이기 위해 pushed authorization requests [RFC9126]를 사용하는 것이다. 자세한 내용은 12절, 13절, 11.4절을 참조한다.¶

매개변수의 인코딩은 매개변수를 사용하는 맥락에 따라 정해진다. [RFC6749]에 따른 인가 요청에서는 직렬화된 JSON을 application/x-www-form-urlencoded 형식으로 인코딩한다. 그림 8에서 2절의 예를 사용해 이를 보여 준다(줄바꿈은 표시용이다).¶

AS는 authorization_details 매개변수에 제공된 데이터를 바탕으로, 요청된 접근 권한에 동의하는지 사용자에게 묻는다.¶

참고: 사용자는 요청된 상세 인가 정보의 일부만 승인할 수도 있다.¶

그림 9에서 client는 계좌 정보에 접근하고 지급을 개시하려 한다.¶

3.1. "scope" 매개변수와의 관계

authorization_details와 scope를 같은 인가 요청에서 사용해 각각 별개의 인가 요구 사항을 전달할 수 있다.¶

이 명세가 authorization_details와 scope의 병용을 지원하는 이유 중 하나는 기존 OAuth 기반 애플리케이션이 authorization_details만 사용하도록 점진적으로 전환할 수 있게 하기 위해서이다. 개별 API에서는 요구 사항을 명시하는 형식을 한 가지만 사용하는 것이 권장된다(RECOMMENDED).¶

AS는 주어진 인가 요청에 대해 두 요구 사항 집합을 함께 처리해야 한다(MUST). AS가 이 매개변수들을 어떻게 결합하는지는 보호 대상 API에 따라 다르며 이 명세의 범위를 벗어난다.¶

사용자 동의를 받을 때 AS는 인가 요청이 나타내는 요구 사항을 하나로 합쳐 사용자에게 제시해야 한다(MUST).¶

resource owner가 client에 요청된 접근 권한을 부여하면, AS는 해당 authorization_details(및 해당하는 경우 scope 값)과 연결된 token을 client에 발급한다.¶

3.2. "resource" 매개변수와의 관계

인가 요청 매개변수 resource는 [RFC8707]에서 정의하며, 요청된 scope가 적용될 수 있는 리소스를 더 구체적으로 지정하는 데 사용할 수 있다. resource 매개변수는 AS가 authorization_details 인가 요청 매개변수를 처리하는 방식에 아무런 영향을 주지 않는다.¶

4. 인가 응답

이 명세는 인가 응답에 대한 확장을 정의하지 않는다.¶

5. 인가 오류 응답

AS는 알 수 없는 유형의 상세 인가 정보나 해당 유형의 정의를 따르지 않는 상세 인가 정보의 처리를 거부해야 한다(MUST). AS는 아래 조건에 해당하면 반드시(MUST) 처리를 중단하고 client에 invalid_authorization_details 오류로 응답해야 한다. 이는 authorization_details 구조에 들어 있는 객체가 하나라도 다음 조건 중 적어도 하나를 충족하는 경우다.¶

  • 알 수 없는 상세 인가 정보 유형 값을 포함함¶
  • 알려진 유형의 객체이지만 알 수 없는 필드를 포함함¶
  • 해당 상세 인가 정보 유형에서 요구하는 데이터 유형과 맞지 않는 필드를 포함함¶
  • 해당 상세 인가 정보 유형에서 유효하지 않은 값이 들어 있는 필드를 포함함¶
  • 해당 상세 인가 정보 유형의 필수 필드가 누락됨¶

6. 토큰 요청

token 요청 매개변수 authorization_details를 사용해 client가 AS에 access token에 할당해 달라고 요청하는 상세 인가 정보를 지정할 수 있다. AS는 요청의 근거가 되는 grant(authorization_code, refresh_token 등의 grant type인 경우) 또는 client의 정책(client_credentials grant type인 경우)이 요청된 상세 인가 정보를 담은 access token의 발급을 허용하는지 확인한다. 허용하지 않으면 AS는 invalid_authorization_details 오류 코드(invalid_scope와 유사함)로 요청을 거부한다.¶

6.1. 상세 인가 정보 비교

OAuth 프로토콜의 여러 동작에서 AS와 RS는 현재 요청이 이미 존재하는 이전 요청보다 권한을 ‘더 많이’ 또는 ‘더 적게’ 요구하는지에 따라 보안 결정을 내릴 수 있다. 예를 들어 token을 갱신할 때 client는 resource owner가 이전에 인가한 것보다 ‘더 적은 권한’을 담은 새 access token을 요청할 수 있다. 요청한 access token에는 줄어든 권한이 반영되지만, 이러한 요청이 resource owner의 이전 인가를 변경하지는 않는다. authorization_details의 각 필드가 무엇을 의미하는지는 해당 API 또는 API 집합의 구현에 따라 달라지므로 임의의 상세 인가 정보 요청 두 개를 비교하는 표준 방식은 없다. API의 설계 및 배포 방식에 따라 요청에 포함된 일부 필드를 함께 적용했을 때 부여되는 접근 권한에 부수 효과가 생길 수 있으므로, 대부분의 경우 AS는 단순한 객체 비교에 의존하지 않는 것이 좋다. 일부 API에서 사용하는 scope 값에도 이와 비슷한 효과가 나타난다.¶

AS는 새 요청을 기존 요청과 비교할 때, 처음 요청을 승인하는 데 사용한 것과 같은 처리 기법을 사용해 resource owner가 새 요청을 인가해야 하는지 판단할 수 있다. 이 비교의 세부 사항은 인가 요청의 type 정의에 따라 달라지며 이 명세의 범위를 벗어나지만, 공통 패턴을 적용할 수는 있다.¶

앞에서부터 이어 온 예를 통해 이를 설명한다. 사용자가 3절의 인가 요청 예를 승인하면 다음 권한과 연결된 authorization code(인가 코드)가 발급된다.¶

  • 계좌 목록 조회¶
  • 하나 이상의 계좌 잔액 조회¶
  • 하나 이상의 계좌 거래 내역 조회¶
  • 지급 개시, 상태 확인 및 취소¶

이제 client는 다음과 같이 계좌 목록을 조회할 권한만 있는 access token을 발급하도록 AS에 요청할 수 있다.¶

이 예의 API는 account_information 유형이 사용하는 각 필드의 권한이 누적되고, actions 및 locations 배열 내의 각 값이 서로 다른 접근 요소를 지정하도록 설계되었다. 이 경우 AS는 다음 단계로 비교를 수행한다.¶

  • 이전 단계에서 발급된 authorization code에 유형이 account_information인 상세 인가 정보 객체가 포함되어 있는지 확인한다.¶
  • 승인된 작업 목록에 list_accounts가 있는지 확인한다.¶
  • locations 값에 이전에 승인한 위치만 포함되어 있는지 확인한다.¶

모든 검사를 통과하면 AS는 줄어든 접근 권한으로 요청된 access token을 발급한다.¶

이 비교는 이 특정 API 유형 정의에 해당한다는 점에 유의한다. 다른 API 유형 정의에서는 처리 규칙이 다를 수 있다. 예를 들어 한 actions 값이 다른 actions 값에 해당하는 권한까지 포함할 수 있다. 가령 client가 처음에 write 접근 권한이 있는 토큰을 요청하면, 이 API에 대한 읽기와 쓰기 접근 권한을 모두 요청하는 셈이다.¶

이후 같은 client가 read 접근 권한을 얻기 위해 갱신 요청을 보낸다.¶

AS는 type 값과 actions 값을 비교하여, read 접근 권한이 이전에 client에 부여한 write 접근 권한에 이미 포함되어 있음을 확인한다.¶

이 API는 privileges에 admin 값을 사용할 수 있도록 설계할 수도 있다. 이 예시에서 그 값은 발급되는 토큰으로 리소스에 대해 어떤 기능이든 실행할 수 있음을 뜻한다. 이어서 해당 client에 이와 같은 admin 권한을 부여하면 API에 대한 authorization_details는 다음과 같다.¶

AS는 type 값을 비교한 뒤, privileges 값이 이전에 client에 부여한 read 또는 write 접근 권한의 모든 측면을 포괄한다는 것을 확인한다. 다른 API 정의에서는 privileges 값이 서로를 포괄하지 않도록 사용할 수도 있다는 점에 유의한다.¶

다음 예시는 client가 공통 데이터 요소 locations(2.2절 참조)를 사용하여 특정 RS로 제한된 access token의 발급을 요청하는 방법을 보여준다. 앞에서부터 이어지는 예시에서 client는 승인된 payment_initiation 유형의 grant 중 https://example.com/payments에 있는 RS에 적용되는 모든 권한을 다음과 같이 요청할 수 있다.¶

7. 토큰 응답

[RFC6749]에 정의된 토큰 응답 매개변수 외에, AS는 반드시(MUST) resource owner가 부여하고 해당 access token에 할당된 authorization_details도 반환해야 한다.¶

토큰 응답으로 발급된 access token에 할당되는 상세 인가 정보는 그에 대응하는 토큰 요청의 authorization_details 매개변수에 따라 결정된다. client가 토큰 요청에 authorization_details 매개변수를 지정하지 않으면, AS가 그 결과에 적용할 authorization_details를 재량으로 결정한다.¶

AS는 필요에 따라(MAY) client에 보내는 authorization_details에서 일부 값을 생략할 수 있다.¶

앞에서부터 이어지는 예시에서는 다음과 같다.¶

7.1. 토큰 응답에서 보강된 상세 인가 정보

access token에 연결된 상세 인가 정보는 client가 요청한 내용과 다를 수 있다(MAY). 사용자가 client의 요청보다 좁은 범위만 인가하는 경우 외에도, AS가 상세 인가 정보 객체의 데이터를 보강하는 사용 사례가 있다. 보강이 허용되는지, 그리고 구체적으로 어떻게 이루어지는지는 반드시 해당 상세 인가 정보 유형의 정의에 포함된다.¶

예를 들어 client가 계좌 정보에 대한 접근을 요청하되, 어떤 계좌에 접근할 수 있을지는 사용자가 결정하도록 맡길 수 있다. 인가 절차에서 사용자는 자신의 계좌 중 client에 접근을 허용할 계좌를 선택한다. 선택된 계좌를 전달하는 한 가지 설계 방식은 AS가 이 정보를 해당 상세 인가 정보 객체에 추가하는 것이다.¶

이 예시에서 요청에 담긴 authorization_details 매개변수는 다음과 같을 수 있다. 빈 배열은 AS가 데이터를 보강할 때 추가할 위치를 표시한다. 이 예시는 설명을 위한 것일 뿐이며, 어떤 상세 인가 정보 유형의 세부 사항이든 이런 방식으로 설계하는 것이 바람직하다는 뜻은 아니다.¶

그런 다음 AS는 상세 인가 정보 객체를 확장해 해당 계좌 식별자를 추가한다.¶

다른 예로, client가 의료 기록에 대한 접근을 요청하지만 요청 시점에는 기록 번호를 모를 수 있다. 이 예시에서 client는 원하는 접근 유형은 지정하지만, 접근 대상의 위치나 식별자는 지정하지 않는다.¶

사용자는 AS와 상호작용할 때 자신이 제공할 책임이 있는 의료 기록 중 어느 것을 client에 줄지 선택한다. 이 정보는 access token과 함께 반환된다.¶

참고: client는 특정 상세 인가 정보 객체가 보강될 수 있음을 미리 알고 있어야 한다. 이 속성은 해당 상세 인가 정보 유형의 정의에 포함된다고 가정한다.¶

8. 토큰 오류 응답

토큰 오류 응답은 반드시(MUST) 5절의 규칙을 따라야 한다.¶

9. resource server

RS가 인가 과정에서 승인된 상세 인가 정보를 적용할 수 있도록, AS는 반드시(MUST) 이 데이터를 RS에서 이용할 수 있게 해야 한다. AS는 선택적으로(MAY) authorization_details 필드를 JSON Web Token(JWT) 형식의 access token이나 token introspection 응답에 추가할 수 있다.¶

9.1. JWT 기반 access token

access token이 JWT [RFC7519]이면, AS는 특정 audience에 맞게 필터링한 상세 인가 정보 객체를 최상위 claim으로 추가하는 것이 권장된다(RECOMMENDED).¶

일반적으로 AS는 사용자 ID, 역할, 거래별 데이터 등 RS가 요청을 처리하는 데 필요한 추가 claim도 JWT에 넣는다. 해당 RS에 필요한 claim은 AS와의 RS별 정책에서 정한다.¶

다음은 앞의 지급 개시 사례에 대한 JWT 예시의 내용이다.¶

이 예시에서 AS는 JWT 기반 access token에 다음 claim을 추가했다.¶

sub:
client가 어느 사용자를 위해 지급 개시를 요청하는지 나타낸다.¶
txn:
제공자 example.com의 여러 서비스에서 거래를 추적하는 데 사용하는 거래 ID¶
debtorAccount:
출금 계좌가 들어 있는 API 고유 필드다. 이 예시에서는 계좌가 authorization_details로 전달되지 않았고, 인가 과정에서 사용자가 직접 선택했다. user_role 필드는 이 계좌에 대한 사용자의 역할을 전달한다. 이 경우 사용자는 계좌 소유자다. 이 데이터는 지급 API(RS)에서 접근 제어에 사용된다.¶

9.2. token introspection

Token introspection [RFC7662]을 사용하면 RS는 AS에 질의하여 access token에 관한 정보를 확인할 수 있다. AS가 응답에 해당 토큰의 상세 인가 정보를 포함한다면, 반드시(MUST) introspection 응답의 JSON 객체에서 최상위 멤버인 authorization_details로 전달해야 한다. authorization_details 멤버는 반드시(MUST) 2절에서 정의한 것과 같은 구조를 담아야 하며, introspection을 요청한 RS에 맞게 필터링하고 확장할 수 있다.¶

11. 구현 시 고려 사항

11.1. 특정 배포 환경에서 상세 인가 정보 사용

특정 배포 환경에서 상세 인가 정보를 사용하려면 다음 단계가 필요하다.¶

  • 상세 인가 정보 유형을 정의한다.¶
  • OAuth 서버 메타데이터에 상세 인가 정보 유형을 공개한다.¶
  • 사용자 동의 화면에서 사용자에게 상세 인가 정보를 어떻게 표시할지 정한다.¶
  • 필요하면 사용자 동의 과정에서 상세 인가 정보를 보강한다(예: 선택된 계좌 추가 또는 만료 시점 설정).¶
  • 필요하면 상세 인가 정보를 access token의 내용이나 introspection 응답에 어떻게 반영할지 정한다.¶
  • RS가 상세 인가 정보 또는 그 정보에서 파생된 토큰 데이터를 어떻게 처리할지 정한다.¶
  • 필요하면 client에 특정 상세 인가 정보 유형을 사용할 권한을 부여한다.¶

11.2. 구현에서 지원할 최소 기능

이 명세를 지원하는 일반적인 AS 구현은 다음 기본 기능을 제공하는 것이 바람직하다.¶

  • 지원하는 상세 인가 정보 유형을 OAuth 서버 메타데이터로 알릴 수 있게 한다.¶
  • 이 명세에 따라 인가 요청에서 authorization_details 매개변수를 받는다.¶
  • 사용자가 동의한 상세 인가 정보를 grant의 일부로 저장할 수 있게 한다.¶
  • RS가 상세 인가 정보를 이용할 수 있도록 access token과 token introspection 응답에 이를 추가하는 기본 동작을 구현한다(scope 값과 유사하다). 이 동작은 모든 grant type, 특히 authorization_code와 refresh_token에서 작동하는 것이 바람직하다.¶

상세 인가 정보를 처리하고 표시하는 방식은 유형에 따라 크게 달라진다. 따라서 구현체는 각 유형에 맞게 동작을 맞춤 설정할 수 있도록 지원하는 것이 좋다. 특히 배포 환경별로 다음을 할 수 있도록 하는 것이 좋다.¶

  • 상세 인가 정보를 표시하는 방식을 정한다.¶
  • 사용자 동의 과정에서 필드를 추가하는 등 요청된 상세 인가 정보를 수정한다.¶
  • 요청된 상세 인가 정보를 기존 상세 인가 정보와 병합한다.¶

이러한 맞춤 설정을 지원하는 한 가지 방법은 확장 모듈을 등록할 수 있는 메커니즘을 두는 것이다. 각 모듈은 해당 유형의 사용자 동의 화면을 표시하고, 구조화된 access token이나 token introspection 응답을 통해 RS에 필요한 데이터를 제공하기 위해 요구되는 변환을 수행한다.¶

11.3. 기계 판독 가능한 유형 스키마 사용

구현체는 배포 환경에서 기계 판독 가능한 스키마 언어로 상세 인가 정보의 유형을 정의할 수 있도록 할 수 있다. 그러면 상세 인가 정보 객체를 생성하고 해당 스키마에 따라 검증하기가 쉬워진다. 예를 들어 상세 인가 정보의 type을 JSON Schema [JSON.Schema]로 정의한다면, 해당 상세 인가 정보 객체에서 JSON Schema 식별자를 type 값으로 사용할 수 있다.¶

다만 type 값은 AS가 이해하는 식별자이며, client와 RS도 필요한 범위에서 이해한다는 점에 유의해야 한다. 이 명세는 type 값이 기계 판독 가능한 스키마를 가리킨다고 가정하지 않으며, client, AS, RS 등 시스템의 어느 참여자도 type 필드가 가리키는 대상을 조회하거나 그 필드의 내용을 특정 방식으로 처리한다고 가정하지 않는다.¶

11.4. 대용량 요청

요청 매개변수나 request object(요청 객체)에 authorization_details를 포함하는 인가 요청 URI는 매우 길어질 수 있다. 따라서 구현자는 request_uri 매개변수([RFC9101]에서 정의)와 푸시 방식으로 request object를 전달하는 메커니즘([RFC9126]에서 정의)을 함께 사용해 authorization_details를 안정적이고 안전하게 전달하는 방안을 고려하는 것이 좋다. 다음은 HTTPS로 보호되는 연결을 통해 인가 요청 데이터를 AS에 직접 보내는 푸시 인가 요청의 예이다.¶

12. 보안 고려 사항

OAuth 인가 요청에서 authorization_details 매개변수는 user agent를 거쳐 전송되므로 사용자가 변조할 수 있다. authorization_details의 무결성이 중요하다면, client는 반드시(MUST) authorization_details가 변조되거나 다른 값으로 바뀌지 않도록 보호해야 한다. 이를 위해 [RFC9101]에 정의된 서명된 request object를 사용해 요청에 서명할 수 있다. 또는 request_uri 인가 요청 매개변수([RFC9101]에서 정의)를 [RFC9126]과 함께 사용해 request object의 URI를 AS로 전달할 수 있다.¶

authorization_details 매개변수의 모든 문자열 비교는 [RFC8259]에서 정의한 방식에 따라 수행해야 한다. 문자열 값이 같은지 판단할 때 추가 변환이나 정규화를 해서는 안 된다.¶

공통 데이터 필드인 locations를 사용하면 client가 특정 인가를 어디에서 사용하려는지 지정할 수 있다. 즉, 어떤 RS에 어떤 권한이 적용되는지를 명확히 정할 수 있다. RS가 여러 개인 경우 audience를 제한하면 의도하지 않은 인가가 client에 부여되는 것을 막을 수 있다. 예를 들어 read scope 값이 이메일 서비스와 클라우드 서비스 양쪽에 적용될 수 있는 상황이 이에 해당한다.¶

AS는 반드시(MUST) 인젝션 공격을 방지하도록 authorization_details로 전달된 데이터를 적절히 정제하고 처리해야 한다.¶

[RFC6749], [RFC7662], [RFC8414]의 보안 고려 사항도 적용된다.¶

13. 개인정보 보호 고려 사항

구현자는 개인정보를 보호하는 방식으로 상세 인가 정보를 설계하고 사용하는 것이 특히 중요하다.¶

authorization_details에 포함된 민감한 개인정보가 리퍼러 헤더 등을 통해 유출되지 않도록 해야 한다. 구현 방법으로는 [RFC9101]에 정의된 암호화된 request object를 사용하거나, authorization_details를 client와 AS 사이의 종단 간 암호화 연결로 전송하는 것이 있다. 후자의 경우 [RFC9126]과 request_uri 인가 요청 매개변수([RFC9101]에서 정의)를 활용한다. 이 방법은 애플리케이션 수준의 암호화가 필요하지 않지만, client와 AS가 메시지를 한 차례 더 교환해야 한다.¶

요청 데이터가 암호화되어 있어도 공격자는 AS를 이용해 사용자의 데이터를 알아낼 수 있다. 공격자가 자신이 제어하는 기기에서 인가 요청에 암호화된 요청 데이터를 삽입하면, AS의 사용자 동의 화면에 복호화된 사용자 데이터가 평문으로 표시될 수 있기 때문이다. 구현체는 이러한 공격 경로를 고려해 적절한 대응책을 마련해야 한다. 예를 들어 데이터의 일부만 표시하거나, 가능하다면 사용자 인증 후에 전제했던 사용자 맥락이 그대로 유지되는지 확인할 수 있다.¶

AS는 authorization_details를 client 또는 RS와 공유할 때 개인정보 보호에 미치는 영향을 고려해야 한다. 이 데이터는 해당 배포 환경의 로컬 정책에 따라 각 당사자가 알아야 할 범위에서만 공유하는 것이 좋다.¶

A.1. OpenID Connect

OpenID Connect [OIDC]는 JSON 기반의 claims 요청 매개변수를 정의한다. OpenID Connect Relying Party로 동작하는 client는 이 매개변수를 사용해 개인정보를 보호하면서 어떤 claim을 받고 싶은지 세밀하게 지정할 수 있다. 또한 각 claim을 ID Token(ID 토큰)이나 userinfo 응답 중 어느 방식으로 전달받을지도 지정할 수 있다.¶

scope 값 openid와 추가 매개변수 claims의 조합은 OIDC에 속하지 않는 다른 모든 scope 값과 마찬가지로 authorization_details와 함께 사용할 수 있다.¶

또 다른 방법으로는 OpenID Connect용 상세 인가 정보 유형을 둘 수 있다. 이 절에서는 그러한 유형이 어떤 형태일 수 있는지 예시를 보여 주지만, 이 유형을 정의하는 것은 이 명세의 범위를 벗어난다.¶

이 가상의 예시에서는 인가 절차 중 OpenID Connect에 해당하는 모든 세부 정보를 하나의 인가용 JSON 객체에 담고자 한다.¶

최상위 필드는 [OIDC]의 정의를 따른다.¶

claim_sets:
사전 정의된 claim 집합의 이름으로, 각 집합에 대응하는 scope 값(예: profile)을 대신한다.¶
max_age:
인증 후 허용되는 최대 경과 시간¶
acr_values:
요청하는 인증 컨텍스트 클래스 참조(ACR) 값¶
claims:
claims JSON 구조(정의는 [OIDC] 참조)¶

다음은 몇 가지 claim 집합을 요청하는 간단한 예시다.¶

참고: locations는 userinfo endpoint의 위치를 지정한다. OpenID Connect에서 client(Relying Party)가 claim을 얻기 위해 access token을 사용하는 곳은 이 endpoint뿐이기 때문이다.¶

좀 더 복잡한 예시는 그림 26에 나와 있다.¶

A.2. 원격 전자 서명

최상위 필드의 의미는 다음과 같다.¶

A.4. eHealth

다음 두 예시는 노르웨이 eHealth 시스템에서 사용하는 API의 요구 사항에서 착안했다.¶

이 사례에서 물리치료사는 자신의 컴퓨터에서 로컬 전자건강기록(EHR) 시스템을 사용한다. 물리치료사는 특정 환자의 전자 환자 기록을 열람하고, 다른 시스템에 있는 그 환자의 진료기록 항목도 가져오려 한다. 그 시스템은 다른 기관이나 국가 차원의 서비스에서 운영하는 것일 수 있다. 이 데이터에는 API를 통해 접근할 수 있다.¶

API에서 요청을 인가하는 데 필요한 정보는 EHR 시스템만 알고 있으며, 이 정보를 API에 제시해야 한다.¶

첫 번째 예시에서 상세 인가 정보 객체에는 조직의 식별자가 들어 있다. 이 경우 API는 민감한 데이터에 대한 접근을 허용하기 위해 해당 조직에 개인 건강 정보를 처리할 적법한 근거가 있는지 확인해야 한다.¶

두 번째 예시에서 API는 요청을 인가하기 위해 더 많은 정보를 요구한다. 이 경우 상세 인가 정보 객체에는 의료 기관과 요청 시점의 사용자 직종에 관한 추가 정보가 들어 있다. 이렇게 더 상세한 정보는 인가와 데이터 최소화 양쪽에 활용할 수 있다.¶

필드 설명:¶

patient_identifier:
환자 식별자이며, OID 형식의 시스템 식별자(네임스페이스)와 해당 네임스페이스 내의 실제 값으로 구성된다.¶
reason_for_request:
사용자가 특정 API에 접근하려는 이유다.¶
requesting_entity:
요청자의 신원, 역할 및 조직 내 맥락을 명시한다. 이 데이터는 인가를 용이하게 하고 감사에 활용하기 위해 제공된다.¶

이 사례에서 AS는 환자가 아닌 요청자를 인증하고, 정책에 따라 접근을 승인한다.¶
