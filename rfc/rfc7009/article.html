초록

이 문서는 OAuth authorization server(인가 서버)에 추가할 endpoint를 제안한다. 이 endpoint를 통해 client(클라이언트)는 이전에 얻은 refresh token(갱신 토큰) 또는 access token(접근 토큰)이 더 이상 필요하지 않음을 authorization server에 알릴 수 있다. 이를 통해 authorization server는 보안 credential을 정리할 수 있다. 철회 요청은 해당 token을 무효화하며, 해당되는 경우 동일한 authorization grant(인가 승인)에 기반한 다른 token도 무효화한다.

이 메모의 상태

이 문서는 Internet Standards Track 문서다.

이 문서는 Internet Engineering Task Force(IETF)의 결과물이다. IETF 커뮤니티의 합의를 나타낸다. 공개 검토를 거쳤으며 Internet Engineering Steering Group(IESG)의 발행 승인을 받았다. Internet Standards에 관한 추가 정보는 RFC 5741의 2절에서 확인할 수 있다.

이 문서의 현재 상태, 정오표 및 의견을 전달하는 방법에 관한 정보는 http://www.rfc-editor.org/info/rfc7009에서 확인할 수 있다.

1. 소개

OAuth 2.0 핵심 명세 [RFC6749]는 client가 refresh token과 access token을 얻는 여러 방법을 정의한다. 이 명세는 두 종류의 token을 모두 철회하는 메커니즘으로 핵심 명세를 보완한다. token은 resource owner(리소스 소유자)가 client에 발급한 authorization grant를 나타내는 문자열이다. 철회 요청은 해당 token을 무효화하며, 해당되는 경우 동일한 authorization grant에 기반한 다른 token과 authorization grant 자체도 무효화한다.

최종 사용자 관점에서 OAuth는 특정 사이트나 애플리케이션에 로그인하는 데 자주 사용된다. 이 철회 메커니즘을 통해 client는 최종 사용자가 로그아웃하거나, 신원을 변경하거나, 해당 애플리케이션을 제거할 때 자신의 token을 무효화할 수 있다. token이 더 이상 필요하지 않음을 authorization server에 알리면 authorization server는 해당 token과 연관된 데이터(예: session 데이터)와 그 기반이 되는 authorization grant를 정리할 수 있다. 이러한 동작은 최종 사용자가 알지 못하는 상태에서 특정 client에 대한 유효한 authorization grant가 남아 있는 상황을 방지한다. 이처럼 token 철회는 방치된 token의 오용을 방지한다. 또한 무효화된 authorization grant가 authorization server에서 최종 사용자에게 제시할 수 있는 authorization grant 목록에 더 이상 나타나지 않으므로 최종 사용자 경험도 개선된다.

1.1. 요구사항 표현

이 문서에서 사용하는 핵심 단어 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", "OPTIONAL"은 RFC 2119 [RFC2119]에 설명된 대로 해석해야 한다.

2. Token 철회

구현은 refresh token 철회를 지원해야 하며(MUST), access token 철회도 지원하는 것이 좋다(SHOULD)(구현 참고 사항 참조).

client는 token revocation endpoint(철회 엔드포인트) URL에 HTTP POST 요청을 보내 특정 token의 철회를 요청한다. 이 URL은 [RFC6749]의 3.1절에 제시된 규칙을 준수해야 한다(MUST). client는 해당 URL이 HTTPS URL인지 확인해야 한다(MUST).

revocation endpoint의 위치를 얻는 수단은 이 명세의 범위를 벗어난다. 예를 들어 client 개발자는 서버 문서를 참조할 수도 있고 자동 탐색을 사용할 수도 있다. 이 endpoint는 보안 credential을 처리하므로 신뢰할 수 있는 출처에서 endpoint 위치를 얻어야 한다.

token revocation endpoint에 대한 요청은 HTTP 요청 안에 평문 credential을 담아 전송하므로, token revocation endpoint의 URL은 HTTPS URL이어야 한다(MUST). authorization server는 [RFC6749]의 1.6절을 준수하는 버전의 Transport Layer Security(TLS) [RFC5246]를 사용해야 한다(MUST). 구현은 자체 보안 요구사항을 충족하는 추가 transport-layer 보안 메커니즘도 지원할 수 있다(MAY).

token revocation endpoint의 호스트에 HTTP로도 접속할 수 있다면, 서버는 대응하는 HTTP URI에서도 철회 서비스를 제공하는 것이 좋다(SHOULD). 다만 이 URI를 token revocation endpoint로 공개해서는 안 된다(MUST NOT). 이렇게 하면 실수로 HTTP를 통해 전송된 token도 철회된다.

2.1. 철회 요청

client는 HTTP 요청의 entity-body에 "application/x-www-form-urlencoded" 형식으로 다음 parameter를 포함하여 요청을 구성한다.

token
REQUIRED. client가 철회하려는 token이다.
token_type_hint
OPTIONAL. 철회를 위해 제출한 token의 유형에 관한 힌트다. client는 authorization server가 token 조회를 최적화하는 데 도움이 되도록 이 parameter를 전달할 수 있다(MAY). 서버가 주어진 힌트로 token을 찾지 못하면, 지원하는 모든 token 유형으로 검색 범위를 확대해야 한다(MUST). authorization server는 이 parameter를 무시할 수 있으며(MAY), 특히 token 유형을 자동으로 감지할 수 있는 경우 그러하다. 이 명세는 다음 두 값을 정의한다.
* access_token: [RFC6749]의 1.4절에 정의된 access token
* refresh_token: [RFC6749]의 1.5절에 정의된 refresh token

이 명세의 구체적인 구현, profile 및 확장은 4.1.2절에 정의된 registry를 사용하여 이 parameter의 다른 값을 정의할 수 있다(MAY).

client는 [RFC6749]의 2.3절에 설명된 대로 자신의 인증 credential도 포함한다.

예를 들어 client는 다음 요청으로 refresh token의 철회를 요청할 수 있다.

     POST /revoke HTTP/1.1
     Host: server.example.com
     Content-Type: application/x-www-form-urlencoded
     Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW

     token=45ghiukldjahdnhzdauz&token_type_hint=refresh_token

authorization server는 먼저 client credential을 검증하고(confidential client(기밀 클라이언트)인 경우), 이어서 해당 token이 철회 요청을 보낸 client에 발급되었는지 확인한다. 이 검증이 실패하면 요청이 거부되고, authorization server는 아래에 설명된 대로 client에 오류를 알린다.

다음 단계에서 authorization server는 token을 무효화한다. 무효화는 즉시 이루어지며, 철회 후에는 token을 다시 사용할 수 없다. 실제로는 전파 지연이 발생할 수 있다. 예를 들어 일부 서버는 무효화 사실을 알고 있지만 다른 서버는 알지 못할 수 있다. 구현은 이러한 시간 구간을 최소화하는 것이 좋으며, client는 서버에서 HTTP 200 응답을 받은 후 해당 token을 사용하려 해서는 안 된다.

authorization server의 철회 정책에 따라 특정 token의 철회가 관련 token과 그 기반이 되는 authorization grant의 철회로 이어질 수 있다. 해당 token이 refresh token이고 authorization server가 access token 철회를 지원한다면, authorization server는 동일한 authorization grant에 기반한 모든 access token도 무효화하는 것이 좋다(SHOULD)(구현 참고 사항 참조). 요청에 전달한 token이 access token이라면 서버는 대응하는 refresh token도 철회할 수 있다(MAY).

참고: [RFC6749]를 준수하는 client는 언제든 예기치 않은 token 무효화를 처리할 준비가 되어 있어야 한다. 이 문서에 명시된 철회 메커니즘과는 별개로 resource owner가 authorization grant를 철회할 수도 있고, authorization server가 보안 위협을 완화하기 위해 token을 무효화할 수도 있다. 따라서 token 철회의 연쇄 적용에 관해 서버마다 정책이 달라도 상호운용성 문제가 발생하지는 않을 것이다.

2.2. 철회 응답

authorization server는 token이 성공적으로 철회되었거나 client가 유효하지 않은 token을 제출한 경우 HTTP 상태 코드 200으로 응답한다.

참고: client가 이런 오류를 합리적으로 처리할 수 없으므로 유효하지 않은 token으로 인해 오류 응답이 발생하지는 않는다. 또한 특정 token을 무효화한다는 철회 요청의 목적은 이미 달성된 상태다.

필요한 모든 정보가 응답 코드로 전달되므로 client는 응답 body의 내용을 무시한다.

authorization server는 유효하지 않은 token type hint 값을 무시하며, 이 값은 철회 응답에 영향을 주지 않는다.

2.2.1. 오류 응답

오류 표시는 [RFC6749]의 5.2절에 있는 정의를 따른다. token revocation endpoint를 위해 다음과 같은 추가 오류 코드를 정의한다.

unsupported_token_type:
authorization server가 제시된 token 유형의 철회를 지원하지 않는다. 즉, client가 이 기능을 지원하지 않는 server에서 access token을 철회하려고 시도했다.

server가 HTTP 상태 코드 503으로 응답하면 client는 token이 여전히 존재한다고 가정해야 하며, 적절한 시간이 지난 뒤 재시도할 수 있다. server는 요청한 client에 서비스가 얼마나 오랫동안 이용 불가능할 것으로 예상되는지 알리기 위해 응답에 "Retry-After" header를 포함할 수 있다.

2.3. Cross-Origin 지원

revocation endpoint가 user-agent 기반 application과 함께 사용되는 것을 목적으로 한다면 Cross-Origin Resource Sharing(CORS) [W3C.WD-cors-20120403]을 지원할 수 있다(MAY).

또한 기존 user-agent와의 상호운용성을 위해, 다음 추가 parameter를 사용하는 GET 요청을 허용하여 JSONP(Remote JSON - JSONP) [jsonp]도 제공할 수 있다(MAY).

callback:
선택 사항이다(OPTIONAL). JavaScript 함수의 qualified name이다.

예를 들어 client는 다음 요청으로 access token의 철회를 요청할 수 있다(줄바꿈은 표시 목적으로만 넣었다).

     https://example.com/revoke?token=agabcdefddddafdd&
     callback=package.myCallback

성공 응답:

     package.myCallback();

오류 응답:

     package.myCallback({"error":"unsupported_token_type"});

client는 JSONP에 의존할 때 악의적인 revocation endpoint가 client에 악성 코드를 주입하려고 시도할 수 있음을 알아두는 것이 좋다.

3. 구현 참고 사항

OAuth 2.0은 access token의 형식에 관해 유연한 배포를 허용한다. access token을 자체 완결적으로 구성하여, resource server(리소스 서버)가 보호된 resource에 접근을 요청하는 client에 대한 인가 결정을 내릴 때 이 token을 발급한 authorization server와 추가로 상호작용할 필요가 없도록 할 수 있다. 그러나 시스템을 설계할 때 그 대신 authorization server에 저장된 인가 데이터를 참조하는 handle을 access token으로 사용할 수도 있다. 이 경우 resource server는 client가 access token을 제시할 때마다 해당 authorization server에 요청을 보내 access token의 내용을 가져와야 한다.

이것들만이 유일한 선택지는 아니지만, 철회에 어떤 영향이 있는지 보여 준다. 후자의 경우 resource server가 수신한 access token을 전달하면 authorization server는 이전에 client에 발급한 access token을 철회할 수 있다. 전자의 경우 access token을 즉시 철회하려면 authorization server와 resource server 사이에 (현재 표준화되지 않은) backend 상호작용을 사용할 수 있다. 또 다른 설계 대안은 수명이 짧은 access token을 발급하는 것이다. 이 token은 대응하는 refresh token을 사용하여 언제든지 갱신할 수 있다. 이를 통해 authorization server는 access token이 사용 중일 때 철회가 반영될 때까지 걸리는 시간에 상한을 둘 수 있다.

어떤 token 철회 방식을 선택할지는 전체 시스템 설계와 application 서비스 제공자의 위험 분석에 달려 있다. 필요한 상태 정보와 통신 overhead 측면에서 철회에 드는 비용은 결국 원하는 보안 속성에 따라 결정된다.

4. IANA 고려 사항

이 명세는 "OAuth Extensions Error Registry"에 오류 값을 등록하고 "OAuth Token Type Hints" registry를 신설한다.

4.1. OAuth 확장 오류 등록

이 명세는 [RFC6749]에 정의된 "OAuth Extensions Error Registry"에 다음 오류 값을 등록한다.

4.1.1. "unsupported_token_type" 오류 값

오류 이름:
unsupported_token_type
오류 사용 위치:
revocation endpoint의 오류 응답
관련 protocol 확장:
Token Revocation Endpoint
변경 관리 주체:
IETF
명세 문서:
[RFC7009]

4.1.2. OAuth Token Type Hints Registry

이 명세는 "OAuth Token Type Hints" registry를 신설한다. "token_type_hint" parameter(2.1절 참조)에 사용할 수 있는 값은 한 명 이상의 Designated Expert(지정 전문가)의 조언에 따라, oauth-ext-review@ietf.org mailing list에서 2주간 검토한 뒤 Specification Required([RFC5226]) 절차로 등록한다. 다만 발행 전에 값을 할당할 수 있도록, Designated Expert는 그러한 명세가 발행될 것이라는 확신이 들면 등록을 승인할 수 있다. 등록 요청은 적절한 제목(예: "Request for parameter: example")으로 oauth-ext-review@ietf.org mailing list에 보내 검토와 의견 수렴을 거쳐야 한다. 검토 기간 내에 Designated Expert는 등록 요청을 승인하거나 거부하고, 그 결정을 검토 list와 IANA에 알린다. 거부 시에는 설명을 포함하는 것이 좋으며, 해당하는 경우 요청이 승인되려면 어떻게 해야 하는지에 대한 제안도 포함하는 것이 좋다. IANA는 Designated Expert가 보낸 registry 갱신만 수락해야 하며, 모든 등록 요청을 검토 mailing list로 안내하는 것이 좋다.

4.1.2.1. 등록 양식
Hint 값:
authorization server에 특정 token 유형을 알리는 데 사용할 수 있는 추가 값이다.
변경 관리 주체:
Standards Track RFC의 경우 "IETF"라고 기재한다. 그 밖의 경우에는 책임 주체의 이름을 기재한다. 다른 세부 정보(예: 우편 주소, email 주소, 홈페이지 URI)도 포함할 수 있다.
명세 문서:
해당 유형을 명시하는 문서에 대한 참조이며, 가급적 문서 사본을 가져오는 데 사용할 수 있는 URI를 포함한다. 관련 절을 표시할 수도 있지만 필수는 아니다.

OAuth Token Type Hint registry의 초기 내용은 다음과 같다.

             +---------------+-------------------+-----------+

5. 보안 고려 사항

authorization server가 access token 철회를 지원하지 않으면 대응하는 refresh token을 철회해도 access token이 즉시 무효화되지 않는다. 배포 환경에서는 보안 위험을 분석할 때 이를 고려해야 한다.

철회를 통해 token을 정리하면 방치된 token의 악용 가능성이 줄어들므로 전반적인 보안과 개인정보 보호에 도움이 된다. 이 명세는 일반적으로 token 탈취와 악용에 대한 대응책을 제공하려는 것은 아니다. 관련 위협과 대응책에 관한 논의는 OAuth 핵심 명세 [RFC6749]의 10절과 OAuth 위협 모델 문서 [RFC6819]에 제시된 보안 고려 사항을 참조한다.

악의적인 client는 새로운 endpoint를 이용하여 authorization server에 서비스 거부 공격을 가하려고 시도할 수 있다. 적절한 대응책을 revocation endpoint에 반드시 적용해야 한다(MUST) ([RFC6819]의 4.4.1.11절 참조). token endpoint에도 이러한 대응책을 마련하는 것이 좋다. 특히, 유효하지 않은 token type hint는 authorization server를 잘못 유도하여 추가 database 조회를 유발할 수 있다. 악의적인 client가 이 기능을 악용하여 서비스 거부 공격을 가하지 못하도록 반드시 주의를 기울여야 한다(MUST).

악의적인 client는 token일 가능성이 있는 문자열을 대상으로 철회 요청을 보내, 이 endpoint에서 유효한 token을 추측하려고 시도할 수 있다. 이 명세에 따르면 client의 요청에는 public client(공개 클라이언트)의 경우 유효한 client_id가, confidential client의 경우 유효한 client credentials가 포함되어야 한다. 철회하려는 token 역시 요청한 client의 소유여야 한다. 공격자가 public client의 client_id와 그 client의 token 하나, 또는 private client의 credentials와 그 client의 token 하나를 추측하는 데 성공한다면, token을 철회하는 것보다 다른 곳에서 사용함으로써 훨씬 더 큰 피해를 줄 수 있다. 공격자가 token을 철회하기로 선택하면 정상적인 client는 authorization grant를 잃고 사용자에게 다시 요청해야 한다. 더 이상의 피해는 발생하지 않으며, 추측해 낸 token은 이제 쓸모가 없어진다.

revocation endpoint는 security credentials를 처리하므로 client는 신뢰할 수 있는 출처에서만 그 위치를 얻어야 한다. 그렇지 않으면 공격자가 가짜 revocation endpoint를 이용하여 유효한 security token을 탈취할 수 있다. 또한 가짜 revocation endpoint를 탐지하기 위해 client는 revocation endpoint를 반드시 인증해야 한다(MUST)(인증서 검증 등).
