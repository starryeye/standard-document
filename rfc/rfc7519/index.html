초록

JSON Web Token (JWT)은 두 당사자 간에 전달할 Claim(클레임)을 간결하게 표현하는 URL-safe 형식입니다. JWT의 Claim은 JSON object로 인코딩되며, 이 object는 JSON Web Signature (JWS) 구조의 Payload 또는 JSON Web Encryption (JWE) 구조의 평문으로 사용됩니다. 이를 통해 Claim에 디지털 서명을 하거나 Message Authentication Code (MAC)로 무결성을 보호할 수 있으며, 암호화도 함께 또는 별도로 적용할 수 있습니다.

1. 소개

JSON Web Token (JWT)은 HTTP Authorization header나 URI query parameter처럼 공간이 제한된 환경에서 사용하도록 고안된 간결한 Claim 표현 형식입니다. JWT는 전송할 Claim을 JSON [RFC7159] object로 인코딩합니다. 이 object는 JSON Web Signature (JWS) [JWS] 구조의 Payload 또는 JSON Web Encryption (JWE) [JWE] 구조의 평문으로 사용됩니다. 이를 통해 Claim에 디지털 서명을 하거나 Message Authentication Code (MAC)로 무결성을 보호할 수 있으며, 암호화도 함께 또는 별도로 적용할 수 있습니다. JWT는 항상 JWS Compact Serialization 또는 JWE Compact Serialization으로 표현합니다.

JWT는 영어 단어 "jot"과 같이 발음하는 것을 권장합니다.

1.1. 표기 규칙

이 문서에서 사용하는 키워드 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", "OPTIONAL"은 "Key words for use in RFCs to Indicate Requirement Levels" [RFC2119]에서 설명한 대로 해석합니다. 이 해석은 해당 용어가 모두 대문자로 표기된 경우에만 적용합니다.

2. 용어

"JSON Web Encryption (JWE)", "Content Encryption Key(콘텐츠 암호화 키) (CEK)", "JWE Compact Serialization", "JWE Encrypted Key", "JWE Initialization Vector"는 JWE 명세 [JWE]에서 정의합니다.

이 명세에서는 다음 용어를 정의합니다.

JSON Web Token (JWT)
Claim 집합을 JSON 객체로 표현하고 그 객체를 JWS 또는 JWE로 인코딩한 문자열입니다. 이를 통해 Claim에 디지털 서명을 하거나 MAC을 적용할 수 있으며, 암호화도 별도로 또는 함께 적용할 수 있습니다.
JWT Claims Set(JWT 클레임 집합)
JWT가 전달하는 Claim을 담은 JSON 객체입니다.
Claim
어떤 대상에 관해 주장하는 개별 정보입니다. Claim은 Claim Name(클레임 이름)과 Claim Value(클레임 값)로 구성된 이름/값 쌍으로 표현합니다.
Claim Name
Claim 표현에서 이름에 해당하는 부분입니다. Claim Name은 항상 문자열입니다.
Claim Value
Claim 표현에서 값에 해당하는 부분입니다. Claim Value는 어떤 JSON 값이든 될 수 있습니다.
Nested JWT(중첩 JWT)
중첩 서명이나 중첩 암호화 또는 둘 다를 적용한 JWT입니다. Nested JWT에서 안쪽 JWT는 이를 감싸는 구조가 JWS이면 Payload 값으로, JWE이면 평문 값으로 사용됩니다.
Unsecured JWT(보호되지 않은 JWT)
Claim에 무결성 보호도 암호화도 적용되지 않은 JWT입니다.
Collision-Resistant Name(충돌 저항성이 있는 이름)
다른 이름과 충돌할 가능성이 매우 낮도록 이름을 할당할 수 있는 이름 공간에 속한 이름입니다. 충돌 저항성이 있는 이름 공간의 예로 Domain Names, ITU-T X.660 및 X.670 권고안 시리즈에서 정의하는 Object Identifiers (OIDs), Universally Unique IDentifiers (UUIDs) [RFC4122]가 있습니다. 관리 권한이 위임된 이름 공간을 사용할 때는 이름을 정의하는 사람이 그 이름을 정의하는 데 쓰는 이름 공간의 부분을 자신이 통제하고 있는지 확인하기 위해 합리적인 주의를 기울여야 합니다.
StringOrURI
JSON 문자열 값으로, 다음과 같은 추가 요건이 있습니다. 임의의 문자열 값을 사용할 수 있지만(MAY), 문자 ":"를 포함하는 값은 반드시 URI [RFC3986]여야 합니다(MUST). StringOrURI 값은 변환이나 정규화를 적용하지 않고 대소문자를 구분하는 문자열로 비교합니다.
NumericDate
윤초를 무시하고 1970-01-01T00:00:00Z UTC부터 지정된 UTC 날짜 및 시각까지의 초 수를 나타내는 JSON 숫자 값입니다. 정수가 아닌 값도 표현할 수 있다는 점을 빼면, 하루를 정확히 86400초로 계산하는 IEEE Std 1003.1, 2013 Edition [POSIX.1]의 "Seconds Since the Epoch" 정의와 같습니다. 날짜 및 시각 전반과 특히 UTC에 관한 자세한 내용은 RFC 3339 [RFC3339]를 참조하십시오.

3. JSON Web Token (JWT) 개요

JWT는 Claim 집합을 JSON 객체로 표현하고, 이 객체를 JWS 구조나 JWE 구조 또는 두 구조 모두에 인코딩합니다. 이 JSON 객체가 JWT Claims Set입니다. RFC 7159 [RFC7159]의 4절에 따라 JSON 객체는 0개 이상의 이름/값 쌍(또는 멤버)으로 구성되며, 이름은 문자열이고 값은 임의의 JSON 값입니다. 이 멤버들이 JWT가 표현하는 Claim입니다. RFC 7159 [RFC7159]의 2절에 따라 이 JSON 객체의 모든 JSON 값이나 구조 문자 앞뒤에는 공백이나 줄바꿈 또는 둘 다를 넣을 수 있습니다(MAY).

JWT Claims Set에 속한 멤버의 이름을 Claim Name이라고 합니다. 각 이름에 대응하는 값을 Claim Value라고 합니다.

JOSE Header의 내용은 JWT Claims Set에 적용한 암호 연산을 설명합니다. JOSE Header가 JWS의 것이면 JWT는 JWS로 표현되고, JWT Claims Set은 JWS Payload가 되며, Claim에는 디지털 서명 또는 MAC이 적용됩니다. JOSE Header가 JWE의 것이면 JWT는 JWE로 표현되고 Claim은 암호화되며, JWT Claims Set은 JWE가 암호화하는 평문이 됩니다. JWT를 또 다른 JWE나 JWS 구조로 감싸 Nested JWT를 만들 수 있으며, 이를 통해 중첩 서명과 암호화를 수행할 수 있습니다.

JWT는 마침표('.')로 구분한, URL에 안전하게 사용할 수 있는 부분들의 나열로 표현합니다. 각 부분은 base64url로 인코딩된 값을 담습니다. JWT를 구성하는 부분의 수는 결과 JWS를 JWS Compact Serialization으로 표현하는지, 결과 JWE를 JWE Compact Serialization으로 표현하는지에 따라 달라집니다.

3.1. JWT 예시

다음 JOSE Header 예시는 인코딩된 객체가 JWT이고, 이 JWT가 HMAC SHA-256 알고리즘으로 MAC을 적용한 JWS임을 선언합니다.

     {"typ":"JWT",
      "alg":"HS256"}

위 JSON 객체의 표현에 생길 수 있는 모호함을 없애기 위해, 이 예시에서 위 JOSE Header를 실제로 표현하는 데 사용한 UTF-8 옥텟 시퀀스도 아래에 제시합니다. (플랫폼마다 줄바꿈을 표현하는 방식이 다르거나(CRLF와 LF), 줄 앞뒤의 공백이 다르거나, 마지막 줄 끝에 줄바꿈이 있거나 없는 등 여러 이유로 모호함이 생길 수 있습니다. 이 예시의 표현에서는 첫째 줄의 앞뒤에 공백이 없고, 첫째 줄과 둘째 줄 사이에 CRLF 줄바꿈(13, 10)이 있으며, 둘째 줄 앞에는 공백(32)이 하나 있고 뒤에는 공백이 없으며, 마지막 줄 끝에는 줄바꿈이 없습니다.) 이 예시의 JOSE Header를 UTF-8로 표현한 옥텟은 다음과 같습니다(JSON 배열 표기법 사용).

   [123, 34, 116, 121, 112, 34, 58, 34, 74, 87, 84, 34, 44, 13, 10, 32,
   34, 97, 108, 103, 34, 58, 34, 72, 83, 50, 53, 54, 34, 125]

JOSE Header의 UTF-8 표현을 이루는 옥텟을 base64url로 인코딩하면 다음과 같은 인코딩된 JOSE Header 값을 얻습니다.

     eyJ0eXAiOiJKV1QiLA0KICJhbGciOiJIUzI1NiJ9

다음은 JWT Claims Set의 예시입니다.

     {"iss":"joe",
      "exp":1300819380,
      "http://example.com/is_root":true}

다음 옥텟 시퀀스는 이 예시에서 위 JWT Claims Set을 나타내는 데 사용한 UTF-8 표현이며, 이것이 JWS Payload입니다.

   [123, 34, 105, 115, 115, 34, 58, 34, 106, 111, 101, 34, 44, 13, 10,
   32, 34, 101, 120, 112, 34, 58, 49, 51, 48, 48, 56, 49, 57, 51, 56,
   48, 44, 13, 10, 32, 34, 104, 116, 116, 112, 58, 47, 47, 101, 120, 97,
   109, 112, 108, 101, 46, 99, 111, 109, 47, 105, 115, 95, 114, 111,
   111, 116, 34, 58, 116, 114, 117, 101, 125]

JWS Payload를 base64url로 인코딩하면 다음과 같은 인코딩된 JWS Payload를 얻습니다(줄바꿈은 표시용입니다).

     eyJpc3MiOiJqb2UiLA0KICJleHAiOjEzMDA4MTkzODAsDQogImh0dHA6Ly
     9leGFtcGxlLmNvbS9pc19yb290Ijp0cnVlfQ

HMAC SHA-256 알고리즘을 사용해 인코딩된 JOSE Header와 인코딩된 JWS Payload의 MAC을 계산하고, [JWS]에 명시된 방식으로 HMAC 값을 base64url로 인코딩하면 다음과 같은 인코딩된 JWS Signature를 얻습니다.

     dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

인코딩된 각 부분을 이 순서대로, 사이에 마침표('.')를 넣어 연결하면 다음과 같은 완전한 JWT를 얻습니다(줄바꿈은 표시용입니다).

     eyJ0eXAiOiJKV1QiLA0KICJhbGciOiJIUzI1NiJ9
     .
     eyJpc3MiOiJqb2UiLA0KICJleHAiOjEzMDA4MTkzODAsDQogImh0dHA6Ly9leGFt
     cGxlLmNvbS9pc19yb290Ijp0cnVlfQ
     .
     dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

이 계산 과정은 [JWS]의 부록 A.1에 더 자세히 나와 있습니다. 암호화된 JWT의 예시는 이 문서의 부록 A.1을 참조하십시오.

4. JWT Claim

JWT Claims Set은 JWT가 전달하는 Claim을 멤버로 갖는 JSON 객체를 나타냅니다. 하나의 JWT Claims Set에 속한 Claim Name은 각각 고유해야 합니다(MUST). JWT 파서는 Claim Name이 중복된 JWT를 거부하거나, ECMAScript 5.1 [ECMAScript]의 15.12절("The JSON Object")에 명시된 대로 이름이 중복된 멤버 중 원문에 마지막으로 나타난 것만 반환하는 JSON 파서를 사용해야 합니다(MUST).

JWT가 유효한 것으로 간주되려면 어떤 Claim을 포함해야 하는지는 사용 맥락에 따라 다르며, 이 명세의 범위를 벗어납니다. JWT를 활용하는 구체적인 애플리케이션에서는 구현체가 일부 Claim을 정해진 방식으로 해석하고 처리하도록 요구합니다. 그러나 그런 요구사항이 없다면 구현체가 이해하지 못하는 Claim은 모두 무시해야 합니다(MUST).

JWT Claim Name은 Registered Claim Names, Public Claim Names, Private Claim Names의 세 종류로 나뉩니다.

4.1. Registered Claim Names

다음 Claim Name은 10.1절에서 신설하는 IANA의 "JSON Web Token Claims" 레지스트리에 등록되어 있습니다. 아래에서 정의하는 Claim은 어느 것도 모든 경우에 사용하거나 구현하도록 의무화하려는 것이 아니며, 유용하고 상호 운용 가능한 Claim 집합을 마련하기 위한 출발점을 제공합니다. JWT를 사용하는 애플리케이션은 구체적으로 어떤 Claim을 사용하고 언제 필수 또는 선택 사항으로 취급하는지 정의하는 것이 좋습니다. JWT의 핵심 목표 중 하나가 간결한 표현이므로 모든 이름은 짧습니다.

4.1.1. "iss" (Issuer) Claim

"iss"(발급자) Claim은 JWT를 발급한 주체를 식별합니다. 이 Claim의 처리 방식은 일반적으로 애플리케이션에 따라 다릅니다. "iss" 값은 StringOrURI 값을 담은 대소문자 구분 문자열입니다. 이 Claim의 사용은 선택 사항입니다(OPTIONAL).

4.1.2. "sub" (Subject) Claim

"sub"(대상 주체) Claim은 JWT가 대상으로 삼는 주체를 식별합니다. JWT의 Claim은 보통 그 주체에 관한 진술입니다. 대상 주체의 값은 발급자의 범위 내에서 고유하도록 범위를 정하거나 전역적으로 고유해야 합니다(MUST). 이 Claim의 처리 방식은 일반적으로 애플리케이션에 따라 다릅니다. "sub" 값은 StringOrURI 값을 담은 대소문자 구분 문자열입니다. 이 Claim의 사용은 선택 사항입니다(OPTIONAL).

4.1.3. "aud" (Audience) Claim

"aud"(수신 대상) Claim은 JWT를 받도록 지정된 수신자를 식별합니다. JWT를 처리하도록 지정된 각 주체는 수신 대상 Claim에 있는 값으로 자신을 식별해야 합니다(MUST). 이 Claim이 있는데도 이를 처리하는 주체가 "aud" Claim에 있는 값으로 자신을 식별하지 못하면 JWT를 거부해야 합니다(MUST). 일반적으로 "aud" 값은 대소문자를 구분하는 문자열의 배열이며, 각 문자열은 StringOrURI 값을 담습니다. JWT의 수신 대상이 하나뿐인 경우에는 예외적으로 "aud" 값이 StringOrURI 값을 담은 단일 대소문자 구분 문자열일 수 있습니다(MAY). 수신 대상 값의 해석은 일반적으로 애플리케이션에 따라 다릅니다. 이 Claim의 사용은 선택 사항입니다(OPTIONAL).

4.1.4. "exp" (Expiration Time) Claim

"exp"(만료 시각) Claim은 JWT의 만료 시각을 지정합니다. 해당 시각부터는 JWT를 처리 대상으로 받아들여서는 안 됩니다(MUST NOT). "exp" Claim을 처리할 때 현재 날짜 및 시각은 이 Claim에 명시된 만료 날짜 및 시각보다 빨라야 합니다(MUST). 구현자는 시계 간 시간 차이를 고려해 보통 몇 분을 넘지 않는 작은 허용 오차를 둘 수 있습니다(MAY). 이 Claim의 값은 NumericDate 값을 담은 숫자여야 합니다(MUST). 이 Claim의 사용은 선택 사항입니다(OPTIONAL).

4.1.5. "nbf" (Not Before) Claim

"nbf"(처리 개시 시각) Claim은 그 전에는 JWT를 처리 대상으로 받아들여서는 안 되는 시각을 지정합니다(MUST NOT). "nbf" Claim을 처리할 때 현재 날짜 및 시각은 이 Claim에 명시된 개시 날짜 및 시각과 같거나 그보다 늦어야 합니다(MUST). 구현자는 시계 간 시간 차이를 고려해 보통 몇 분을 넘지 않는 작은 허용 오차를 둘 수 있습니다(MAY). 이 Claim의 값은 NumericDate 값을 담은 숫자여야 합니다(MUST). 이 Claim의 사용은 선택 사항입니다(OPTIONAL).

4.1.6. "iat" (Issued At) Claim

"iat"(발급 시각) Claim은 JWT가 발급된 시각을 지정합니다. 이 Claim을 사용하면 JWT가 발급된 뒤 얼마나 시간이 지났는지 확인할 수 있습니다. 이 Claim의 값은 NumericDate 값을 담은 숫자여야 합니다(MUST). 이 Claim의 사용은 선택 사항입니다(OPTIONAL).

4.1.7. "jti" (JWT ID) Claim

"jti"(JWT ID) Claim은 JWT의 고유 식별자를 제공합니다. 동일한 값이 다른 데이터 객체에 우연히 할당될 확률이 무시할 수 있을 정도로 낮도록 이 식별자 값을 할당해야 합니다(MUST). 애플리케이션이 여러 발급자를 사용하는 경우에는 서로 다른 발급자가 생성한 값 사이의 충돌도 방지해야 합니다(MUST). "jti" Claim은 JWT의 재전송 공격을 방지하는 데 사용할 수 있습니다. "jti" 값은 대소문자를 구분하는 문자열입니다. 이 Claim의 사용은 선택 사항입니다(OPTIONAL).

4.2. Public Claim Names

JWT 사용자는 Claim Name을 자유롭게 정의할 수 있습니다. 다만 충돌을 방지하려면 새 Claim Name은 10.1절에서 신설하는 IANA "JSON Web Token Claims" 레지스트리에 등록하거나, Collision-Resistant Name을 포함하는 값인 Public Name으로 정하는 것이 좋습니다. 어느 경우든 이름이나 값을 정의하는 주체는 Claim Name 정의에 사용하는 이름 공간의 해당 부분을 자신이 관리하도록 합리적인 예방 조치를 취할 필요가 있습니다.

4.3. Private Claim Names

JWT의 생성자와 소비자는 Registered Claim Names(4.1절)도 Public Claim Names(4.2절)도 아닌 Private Name을 Claim Name으로 사용하기로 합의할 수 있습니다(MAY). Public Claim Names와 달리 Private Claim Names는 충돌할 수 있으므로 주의해서 사용하는 것이 좋습니다.

5. JOSE Header

JWT 객체에서 JOSE Header가 나타내는 JSON 객체의 멤버는 JWT에 적용된 암호 연산을 설명하며, 선택적으로 JWT의 추가 속성도 설명합니다. JWT가 JWS인지 JWE인지에 따라 JOSE Header 값에 해당 규칙이 적용됩니다.

이 명세는 JWT가 JWS인 경우와 JWE인 경우 모두에 대해 다음 Header Parameters의 사용법을 추가로 규정합니다.

5.1. "typ"(Type) Header Parameter

[JWS]와 [JWE]가 정의하는 "typ"(type) Header Parameter는 JWT 애플리케이션이 이 JWT 전체의 미디어 타입[IANA.MediaTypes]을 선언하는 데 사용합니다. JWT 객체를 담을 수 있는 애플리케이션 데이터 구조에 JWT가 아닌 값도 들어갈 수 있을 때 사용하도록 마련된 것으로, 애플리케이션은 이 값으로 그 구조에 들어갈 수 있는 여러 종류의 객체를 구분할 수 있습니다. 해당 객체가 JWT라는 사실을 이미 아는 경우에는 일반적으로 애플리케이션에서 이 값을 사용하지 않습니다. JWT 구현은 이 매개변수를 무시하며, 이 매개변수에 대한 처리는 모두 JWT 애플리케이션에서 수행합니다. 이 매개변수가 있으면 해당 객체가 JWT임을 나타내기 위해 그 값을 "JWT"로 하는 것이 권장됩니다(RECOMMENDED). 미디어 타입의 이름은 대소문자를 구분하지 않지만, 기존 구현과의 호환성을 위해 "JWT"는 항상 대문자로 표기하는 것이 권장됩니다(RECOMMENDED). 이 Header Parameter의 사용은 선택 사항입니다(OPTIONAL).

5.2. "cty"(Content Type) Header Parameter

이 명세에서는 [JWS]와 [JWE]가 정의하는 "cty"(content type) Header Parameter로 JWT의 구조 정보를 전달합니다.

중첩 서명 또는 암호화 연산을 사용하지 않는 일반적인 경우에는 이 Header Parameter를 사용하지 않는 것이 권장됩니다(NOT RECOMMENDED). 중첩 서명 또는 암호화를 사용한다면 이 Header Parameter가 있어야 합니다(MUST). 이 경우 이 JWT가 Nested JWT를 담고 있음을 나타내도록 값은 "JWT"여야 합니다(MUST). 미디어 타입의 이름은 대소문자를 구분하지 않지만, 기존 구현과의 호환성을 위해 "JWT"는 항상 대문자로 표기하는 것이 권장됩니다(RECOMMENDED). Nested JWT의 예는 부록 A.2를 참조하십시오.

5.3. Claim을 Header Parameter로 복제하기

암호화된 JWT를 사용하는 일부 애플리케이션에서는 일부 Claim을 암호화하지 않은 형태로도 제공하면 유용합니다. 예를 들어 JWT를 복호화하기 전에 이를 처리할지, 처리한다면 어떻게 할지 결정하는 애플리케이션 처리 규칙에 이 표현을 사용할 수 있습니다.

이 명세에서는 애플리케이션의 필요에 따라 JWT Claims Set의 Claim을 JWE 형식인 JWT의 Header Parameter로 복제할 수 있도록 허용합니다. 이처럼 복제된 Claim이 있는 경우, 이를 수신하는 애플리케이션은 해당 Claim에 대해 별도의 구체적인 처리 규칙을 정의하지 않는 한 원본과 복제본의 값이 같은지 확인하는 것이 권장됩니다(SHOULD). 암호화하지 않고 전송해도 안전한 Claim만 JWT의 Header Parameter 값으로 복제되도록 할 책임은 애플리케이션에 있습니다.

이 명세의 10.4.1절에서는 암호화된 JWT에서 Claim의 비암호화 복제본이 필요한 애플리케이션에 이를 제공하기 위해 "iss"(issuer), "sub"(subject), "aud"(audience)를 Header Parameter 이름으로 등록합니다. 다른 명세에서도 필요에 따라 등록된 다른 Claim Name을 같은 방식으로 Header Parameter 이름으로 등록할 수 있습니다(MAY).

6. Unsecured JWT

JWT에 포함된 서명이나 암호화 또는 둘 모두가 아닌 다른 수단(예: 해당 JWT를 담는 데이터 구조에 적용한 서명)으로 JWT 콘텐츠를 보호하는 사용 사례를 지원하기 위해, 서명이나 암호화 없이 JWT를 생성할 수도 있습니다(MAY). JWA 명세[JWA]에서 정의한 대로, Unsecured JWT는 "alg" Header Parameter 값으로 "none"을 사용하고 JWS Signature 값으로 빈 문자열을 사용하는 JWS입니다. 즉, JWT Claims Set을 JWS Payload로 사용하는 Unsecured JWS입니다.

6.1. Unsecured JWT 예시

다음 JOSE Header 예시는 인코딩된 객체가 Unsecured JWT임을 선언합니다.

     {"alg":"none"}

JOSE Header의 UTF-8 표현을 구성하는 옥텟을 Base64url로 인코딩하면 다음과 같은 인코딩된 JOSE Header 값을 얻습니다.

     eyJhbGciOiJub25lIn0

다음은 JWT Claims Set의 예시입니다.

     {"iss":"joe",
      "exp":1300819380,
      "http://example.com/is_root":true}

JWT Claims Set의 UTF-8 표현을 구성하는 옥텟을 Base64url로 인코딩하면 다음과 같은 인코딩된 JWS Payload를 얻습니다(줄바꿈은 표시를 위한 것일 뿐입니다).

     eyJpc3MiOiJqb2UiLA0KICJleHAiOjEzMDA4MTkzODAsDQogImh0dHA6Ly9leGFt
     cGxlLmNvbS9pc19yb290Ijp0cnVlfQ

인코딩된 JWS Signature는 빈 문자열입니다.

이렇게 인코딩된 각 부분을 나열된 순서대로 사이에 마침표('.')를 넣어 연결하면 다음과 같은 완전한 JWT를 얻습니다(줄바꿈은 표시를 위한 것일 뿐입니다).

     eyJhbGciOiJub25lIn0
     .
     eyJpc3MiOiJqb2UiLA0KICJleHAiOjEzMDA4MTkzODAsDQogImh0dHA6Ly9leGFt
     cGxlLmNvbS9pc19yb290Ijp0cnVlfQ
     .

7. JWT 생성 및 검증

7.1. JWT 생성

JWT를 생성하려면 다음 단계를 수행합니다. 단계의 입력과 출력 사이에 의존 관계가 없다면 단계 순서는 중요하지 않습니다.

1. 원하는 Claim이 포함된 JWT Claims Set을 생성합니다. 이 표현에는 공백이 명시적으로 허용되며 인코딩 전에 정규형으로 변환할 필요가 없습니다.
2. JWT Claims Set의 UTF-8 표현을 구성하는 옥텟을 Message로 삼습니다.
3. 원하는 Header Parameters가 포함된 JOSE Header를 생성합니다. JWT는 [JWS] 또는 [JWE] 명세를 준수해야 합니다(MUST). 이 표현에는 공백이 명시적으로 허용되며 인코딩 전에 정규형으로 변환할 필요가 없습니다.
4. JWT가 JWS인지 JWE인지에 따라 다음 두 경우로 나뉩니다.
* JWT가 JWS이면 Message를 JWS Payload로 사용하여 JWS를 생성합니다. JWS 생성에 대해 [JWS]에 명시된 모든 단계를 따라야 합니다(MUST).
* 그렇지 않고 JWT가 JWE이면 Message를 JWE의 평문으로 사용하여 JWE를 생성합니다. JWE 생성에 대해 [JWE]에 명시된 모든 단계를 따라야 합니다(MUST).
5. 중첩 서명 또는 암호화 연산을 수행할 예정이라면 JWS 또는 JWE를 Message로 삼고 3단계로 돌아갑니다. 그 단계에서 새로 만드는 JOSE Header의 "cty"(content type) 값은 "JWT"로 설정합니다.
6. 그렇지 않으면 JWS 또는 JWE를 최종 JWT로 삼습니다.

7.2. JWT 검증

JWT를 검증할 때는 다음 단계를 수행합니다. 단계의 입력과 출력 사이에 의존 관계가 없다면 단계 순서는 중요하지 않습니다. 나열된 단계 중 하나라도 실패하면 JWT를 거부해야 합니다(MUST). 즉, 애플리케이션은 이를 유효하지 않은 입력으로 취급해야 합니다.

1. JWT에 마침표('.')가 하나 이상 있는지 확인합니다.
2. JWT에서 첫 번째 마침표('.') 앞의 부분을 Encoded JOSE Header로 삼습니다.
3. 줄바꿈, 공백 또는 기타 추가 문자가 사용되지 않아야 한다는 제약을 지켜 Encoded JOSE Header를 Base64url로 디코딩합니다.
4. 결과 옥텟 시퀀스가 RFC 7159 [RFC7159]를 준수하는 완전히 유효한 JSON 객체를 UTF-8로 인코딩한 표현인지 확인합니다. 이 JSON 객체를 JOSE Header로 삼습니다.
5. 결과 JOSE Header에 포함된 매개변수와 값이 모두 구문과 의미가 해석 가능하고 지원되는 것이거나, 해석할 수 없을 때 무시하도록 명시된 것인지 확인합니다.
6. [JWE]의 9절에서 설명하는 방법 중 하나를 사용하여 JWT가 JWS인지 JWE인지 판단합니다.
7. JWT가 JWS인지 JWE인지에 따라 다음 두 경우로 나뉩니다.
* JWT가 JWS이면 [JWS]에 명시된 JWS 검증 단계를 따릅니다. JWS Payload를 base64url로 디코딩한 결과를 Message로 삼습니다.
* 그렇지 않고 JWT가 JWE이면 [JWE]에 명시된 JWE 검증 단계를 따릅니다. 그 결과로 얻은 평문을 Message로 삼습니다.
8. JOSE Header에 "JWT"라는 "cty"(content type) 값이 들어 있으면 Message는 중첩 서명 또는 암호화 연산이 적용된 JWT입니다. 이 경우 Message를 JWT로 사용하여 1단계로 돌아갑니다.
9. 그렇지 않으면 줄바꿈, 공백 또는 기타 추가 문자가 사용되지 않아야 한다는 제약을 지켜 Message를 base64url로 디코딩합니다.
10. 결과 옥텟 시퀀스가 RFC 7159 [RFC7159]를 준수하는 완전히 유효한 JSON 객체를 UTF-8로 인코딩한 표현인지 확인합니다. 이 JSON 객체를 JWT Claims Set으로 삼습니다.

마지막으로, 주어진 맥락에서 어떤 알고리즘을 사용할 수 있는지는 애플리케이션이 결정한다는 점에 유의하십시오. JWT 검증에 성공하더라도 JWT에 사용된 알고리즘을 애플리케이션이 허용하지 않는다면, 애플리케이션은 해당 JWT를 거부하는 것이 권장됩니다(SHOULD).

7.3. 문자열 비교 규칙

JWT를 처리하려면 알려진 문자열을 JSON 객체의 멤버 및 값과 비교해야 합니다. 예를 들어 어떤 알고리즘이 사용되었는지 확인할 때는 "alg"를 인코딩한 Unicode [UNICODE] 문자열을 JOSE Header의 멤버 이름과 비교하여 일치하는 Header Parameter 이름이 있는지 확인합니다.

멤버 이름을 비교하는 JSON 규칙은 RFC 7159 [RFC7159]의 8.3절에 설명되어 있습니다. 문자열 비교 연산으로는 같은지 다른지만 판정하므로, 멤버 이름이나 멤버 값을 알려진 문자열과 비교하는 데 같은 규칙을 사용할 수 있습니다.

멤버 정의에서 해당 멤버 값에 다른 비교 규칙을 사용하라고 명시한 경우를 제외하고는 모든 JSON 문자열 비교에 이 비교 규칙을 사용해야 합니다(MUST). 이 명세에서는 "typ"와 "cty"의 멤버 값에만 이 비교 규칙을 적용하지 않습니다.

일부 애플리케이션은 대소문자를 구분하는 값에 대소문자를 구분하지 않는 정보를 포함할 수 있습니다. 예를 들어 "iss"(발급자) Claim Value에 DNS 이름을 포함할 수 있습니다. 이런 경우 여러 당사자가 비교를 위해 동일한 값을 생성해야 할 수 있다면, 애플리케이션은 대소문자를 구분하지 않는 부분을 소문자로 표기하는 등 해당 부분의 표준 대소문자 표기 규칙을 정해야 할 수 있습니다. (하지만 다른 모든 당사자가 생성 당사자가 내보낸 값을 독립적으로 생성한 값과 비교하지 않고 그대로 사용한다면, 생성자가 사용한 대소문자는 중요하지 않습니다.)

8. 구현 요구 사항

이 절은 이 명세의 알고리즘과 기능 중 반드시 구현해야 하는 것을 정의합니다. 이 명세를 사용하는 애플리케이션은 자신이 사용하는 구현에 추가 요구 사항을 부과할 수 있습니다. 예를 들어 어떤 애플리케이션은 암호화된 JWT와 Nested JWT에 대한 지원을 요구하고, 다른 애플리케이션은 P-256 곡선과 SHA-256 해시 알고리즘을 사용하는 Elliptic Curve Digital Signature Algorithm(ECDSA)으로 JWT에 서명하는 기능("ES256")을 요구할 수 있습니다.

이 명세를 준수하는 JWT 구현은 JSON Web Algorithms [JWA]에 명시된 서명 및 MAC 알고리즘 중 HMAC SHA-256("HS256")과 "none"만을 필수로 구현해야 합니다(MUST). 또한 구현은 SHA-256 해시 알고리즘을 사용하는 RSASSA-PKCS1-v1_5("RS256")와 P-256 곡선 및 SHA-256 해시 알고리즘을 사용하는 ECDSA("ES256")도 지원하는 것이 권장됩니다(RECOMMENDED). 다른 알고리즘과 키 크기의 지원은 선택 사항입니다(OPTIONAL).

암호화된 JWT의 지원은 선택 사항입니다(OPTIONAL). 구현이 암호화 기능을 제공한다면, 이 명세를 준수하는 구현은 [JWA]에 명시된 암호화 알고리즘 중 2048비트 키를 사용하는 RSAES-PKCS1-v1_5("RSA1_5"), 128비트 및 256비트 키를 사용하는 AES Key Wrap("A128KW" 및 "A256KW"), 그리고 AES-CBC와 HMAC SHA-2를 사용하는 복합 인증 암호화 알고리즘("A128CBC-HS256" 및 "A256CBC-HS512")만을 필수로 구현해야 합니다(MUST). 또한 Content Encryption Key를 래핑할 키를 Elliptic Curve Diffie-Hellman Ephemeral Static(ECDH-ES)으로 합의하는 기능("ECDH-ES+A128KW" 및 "ECDH-ES+A256KW")과 128비트 및 256비트 키로 Galois/Counter Mode(GCM)에서 AES를 사용하는 기능("A128GCM" 및 "A256GCM")도 지원하는 것이 권장됩니다(RECOMMENDED). 다른 알고리즘과 키 크기의 지원은 선택 사항입니다(OPTIONAL).

Nested JWT의 지원은 선택 사항입니다(OPTIONAL).

9. 콘텐츠가 JWT임을 나타내는 URI

이 명세는 예를 들어 미디어 타입 대신 URI로 콘텐츠의 유형을 나타내는 애플리케이션이 해당 콘텐츠가 JWT임을 표시할 수 있도록 URN "urn:ietf:params:oauth:token-type:jwt"를 등록합니다.

10. IANA 고려 사항

10.1. JSON Web Token Claims 레지스트리

이 절에서는 JWT의 Claim Name을 위한 IANA "JSON Web Token Claims" 레지스트리를 신설합니다. 이 레지스트리에는 Claim Name과 이를 정의하는 명세에 대한 참조를 기록합니다. 이 절에서는 4.1절에서 정의한 Claim Name을 등록합니다.

값은 jwt-reg-review@ietf.org 메일링 리스트에서 세 주 동안 검토한 후, 한 명 이상의 Designated Expert의 의견에 따라 Specification Required [RFC5226] 정책으로 등록합니다. 다만 명세를 발행하기 전에 값을 할당할 수 있도록, Designated Expert는 해당 명세가 발행될 것이라고 판단하면 등록을 승인할 수 있습니다.

검토를 위해 메일링 리스트로 보내는 등록 요청에는 적절한 제목(예: "Request to register claim: example")을 사용하는 것이 좋습니다.

Designated Expert는 검토 기간 내에 등록 요청을 승인하거나 거부하고 그 결정을 검토 메일링 리스트와 IANA에 알립니다. 거부할 때는 이유를 설명하고, 해당하는 경우 요청이 승인되려면 어떻게 해야 하는지 제안하는 것이 좋습니다. 21일을 초과하여 결정되지 않은 등록 요청은 iesg@ietf.org 메일링 리스트를 통해 IESG에 회부하여 해결을 요청할 수 있습니다.

Designated Expert가 적용할 검토 기준에는 등록 제안이 기존 기능과 중복되는지, 일반적으로 적용될 가능성이 있는지 아니면 단일 애플리케이션에만 유용한지, 등록 설명이 명확한지 등이 포함됩니다.

IANA는 Designated Expert가 제출한 레지스트리 업데이트만 받아들여야 하며, 모든 등록 요청은 검토 메일링 리스트로 안내하는 것이 좋습니다.

등록 여부를 폭넓은 관점에서 검토할 수 있도록, 이 명세를 사용하는 여러 애플리케이션의 관점을 대변할 수 있는 Designated Expert를 여러 명 임명하는 것이 좋습니다. 등록 결정이 특정 전문가에게 이해 충돌을 일으킨다고 여겨질 수 있는 경우, 그 전문가는 결정을 다른 전문가들의 판단에 맡기는 것이 좋습니다.

10.1.1. 등록 양식

Claim Name: 요청하는 이름입니다(예: "iss"). 이 명세의 핵심 목표 중 하나는 결과 표현을 간결하게 유지하는 것이므로, 이름은 짧게, 즉 충분히 설득력 있는 사유가 없다면 8자를 넘지 않게 정하는 것이 권장됩니다(RECOMMENDED). 이 이름은 대소문자를 구분합니다. Designated Expert가 예외를 허용할 만한 충분히 설득력 있는 사유가 있다고 밝히지 않는 한, 대소문자를 무시해 비교했을 때 다른 등록 이름과 일치하는 이름을 사용할 수 없습니다.

Claim 설명: Claim에 대한 간단한 설명입니다(예: "Issuer").

변경 관리자: Standards Track RFC의 경우 "IESG"를 기재합니다. 그 외의 경우에는 담당자의 이름을 기재합니다. 우편 주소, 이메일 주소, 홈페이지 URI 등 다른 정보도 포함할 수 있습니다.

명세 문서: 해당 매개변수를 명시하는 문서에 대한 참조입니다. 문서 사본을 가져올 수 있는 URI를 포함하는 것이 바람직합니다. 관련 절도 명시할 수 있지만 필수는 아닙니다.

11. 보안 고려 사항

JWT/JWS/JWE/JWK 에이전트는 암호 기술을 사용하는 애플리케이션에 관련된 모든 보안 문제를 다루어야 합니다. 여기에는 사용자의 비대칭 개인 키 및 대칭 비밀 키를 보호하는 일과 여러 공격에 대한 대응책을 적용하는 일이 포함됩니다.

JWS 명세의 모든 보안 고려 사항은 JWT에도 적용되며, 암호화를 사용하는 경우에는 JWE의 보안 고려 사항도 적용됩니다. 특히 [JWS]의 10.12절("JSON Security Considerations")과 10.13절("Unicode Comparison Security Considerations")은 JOSE Header에 적용되는 것과 동일한 방식으로 JWT Claims Set에도 적용됩니다.

11.1. 신뢰 판단

JWT의 내용이 암호학적으로 보호되고 신뢰 판단에 필요한 맥락과 결합된 경우에만, 신뢰 여부를 판단할 때 그 내용에 의존할 수 있습니다. 특히 JWT의 서명이나 암호화 또는 둘 다에 사용한 키는 일반적으로 JWT 발급자로 식별된 당사자가 관리한다는 사실을 검증할 수 있어야 합니다.

11.2. 서명과 암호화 순서

구문상 Nested JWT의 서명과 암호화 연산은 어느 순서로든 적용할 수 있지만, 둘 다 필요한 경우 생성자는 먼저 메시지에 서명한 다음 그 결과를 암호화하는 것이 일반적입니다(이렇게 하면 서명도 암호화됩니다). 이 방식은 서명을 제거해 암호화된 메시지만 남기는 공격을 막고, 서명자의 프라이버시도 보호합니다. 또한 많은 관할권에서는 암호문에 대한 서명을 유효한 것으로 인정하지 않습니다.

서명과 암호화의 순서에서 비롯될 수 있는 보안 문제는 기반이 되는 JWS 및 JWE 명세에서 이미 다룬다는 점에 유의해야 합니다. 특히 JWE는 인증 암호화 알고리즘만 지원하므로, 여러 맥락에서 암호화 후 서명이 필요할 수 있다는 암호학적 우려는 이 명세에 해당하지 않습니다.

12. 개인정보 보호 고려 사항

JWT에는 개인정보 보호상 민감한 정보가 포함될 수 있습니다. 이 경우 해당 정보가 의도하지 않은 당사자에게 공개되지 않도록 조치를 취해야 합니다(MUST). 한 가지 방법은 암호화된 JWT를 사용하고 수신자를 인증하는 것입니다. 다른 방법은 암호화되지 않은 민감 정보가 담긴 JWT를 Transport Layer Security(TLS)처럼 암호화를 사용하고 엔드포인트 인증을 지원하는 프로토콜로만 전송하는 것입니다. 개인정보 보호 문제를 최소화하는 가장 간단한 방법은 JWT에 이러한 민감 정보를 넣지 않는 것입니다.

A.2. Nested JWT 예시

이 예시는 JWT를 JWE 또는 JWS의 페이로드로 사용해 Nested JWT를 만드는 방법을 보여 줍니다. 여기서는 JWT Claims Set에 먼저 서명한 뒤 암호화합니다.

내부의 서명된 JWT는 [JWS] 부록 A.2의 예시와 동일합니다. 따라서 그 계산 과정은 여기서 반복하지 않습니다. 이 예시에서는 이어서 RSAES-PKCS1-v1_5 및 AES_128_CBC_HMAC_SHA_256을 사용해 내부 JWT를 수신자용으로 암호화합니다.

다음 예시의 JOSE Header는 아래 사항을 명시합니다.

o RSAES-PKCS1-v1_5 알고리즘으로 Content Encryption Key를 수신자용으로 암호화하여 JWE Encrypted Key를 생성합니다.

o AES_128_CBC_HMAC_SHA_256 알고리즘으로 평문에 인증 암호화를 적용하여 JWE Ciphertext와 JWE Authentication Tag를 생성합니다.

o 평문 자체가 JWT입니다.

     {"alg":"RSA1_5","enc":"A128CBC-HS256","cty":"JWT"}

JOSE Header를 UTF-8로 표현한 옥텟을 Base64url로 인코딩하면 다음과 같은 인코딩된 JOSE Header 값을 얻습니다.

     eyJhbGciOiJSU0ExXzUiLCJlbmMiOiJBMTI4Q0JDLUhTMjU2IiwiY3R5IjoiSldUIn0

부록 B. JWT와 SAML Assertion의 관계

Security Assertion Markup Language(SAML) 2.0 [OASIS.saml-core-2.0-os]은 JWT가 지원하는 것보다 표현력이 높고 보안 옵션이 더 많은 보안 토큰을 만들기 위한 표준을 제공합니다. 다만 이러한 유연성과 표현력을 얻는 대가로 크기와 복잡성이 모두 증가합니다. SAML이 XML [W3C.CR-xml11-20060816]과 XML Digital Signature(DSIG) [RFC3275]를 사용한다는 점은 SAML Assertion의 크기를 늘리는 요인입니다. 또한 XML, 특히 XML Canonicalization [W3C.REC-xml-c14n-20010315]을 사용한다는 점은 SAML Assertion의 복잡성을 높이는 요인입니다.

JWT는 HTTP 헤더와 URI의 쿼리 인수에 들어갈 만큼 작고 단순한 보안 토큰 형식을 제공하는 것을 목표로 합니다. 이를 위해 SAML보다 훨씬 단순한 토큰 모델을 지원하고 JSON [RFC7159] 객체 인코딩 구문을 사용합니다. 또한 XML DSIG보다 작고 유연성은 낮은 형식으로 Message Authentication Code(MAC)와 디지털 서명을 사용해 토큰을 보호할 수 있습니다.

따라서 JWT는 SAML Assertion이 하는 일의 일부를 수행할 수 있지만, SAML Assertion을 완전히 대체하기 위한 것은 아닙니다. 구현의 용이성이나 작은 크기가 중요할 때 쓰는 토큰 형식입니다.

SAML Assertion은 언제나 어떤 엔터티가 특정 주체에 대해 내놓는 진술입니다. JWT도 흔히 같은 방식으로 사용되며, 진술하는 엔터티는 "iss"(issuer) Claim으로, 그 주체는 "sub"(subject) Claim으로 나타냅니다. 다만 이 Claim들은 선택 사항이므로 JWT 형식을 다른 용도로 사용하는 것도 허용됩니다.

부록 C. JWT와 Simple Web Token(SWT)의 관계

JWT와 SWT [SWT]는 본질적으로 모두 애플리케이션 간에 Claim의 집합을 전달할 수 있게 합니다. SWT에서는 Claim Name과 Claim Value가 모두 문자열입니다. JWT에서는 Claim Name이 문자열이지만 Claim Value는 모든 JSON 타입이 될 수 있습니다. 두 토큰 형식 모두 내용에 암호학적 보호를 제공합니다. SWT는 HMAC SHA-256을 사용하고 JWT는 서명, MAC, 암호화 알고리즘을 포함한 여러 알고리즘 중에서 선택할 수 있습니다.

감사의 말

저자들은 JWT를 설계할 때 SWT [SWT]의 설계와 단순성, 그리고 Dick Hardt가 OpenID 커뮤니티에서 논의한 JSON 토큰 관련 아이디어를 의도적으로 반영했음을 밝힙니다.
