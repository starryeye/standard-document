초록

이 명세는 OAuth 2.0 client가 OAuth 2.0 authorization server(인가 서버)와 상호작용하는 데 필요한 정보를 얻을 수 있도록 metadata(메타데이터) 형식을 정의합니다. 이 정보에는 endpoint의 위치와 authorization server의 기능이 포함됩니다.

이 문서의 지위

이 문서는 인터넷 표준 트랙 문서입니다.

이 문서는 Internet Engineering Task Force(IETF)의 산출물이며, IETF 커뮤니티의 합의를 나타냅니다. 공개 검토를 거쳤으며 Internet Engineering Steering Group(IESG)이 발행을 승인했습니다. 인터넷 표준에 관한 자세한 내용은 RFC 7841의 2절에서 확인할 수 있습니다.

이 문서의 현재 상태, 정오표 및 의견 제출 방법에 관한 정보는 https://www.rfc-editor.org/info/rfc8414에서 확인할 수 있습니다.

1. 소개

이 명세는 "OpenID Connect Discovery 1.0" [OpenID.Discovery]에서 정의한 metadata 형식을 일반화하여, OpenID Connect Discovery와의 호환성을 유지하면서 더 다양한 OAuth 2.0 사용 사례에 적용할 수 있게 합니다. 이는 "OAuth 2.0 Dynamic Client Registration(동적 클라이언트 등록) Protocol" [RFC7591]이 "OpenID Connect Dynamic Client Registration 1.0" [OpenID.Registration]에서 정의한 Dynamic Client Registration 메커니즘을 해당 명세와 호환되도록 일반화한 방식을 의도적으로 따릅니다.

authorization server의 metadata는 well-known 위치에서 JSON [RFC8259] 문서로 가져옵니다. 이 문서는 해당 authorization server의 endpoint 위치와 지원 기능을 명시합니다. 이 과정은 3절에서 설명합니다.

이 metadata는 서버 origin이 직접 진술하여 HTTPS로 전달하거나, JSON Web Token (JWT) [JWT]의 claim으로 표현한 서명된 metadata 값의 집합으로 전달할 수 있습니다. JWT를 사용하는 경우 issuer(발급자)가 해당 authorization server에 관한 데이터의 유효성을 보증합니다. 이는 OAuth Dynamic Client Registration [RFC7591]에서 Software Statement가 하는 역할과 유사합니다.

client가 authorization server를 선택하는 방법은 이 명세의 범위를 벗어납니다. 경우에 따라 해당 authorization server의 issuer 식별자를 client에 수동으로 설정할 수 있습니다. 다른 경우에는 "OpenID Connect Discovery 1.0" [OpenID.Discovery]의 2절에서 설명하듯, 예를 들어 WebFinger [RFC7033]를 사용해 동적으로 찾을 수 있습니다.

1.1. 요구사항 표기와 규칙

이 문서에서 키워드 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", "OPTIONAL"은 여기에 보인 것처럼 모두 대문자로 표기된 경우에만 BCP 14 [RFC2119] [RFC8174]에 설명된 의미로 해석합니다.

이 명세에서 JSON Web Signature (JWS) [JWS] 및 JSON Web Encryption (JWE) [JWE] 데이터 구조를 사용하는 모든 경우에는 JWS Compact Serialization 또는 JWE Compact Serialization을 사용합니다. JWS JSON Serialization과 JWE JSON Serialization은 사용하지 않습니다.

1.2. 용어

이 명세는 OAuth 2.0 [RFC6749]에서 정의한 "Access Token", "Authorization Code", "Authorization Endpoint", "Authorization Grant", "Authorization Server", "Client", "Client Authentication", "Client Identifier", "Client Secret", "Grant Type", "Protected Resource", "Redirection URI", "Refresh Token", "Resource Owner", "Resource Server", "Response Type", "Token Endpoint"라는 용어를 사용합니다. 또한 JSON Web Token (JWT) [JWT]에서 정의한 "Claim Name", "Claim Value", "JSON Web Token (JWT)"와 "OAuth 2.0 Multiple Response Type Encoding Practices" [OAuth.Responses]에서 정의한 "Response Mode"라는 용어를 사용합니다.

2. Authorization Server Metadata

authorization server에는 자체 구성을 설명하는 metadata가 있을 수 있습니다. 이 명세에서 사용하는 다음 authorization server metadata 값은 7.1절에서 신설하는 IANA의 "OAuth Authorization Server Metadata" 레지스트리에 등록됩니다.

issuer
REQUIRED. authorization server의 issuer 식별자입니다. 이 식별자는 "https" 스킴을 사용하며 query 또는 fragment 구성 요소가 없는 URL입니다. 3절에서 설명하는 것처럼, authorization server metadata는 이 issuer 식별자로부터 도출한, RFC 5785 [RFC5785]에 따른 ".well-known" 위치에 게시됩니다. issuer 식별자는 "OAuth 2.0 Mix-Up Mitigation" [MIX-UP]에서 설명하는 authorization server mix-up 공격을 방지하는 데 사용됩니다.
authorization_endpoint
authorization server의 authorization endpoint(인가 엔드포인트) [RFC6749] URL입니다. authorization endpoint를 사용하는 grant type(인가 유형)을 하나도 지원하지 않는 경우를 제외하면 이 항목은 REQUIRED입니다.
token_endpoint
authorization server의 token endpoint(토큰 엔드포인트) [RFC6749] URL입니다. implicit grant type만 지원하는 경우를 제외하면 이 항목은 REQUIRED입니다.
jwks_uri
OPTIONAL. authorization server의 JWK Set [JWK] 문서 URL입니다. 이 문서에는 client가 authorization server의 서명을 검증하는 데 사용하는 서명 키가 하나 이상 들어 있습니다. 이 URL은 "https" 스킴을 사용해야 합니다(MUST). JWK Set에는 client가 서버로 보내는 요청을 암호화하는 데 사용하는 서버의 암호화 키가 하나 이상 포함될 수도 있습니다(MAY). 서명 키와 암호화 키를 모두 제공하는 경우, 각 키의 용도를 나타내도록 해당 JWK Set의 모든 키에 "use"(공개 키 용도) 매개변수 값이 REQUIRED입니다.
registration_endpoint
OPTIONAL. authorization server의 OAuth 2.0 Dynamic Client Registration endpoint [RFC7591] URL입니다.
scopes_supported
RECOMMENDED. 이 authorization server가 지원하는 OAuth 2.0 [RFC6749] "scope" 값 목록을 담은 JSON 배열입니다. 서버는 이 매개변수를 사용하더라도 지원하는 scope 값 중 일부를 공개하지 않을 수 있습니다(MAY).
response_types_supported
REQUIRED. 이 authorization server가 지원하는 OAuth 2.0 "response_type" 값 목록을 담은 JSON 배열입니다. 이 배열에 사용하는 값은 "OAuth 2.0 Dynamic Client Registration Protocol" [RFC7591]에서 정의한 "response_types" 매개변수에 사용하는 값과 같습니다.
response_modes_supported
OPTIONAL. "OAuth 2.0 Multiple Response Type Encoding Practices" [OAuth.Responses]에 명시된 OAuth 2.0 "response_mode" 값 중 이 authorization server가 지원하는 값의 목록을 담은 JSON 배열입니다. 생략하면 기본값은 ["query", "fragment"]입니다. response mode 값 "form_post"도 "OAuth 2.0 Form Post Response Mode" [OAuth.Post]에서 정의합니다.
grant_types_supported
OPTIONAL. 이 authorization server가 지원하는 OAuth 2.0 grant type 값 목록을 담은 JSON 배열입니다. 이 배열에 사용하는 값은 "OAuth 2.0 Dynamic Client Registration Protocol" [RFC7591]에서 정의한 "grant_types" 매개변수에 사용하는 값과 같습니다. 생략하면 기본값은 ["authorization_code", "implicit"]입니다.
token_endpoint_auth_methods_supported
OPTIONAL. 이 token endpoint가 지원하는 client authentication 방식의 목록을 담은 JSON 배열입니다. client authentication 방식의 값은 [RFC7591]의 2절에서 정의한 "token_endpoint_auth_method" 매개변수에 사용합니다. 생략하면 기본값은 "client_secret_basic"으로, OAuth 2.0 [RFC6749]의 2.3.1절에 명시된 HTTP Basic Authentication Scheme입니다.
token_endpoint_auth_signing_alg_values_supported
OPTIONAL. "private_key_jwt" 및 "client_secret_jwt" 인증 방식에서 token endpoint가 client를 인증할 때 사용하는 JWT [JWT]의 서명에 대해, 이 endpoint가 지원하는 JWS 서명 알고리즘("alg" 값)의 목록을 담은 JSON 배열입니다. "token_endpoint_auth_methods_supported" 항목에 이 두 인증 방식 중 하나라도 명시된 경우에는 이 metadata 항목이 있어야 합니다(MUST). 이 항목을 생략하더라도 기본 알고리즘이 적용되는 것은 아닙니다. 서버는 "RS256"을 지원하는 것이 권장됩니다(SHOULD). "none" 값은 사용해서는 안 됩니다(MUST NOT).
service_documentation
OPTIONAL. 개발자가 authorization server를 사용할 때 알고 싶거나 알아야 할 정보를 사람이 읽을 수 있는 형태로 제공하는 페이지의 URL입니다. 특히 authorization server가 Dynamic Client Registration을 지원하지 않는 경우, 이 문서에서 client를 등록하는 방법을 안내해야 합니다.
ui_locales_supported
OPTIONAL. 사용자 인터페이스에서 지원하는 언어와 문자 체계를 BCP 47 [RFC5646]의 언어 태그 값으로 구성된 JSON 배열로 나타냅니다. 생략하면 어떤 언어와 문자 체계를 지원하는지는 명시되지 않습니다.
op_policy_uri
OPTIONAL. client를 등록하는 사람이 authorization server가 제공한 데이터를 client가 어떻게 사용할 수 있는지에 관한 요구사항을 읽을 수 있도록, authorization server가 제공하는 URL입니다. 이 URL이 주어지면 등록 절차에서 client를 등록하는 사람에게 표시하는 것이 권장됩니다(SHOULD). 5절에서 설명하는 것처럼, "op_policy_uri"라는 식별자는 OpenID 전용처럼 보이지만 이 명세에서는 실제로 OpenID Connect에 한정되지 않는 일반적인 OAuth 2.0 기능을 가리킵니다.
op_tos_uri
OPTIONAL. client를 등록하는 사람이 authorization server의 서비스 이용약관을 읽을 수 있도록 authorization server가 제공하는 URL입니다. 이 URL이 주어지면 등록 절차에서 client를 등록하는 사람에게 표시하는 것이 권장됩니다(SHOULD). 5절에서 설명하는 것처럼, "op_tos_uri"라는 식별자는 OpenID 전용처럼 보이지만 이 명세에서는 실제로 OpenID Connect에 한정되지 않는 일반적인 OAuth 2.0 기능을 가리킵니다.
revocation_endpoint
OPTIONAL. authorization server의 OAuth 2.0 revocation endpoint(토큰 폐기 엔드포인트) [RFC7009] URL입니다.
revocation_endpoint_auth_methods_supported
OPTIONAL. 이 revocation endpoint가 지원하는 client authentication 방식의 목록을 담은 JSON 배열입니다. 유효한 client authentication 방식의 값은 IANA의 "OAuth Token Endpoint Authentication Methods" 레지스트리 [IANA.OAuth.Parameters]에 등록된 값입니다. 생략하면 기본값은 "client_secret_basic"으로, OAuth 2.0 [RFC6749]의 2.3.1절에 명시된 HTTP Basic Authentication Scheme입니다.
revocation_endpoint_auth_signing_alg_values_supported
OPTIONAL. revocation endpoint가 client를 인증하는 데 사용하는 JWT [JWT]의 서명에 대해 지원하는 JWS 서명 알고리즘("alg" 값)의 목록을 담은 JSON 배열로, "private_key_jwt" 및 "client_secret_jwt" 인증 방식에 적용됩니다. "revocation_endpoint_auth_methods_supported" 항목에 이 두 인증 방식 중 하나라도 명시된 경우에는 이 metadata 항목이 있어야 합니다(MUST). 이 항목을 생략하더라도 기본 알고리즘이 적용되는 것은 아닙니다. "none" 값은 사용해서는 안 됩니다(MUST NOT).
introspection_endpoint
OPTIONAL. authorization server의 OAuth 2.0 introspection endpoint(토큰 인트로스펙션 엔드포인트) [RFC7662] URL입니다.
introspection_endpoint_auth_methods_supported
OPTIONAL. 이 introspection endpoint에서 지원하는 client authentication 방식 목록을 담은 JSON 배열입니다. 유효한 client authentication 방식 값은 IANA의 "OAuth Token Endpoint Authentication Methods" 레지스트리 [IANA.OAuth.Parameters] 또는 "OAuth Access Token Types" 레지스트리 [IANA.OAuth.Parameters]에 등록된 값입니다. (7.2절에 따라 두 레지스트리의 값은 서로 다르며 앞으로도 서로 다르게 유지됩니다.) 이 항목을 생략하면 다른 방법으로 지원되는 인증 방식 집합을 확인해야 합니다(MUST).
introspection_endpoint_auth_signing_alg_values_supported
OPTIONAL. "private_key_jwt" 및 "client_secret_jwt" 인증 방식에서 introspection endpoint가 client authentication에 사용하는 JWT [JWT]의 서명에 대해, 해당 endpoint가 지원하는 JWS 서명 알고리즘("alg" 값) 목록을 담은 JSON 배열입니다. 두 인증 방식 중 하나라도 "introspection_endpoint_auth_methods_supported" 항목에 명시되어 있으면 이 metadata 항목이 반드시 있어야 합니다(MUST). 이 항목이 생략되어도 기본 알고리즘이 있다고 간주하지 않습니다. "none" 값은 사용해서는 안 됩니다(MUST NOT).
code_challenge_methods_supported
OPTIONAL. 이 authorization server에서 지원하는 Proof Key for Code Exchange (PKCE) [RFC7636] code challenge method(코드 챌린지 방식) 목록을 담은 JSON 배열입니다. Code challenge method 값은 [RFC7636] 4.3절에 정의된 "code_challenge_method" 매개변수에 사용됩니다. 유효한 code challenge method 값은 IANA의 "PKCE Code Challenge Methods" 레지스트리 [IANA.OAuth.Parameters]에 등록된 값입니다. 이 항목이 생략되면 authorization server는 PKCE를 지원하지 않습니다.

authorization server metadata 매개변수를 추가로 사용할 수도 있습니다(MAY). 이 중 일부는 OpenID Connect Discovery 1.0 [OpenID.Discovery] 등 다른 명세에서 정의합니다.

2.1. 서명된 Authorization Server Metadata

metadata 값은 JSON 요소뿐 아니라 "signed_metadata" 값으로도 제공할 수 있습니다(MAY). 이 값은 authorization server에 관한 metadata 값을 한데 묶어 진술하는 JSON Web Token (JWT) [JWT]입니다. 서명된 metadata에서 사용할 수 있는 claim 집합은 2절에 정의되어 있습니다. 서명된 metadata에는 JSON Web Signature (JWS) [JWS]를 사용해 디지털 서명이나 MAC을 적용해야 하며(MUST), 그 안의 claim을 증명하는 당사자를 나타내는 "iss"(issuer) claim이 포함되어야 합니다(MUST). metadata를 사용하는 쪽이 이 기능을 지원하지 않으면 서명된 metadata를 무시할 수 있습니다(MAY). 서명된 metadata를 지원한다면, 서명된 metadata로 전달된 값이 일반 JSON 요소로 전달된 대응 값보다 우선해야 합니다(MUST).

서명된 metadata는 다음 OPTIONAL 멤버를 통해 authorization server metadata JSON 객체에 포함됩니다.

signed_metadata
authorization server에 관한 metadata 값을 claim으로 담은 JWT입니다. 이 값은 서명된 JWT 전체로 이루어진 문자열입니다. "signed_metadata" metadata 값은 이 JWT 안에 claim으로 나타나지 않는 것이 좋습니다(SHOULD NOT).

3. Authorization Server Metadata 가져오기

metadata를 지원하는 authorization server는 2절에 명시된 metadata를 담은 JSON 문서를 정해진 경로에서 제공해야 합니다(MUST). 이 경로는 authorization server의 issuer 식별자에서 호스트 구성 요소 뒤에 well-known URI 문자열을 삽입해 만들며, 경로 구성 요소가 있으면 그 앞에 삽입합니다. 기본 well-known URI 문자열은 "/.well-known/oauth-authorization-server"입니다. 이 경로에는 "https" 스킴을 사용해야 합니다(MUST). ".well-known"의 구문과 의미는 RFC 5785 [RFC5785]에 정의되어 있습니다. 사용하는 well-known URI 접미사는 IANA의 "Well-Known URIs" 레지스트리 [IANA.well-known]에 등록되어 있어야 합니다(MUST).

OAuth authorization server를 애플리케이션별 방식으로 활용하는 애플리케이션들은 저마다 사용하는 authorization server metadata를 게시하기 위해 서로 다른 well-known URI 접미사를 정의하고 등록할 수 있습니다. 예를 들어, 예시 애플리케이션이 OAuth authorization server를 고유한 방식으로 사용하고 게시해야 할 고유한 metadata 값이 있다면, "example-configuration" URI 접미사를 등록해 사용할 수 있습니다. 그러면 authorization server의 issuer 식별자에서 호스트 구성 요소와 경로 구성 요소 사이에 "/.well-known/example-configuration"을 삽입해 만든 경로에 metadata 문서를 게시할 수 있습니다. 반면 이런 애플리케이션 중 상당수는 기본 well-known URI 문자열 "/.well-known/oauth-authorization-server"를 사용하고 애플리케이션 전용 접미사는 등록하지 않을 것입니다. 이 기본 문자열은 범용 OAuth authorization server에 적합한 선택입니다.

이 명세를 사용하는 OAuth 2.0 애플리케이션은 이 용도로 사용할 well-known URI 접미사를 명시해야 합니다(MUST). 동일한 authorization server는 자신의 issuer 식별자에서 파생된 여러 well-known 위치에 metadata를 게시할 수 있습니다(MAY). 예를 들어 "/.well-known/example-configuration"과 "/.well-known/oauth-authorization-server" 양쪽에 게시할 수 있습니다.

일부 OAuth 애플리케이션은 well-known URI 접미사로 "openid-configuration"을 선택할 것입니다. 5절에서 설명하듯이, "/.well-known/openid-configuration"이라는 식별자가 OpenID 전용처럼 보이지만 이 명세에서는 실제로 OpenID Connect에 한정되지 않는 일반적인 OAuth 2.0 기능을 가리킵니다.

3.1. Authorization Server Metadata 요청

authorization server metadata 문서는 앞서 명시한 경로에 HTTP "GET" 요청을 보내 조회해야 합니다(MUST).

issuer 식별자가 "https://example.com"이고 well-known URI 접미사가 "oauth-authorization-server"인 경우, issuer 식별자에 경로 구성 요소가 없으므로 client는 metadata를 얻기 위해 다음 요청을 보냅니다.

     GET /.well-known/oauth-authorization-server HTTP/1.1
     Host: example.com

issuer 식별자 값에 경로 구성 요소가 있으면, 호스트 구성 요소와 경로 구성 요소 사이에 "/.well-known/"과 well-known URI 접미사를 삽입하기 전에 끝의 "/"를 제거해야 합니다(MUST). issuer 식별자가 "https://example.com/issuer1"이고 well-known URI 접미사가 "oauth-authorization-server"인 경우, issuer 식별자에 경로 구성 요소가 있으므로 client는 metadata를 얻기 위해 다음 요청을 보냅니다.

     GET /.well-known/oauth-authorization-server/issuer1 HTTP/1.1
     Host: example.com

경로 구성 요소를 사용하면 호스트 하나에서 여러 issuer를 지원할 수 있습니다. 일부 멀티테넌트 호스팅 구성에서는 이 기능이 필요합니다. 이때 ".well-known"은 호스트 하나에서 여러 issuer를 지원하는 데 쓰이며, RFC 5785 [RFC5785]에서와 달리 호스트에 관한 일반 정보를 제공하지 않습니다.

3.2. Authorization Server Metadata 응답

응답은 필요한 모든 endpoint와 공개 키의 위치 정보를 비롯하여 authorization server의 구성에 관한 claim을 담습니다. 성공 응답은 HTTP 상태 코드 200 OK를 사용하고, 2절에 정의된 metadata 값의 부분집합에 해당하는 claim을 멤버로 담은 JSON 객체를 "application/json" 콘텐츠 유형으로 반환해야 합니다(MUST). 다른 claim을 함께 반환할 수도 있습니다(MAY).

여러 값을 반환하는 claim은 JSON 배열로 표현합니다. 요소가 하나도 없는 claim은 응답에서 생략해야 합니다(MUST).

오류 응답에는 해당 오류에 맞는 HTTP 상태 코드 값을 사용합니다.

다음은 규범적 요구사항이 아닌 응답 예시입니다.

     HTTP/1.1 200 OK
     Content-Type: application/json

     {
      "issuer":
        "https://server.example.com",
      "authorization_endpoint":
        "https://server.example.com/authorize",
      "token_endpoint":
        "https://server.example.com/token",
      "token_endpoint_auth_methods_supported":
        ["client_secret_basic", "private_key_jwt"],
      "token_endpoint_auth_signing_alg_values_supported":
        ["RS256", "ES256"],
      "userinfo_endpoint":
        "https://server.example.com/userinfo",
      "jwks_uri":
        "https://server.example.com/jwks.json",
      "registration_endpoint":
        "https://server.example.com/register",
      "scopes_supported":
        ["openid", "profile", "email", "address",
         "phone", "offline_access"],
      "response_types_supported":
        ["code", "code token"],
      "service_documentation":
        "http://server.example.com/service_documentation.html",
      "ui_locales_supported":
        ["en-US", "en-GB", "en-CA", "fr-FR", "fr-CA"]
     }

3.3. Authorization Server Metadata 검증

반환된 "issuer" 값은 metadata를 가져오는 데 사용한 URL을 만들 때 well-known URI 문자열을 삽입하기 전의 authorization server issuer 식별자 값과 동일해야 합니다(MUST). 두 값이 동일하지 않으면 응답에 포함된 데이터를 사용해서는 안 됩니다(MUST NOT).

4. 문자열 연산

일부 OAuth 2.0 메시지를 처리하려면 메시지에 포함된 값을 이미 알려진 값과 비교해야 합니다. 예를 들어 metadata 응답의 멤버 이름을 "issuer"와 같은 특정 멤버 이름과 비교할 수 있습니다. 다만 Unicode [UNICODE] 문자열을 비교하는 방식은 보안에 중대한 영향을 미칩니다.

따라서 JSON 문자열과 다른 Unicode 문자열은 아래에 명시된 방식으로 비교해야 합니다(MUST).

1. JSON에서 적용한 이스케이프 처리를 모두 되돌려 Unicode code point(유니코드 코드 포인트) 배열을 만듭니다.
2. JSON 문자열과 비교 대상 문자열 어느 쪽에도 어떤 단계에서든 Unicode Normalization [USA15]을 적용해서는 안 됩니다(MUST NOT).
3. 두 문자열을 비교할 때는 서로 대응하는 Unicode code point가 같은지 하나씩 비교해야 합니다(MUST).

이는 [RFC8259] 8.3절에 설명된 동등성 비교 절차와 동일합니다.

5. 호환성 참고 사항

"/.well-known/openid-configuration", "op_policy_uri", "op_tos_uri" 식별자는 OpenID Connect [OpenID.Core] 명세 계열을 가리키는 문자열을 포함하며, 이 식별자들은 원래 "OpenID Connect Discovery 1.0" [OpenID.Discovery]에서 정의되었습니다. OpenID 전용처럼 보이는 이 식별자들을 재사용하지만, 이 명세에서는 실제로 OpenID Connect에 한정되지 않는 일반적인 OAuth 2.0 기능을 가리킵니다.

3절에 정의된, issuer 식별자를 authorization server metadata 위치로 변환하는 알고리즘은 issuer 식별자에 경로 구성 요소가 없는 경우 "OpenID Connect Discovery 1.0" [OpenID.Discovery] 4절에 정의된 대응 변환과 동일합니다. 하지만 경로 구성 요소가 있으면 두 변환 방식이 다릅니다. OpenID Connect Discovery 1.0은 well-known URI 문자열을 issuer 식별자 끝에 덧붙이도록 명시하는 반면(예: "https://example.com/issuer1/.well-known/openid-configuration"), 이 명세는 issuer 식별자의 경로 구성 요소 앞에 삽입하도록 명시하기 때문입니다(예: "https://example.com/.well-known/openid-configuration/issuer1").

앞으로 OAuth authorization server metadata 위치를 정할 때는 이 명세에서 정의한 변환을 사용하는 것이 좋습니다. 다만 OpenID Connect Discovery 1.0의 변환이 이미 사용 중인 레거시 환경에 배포하는 경우, 전환 기간에는 경로 구성 요소가 있는 issuer 식별자의 metadata를 두 위치에 모두 게시해야 할 수도 있습니다. 이 기간에 애플리케이션은 먼저 이 명세의 변환을 적용해 그 결과 위치에서 authorization server metadata를 가져오도록 시도하는 것이 좋습니다. 해당 위치에서 가져오지 못한 경우에만 OpenID Connect Discovery 1.0이 정의한 변환으로 얻은 대체 위치에서 다시 시도하는 것이 좋습니다. 이러한 하위 호환 동작은 애플리케이션이 사용하는 well-known URI 접미사가 "openid-configuration"인 경우에만 필요할 것으로 예상됩니다.

6. 보안 고려 사항

6.1. TLS 요구사항

구현체는 TLS를 지원해야 합니다(MUST). 어떤 버전을 구현하는 것이 적절한지는 시간이 지나면서 달라지며, 구현 시점의 보급 현황과 알려진 보안 취약점에 따라 결정됩니다. authorization server는 TLS 버전 1.2 [RFC5246]를 지원해야 하며(MUST), 자체 보안 요구사항을 충족하는 TLS 메커니즘을 추가로 지원할 수 있습니다(MAY). TLS를 사용할 때 client는 RFC 6125 [RFC6125]에 따라 TLS/SSL 서버 인증서를 검증해야 합니다(MUST). 구현 시 보안 고려 사항은 "Recommendations for Secure Use of Transport Layer Security (TLS) and Datagram Transport Layer Security (DTLS)" [BCP195]에서 확인할 수 있습니다.

정보 유출과 변조를 막으려면 기밀성과 무결성을 보호하는 cipher suite를 사용하는 TLS로 기밀성을 보호해야 합니다(MUST).

6.2. 사칭 공격

client가 authorization server metadata를 요청할 때는 6.1절에 설명된 대로 TLS 인증서를 검사해야 합니다(MUST). 서버 인증서가 issuer 식별자 URL에 대해 유효한지 확인하면 중간자 공격과 DNS 기반 공격을 방지할 수 있습니다. 이러한 공격은 client를 속여 공격자의 키와 endpoint를 사용하게 함으로써 정당한 authorization server를 사칭할 수 있게 합니다. 공격자가 사칭에 성공하면, 영향을 받은 client가 사칭 대상 authorization server를 사용해 접근할 수 있는 리소스에 접근할 수 있습니다.

공격자는 사칭 대상 authorization server의 issuer 식별자 URL을 "issuer" claim에 넣되, endpoint와 서명 키는 자신의 것으로 넣은 metadata 문서를 게시하여 authorization server를 사칭하려 할 수도 있습니다. client가 그 문서를 받아들이면 공격자는 해당 authorization server를 사칭할 수 있습니다. 이를 방지하려면 client는 metadata 요청의 접두부로 사용하는 issuer 식별자 URL이 수신한 authorization server metadata 문서에 있는 "issuer" metadata 값과 정확히 일치하는지 확인해야 합니다(MUST).

6.3. 표준 형식으로 metadata 게시

authorization server 정보를 표준 형식으로 게시하면 정당한 client와 공격자 모두 authorization server를 더 쉽게 사용할 수 있습니다. authorization server가 metadata를 자체 방식으로 게시하든 이 명세에서 정의한 표준 형식으로 게시하든, 이 정보를 이용해 시도할 수 있는 공격에는 동일한 방어 조치를 적용하는 것이 바람직합니다.

6.4. protected resource(보호된 리소스)

모든 사용 사례에서 authorization server와 함께 사용할 적절한 protected resource를 안전하게 결정하는 방법은 이 명세의 범위에 포함되지 않습니다. 이 명세는 client가 authorization server와 함께 사용할 적절한 protected resource를 결정할 수단을 갖추고 있으며, 각 authorization server에 올바른 metadata를 사용한다고 가정합니다. 구현자는 client가 부적절한 protected resource를 사용하면 공격자가 authorization server나 client에 탐지되지 않은 채 유효한 protected resource에 대한 중간자 proxy로 동작할 수 있음을 유의해야 합니다.

authorization server와 함께 사용할 적절한 protected resource를 결정하는 방법은 일반적으로 애플리케이션에 따라 다릅니다. 예를 들어 일부 authorization server는 고정된 protected resource 하나 또는 고정된 protected resource 집합과 함께 사용됩니다. 그 위치는 널리 알려져 있을 수도 있고, authorization server가 metadata 값으로 게시할 수도 있습니다. 다른 경우에는 관리 작업을 통해 authorization server와 함께 사용할 수 있는 리소스 집합을 동적으로 변경할 수 있습니다. 이 밖에도 authorization server와 protected resource 사이의 적절한 연결 관계를 결정하는 방법은 다양합니다.

7. IANA 고려 사항

이 명세에서 신설하는 registry에는 다음 등록 절차를 적용합니다.

값은 oauth-ext-review@ietf.org mailing list에서 2주간의 검토를 거친 뒤, 한 명 이상의 Designated Expert(지정 전문가)의 자문에 따라 Specification Required [RFC8126] 정책으로 등록합니다. 다만 명세가 발행되기 전에 값을 배정할 수 있도록, Designated Expert는 해당 명세가 발행될 것이라고 판단하면 등록을 승인할 수 있습니다.

검토를 위해 mailing list에 보내는 등록 요청에는 적절한 제목을 사용하는 것이 바람직합니다(예: "Request to register OAuth Authorization Server Metadata: example").

Designated Expert는 검토 기간 안에 등록 요청을 승인하거나 거부하고, 그 결정을 검토용 mailing list와 IANA에 알립니다. 거부할 때는 그 이유와, 해당하는 경우 요청이 승인될 수 있도록 개선할 방안을 함께 제시하는 것이 바람직합니다. 21일을 넘겨도 결정되지 않은 등록 요청은 해결을 위해 IESG에 알릴 수 있습니다(iesg@ietf.org mailing list 이용).

Designated Expert가 적용할 기준에는 제안된 등록이 기존 기능과 중복되는지, 일반적으로 적용할 수 있을 가능성이 있는지 아니면 특정 애플리케이션 하나에만 유용한지, 그리고 등록이 타당한지를 판단하는 것이 포함됩니다.

IANA는 Designated Expert가 제출한 registry 갱신만 받아들여야 하며, 모든 등록 요청은 검토용 mailing list로 안내하는 것이 바람직합니다.

등록 결정을 다양한 관점에서 충분한 정보를 바탕으로 검토할 수 있도록, 이 명세를 사용하는 여러 애플리케이션의 관점을 대변할 수 있는 Designated Expert를 여러 명 임명하는 것을 권장합니다. 등록 결정이 특정 Designated Expert에게 이해 상충을 일으키는 것으로 비칠 수 있다면, 해당 Designated Expert는 다른 Designated Expert의 판단에 맡기는 것이 바람직합니다.

7.1. OAuth Authorization Server Metadata Registry

이 명세는 OAuth 2.0 authorization server metadata 이름을 위한 IANA "OAuth Authorization Server Metadata" registry를 신설합니다. 이 registry에는 authorization server metadata 멤버와 이를 정의하는 명세에 대한 참조를 기록합니다.

Designated Expert는 다음 두 가지 중 하나를 따라야 합니다.

(a) 등록하려는 metadata 이름과 값에 큰따옴표('"')와 역슬래시('\')를 제외한 인쇄 가능한 ASCII 문자(Unicode code point U+0021, U+0023~U+005B, U+005D~U+007E에 해당하는 문자)만 사용하도록 요구합니다. 또는

(b) 다른 code point를 사용하는 새 metadata 멤버나 값을 정의한다면, 그 정의에 이를 나타내는 정확한 Unicode code point 시퀀스를 명시하도록 요구합니다. 또한 JSON 문자열에서 escape된 문자로만 표현할 수 있는 Unicode code point를 사용하는 등록 제안은 받아들여서는 안 됩니다.

7.1.1. 등록 양식

metadata 이름: 요청하는 이름(예: "issuer"). 이 이름은 대소문자를 구분합니다. Designated Expert가 예외를 허용할 만한 충분히 설득력 있는 사유가 있다고 명시하지 않는 한, 대소문자를 구분하지 않고 비교했을 때(두 문자열 모두에 Unicode toLowerCase() 연산을 적용하면 일치하는 경우) 이미 등록된 다른 이름과 일치해서는 안 됩니다.

metadata 설명: metadata에 대한 간략한 설명(예: "Issuer identifier URL").

변경 관리 주체: Standards Track RFC에는 "IESG"를 기재합니다. 그 외에는 담당 주체의 이름을 기재합니다. 우편 주소, 이메일 주소, 홈페이지 URI 등 다른 세부 정보도 포함할 수 있습니다.

명세 문서: 해당 매개변수를 명세하는 하나 이상의 문서에 대한 참조. 가급적 문서 사본을 가져올 수 있는 URI도 포함합니다. 관련 절을 표시할 수도 있지만 필수는 아닙니다.

7.2. 개정된 등록 지침

이 명세는 아래 두 IANA registry의 Designated Expert를 위한 지침을 추가합니다. 두 registry는 모두 "OAuth Parameters" registry [IANA.OAuth.Parameters]에 속합니다.

o OAuth Access Token Types

o OAuth Token Endpoint Authentication Methods

IANA는 이들 registry의 참고 문헌 섹션에 이 명세의 링크를 추가했습니다.

두 registry의 Designated Expert는 어느 한 registry에 이미 있는 값을 다른 registry에 등록하려는 요청을 거부해야 합니다. "introspection_endpoint_auth_methods_supported" parameter가 두 registry 중 어느 쪽의 값이든 사용할 수 있도록 허용하므로 이 지침이 필요합니다. 이렇게 하면 두 registry에 같은 값이 존재하지 않으므로 모호함이 생기지 않습니다.
