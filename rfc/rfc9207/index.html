초록

이 문서는 iss라는 새 매개변수를 규정한다. 이 매개변수는 OAuth 인가 흐름의 인가 응답에 authorization server의 issuer identifier를 명시적으로 포함하는 데 쓰인다. iss 매개변수는 ‘mix-up attack(서버 혼동 공격)’에 대한 효과적인 대응책이다.¶

1. 소개

OAuth 2.0 인가 프레임워크 [RFC6749]를 사용하면 client(클라이언트)는 서로 다른 주체가 관리하는 여러 독립적인 authorization server와 상호작용할 수 있다. 일부 OAuth grant type(그랜트 유형)은 resource owner(리소스 소유자)의 user agent(사용자 에이전트)를 통해 authorization server의 응답을 OAuth client에 전달한다. authorization code grant(인가 코드 그랜트)의 인가 응답이 그 예다.¶

4.1.2절([RFC6749])에서 규정하는 인가 응답에는 그 응답을 발급한 authorization server의 신원을 알려 주는 정보가 전혀 없다. 따라서 resource owner의 user agent에서 응답을 받은 client는 응답과 그 안의 비밀 정보를 누가 처음 발급했는지 확신할 수 없다. 응답의 출처를 확신할 수 없다는 점 때문에 ‘mix-up attack’이라는 유형의 공격이 가능해진다.¶

mix-up attack은 여러 authorization server와 상호작용하는 모든 OAuth client에 잠재적 위협이다. 그러한 authorization server 중 적어도 하나가 공격자의 통제하에 있으면 공격자는 mix-up attack을 통해 나머지 authorization server 중 어느 하나가 발급한 authorization code(인가 코드)나 access token(액세스 토큰)을 획득할 수 있다. 공격자가 client에서 지원하는 authorization server를 장악하는 데에는 여러 경로가 있다. 예를 들어 authorization server가 침해되거나, 공격자가 동적 client 등록 [RFC7591] 등을 이용해 자신이 운영하는 authorization server를 등록할 수 있다.¶

authorization server 한 곳과만 상호작용하는 OAuth client는 mix-up attack에 취약하지 않다. 하지만 이후 두 번째 authorization server를 지원하기로 하면 취약해지므로 mix-up attack에 대한 대응책을 적용해야 한다.¶

mix-up attack은 client를 속여 정상적인 authorization server나 resource server(리소스 서버) 대신 공격자에게 authorization code 또는 access token을 보내게 함으로써 이를 탈취하는 것을 목표로 한다. 이는 OAuth로 접근을 관리하는 리소스의 기밀성과 무결성에 심각한 위협이 된다. mix-up attack 유형에 대한 자세한 설명과 여러 변형은 4.4절("OAuth 2.0 Security Best Current Practice" [OAUTH-SECURITY-TOPICS])과, 이 공격 유형을 처음 지적한 연구인 "On the security of modern Single Sign-On Protocols: Second-Order Vulnerabilities in OpenID Connect" [arXiv.1508.04324] 및 "A Comprehensive Formal Security Analysis of OAuth 2.0" [arXiv.1601.01229]에서 확인할 수 있다.¶

이 문서는 인가 응답에 사용되는 새 매개변수 iss를 정의한다. authorization server는 iss 매개변수를 사용해 자신의 신원을 인가 응답에 명시할 수 있다. client는 iss 매개변수의 값을 자신이 통신 중이라고 판단한 authorization server의 issuer identifier(예를 들어 해당 서버의 메타데이터에서 얻은 값)와 비교할 수 있다. iss 매개변수를 통해 client는 authorization server의 신원을 확인하고 authorization code와 access token 같은 자격 증명을 의도한 수신자에게만 보낼 수 있다.¶

mix-up attack에 대한 iss 매개변수의 방어 효과는 "A Comprehensive Formal Security Analysis of OAuth 2.0" [arXiv.1601.01229]에서 분석하고 형식적으로 증명했다.¶

1.1. 표기 규칙과 용어

이 문서의 핵심 용어 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", "OPTIONAL"은 여기에 표시된 것처럼 모두 대문자로 표기된 경우에만 BCP 14 [RFC2119] [RFC8174]에 따라 해석한다.¶

이 명세에서는 OAuth 2.0 Authorization Framework [RFC6749]에서 정의한 "access token", "authorization code", "authorization code grant", "authorization server", "resource server", "인가 응답", "grant type", "client"라는 용어를 사용한다. "issuer identifier"는 OAuth 2.0 Authorization Server Metadata [RFC8414]에서 정의한다.¶

2. 응답 매개변수 iss

이 명세를 지원하는 authorization server는 client에 보내는 인가 응답에서 자신의 신원을 나타내야 한다(MUST). 이를 위해 오류 응답을 포함한 인가 응답에 iss 매개변수를 넣는다.¶

iss 매개변수의 값은 [RFC8414]에서 정의한 대로, 인가 응답을 생성한 authorization server의 issuer identifier다. 이 값은 "https" 스킴을 사용하고 쿼리나 프래그먼트 구성 요소가 없는 URL이어야 한다(MUST).¶

2.1. 인가 응답 예제

다음은 issuer identifier가 https://honest.as.example인 authorization server의 인가 응답 예제다(추가된 줄바꿈과 들여쓰기는 표시용일 뿐이다).¶

HTTP/1.1 302 Found
Location: https://client.example/cb?
  code=x1848ZT64p4IirMPT0R-X3141MFPTuBX-VFL_cvaplMH58
  &state=ZWVlNDBlYzA1NjdkMDNhYjg3ZjUxZjAyNGQzMTM2NzI
  &iss=https%3A%2F%2Fhonest.as.example
¶

2.2. 오류 응답 예제

다음은 같은 authorization server의 오류 응답 예제다(추가된 줄바꿈과 들여쓰기는 표시용일 뿐이다).¶

HTTP/1.1 302 Found
Location: https://client.example/cb?
  error=access_denied
  &state=N2JjNGJhY2JiZjRhYzA3MGJkMzNmMDE5OWJhZmJhZjA
  &iss=https%3A%2F%2Fhonest.as.example
¶

2.3. issuer identifier 제공

이 명세를 지원하는 authorization server는 자신의 issuer identifier를 제공해야 한다(MUST). 그래야 client가 iss 매개변수를 제대로 검증할 수 있다.¶

[RFC8414]에 따라 메타데이터를 게시하는 authorization server에는 다음 규칙을 적용한다.¶

  • 서버 메타데이터의 issuer 값에 포함된 issuer identifier는 반드시(MUST) iss 매개변수의 값과 동일해야 한다.¶

  • 서버는 다음과 같이 매개변수 지원을 표시해야 한다(MUST). iss 매개변수를 지원한다는 뜻으로 메타데이터 매개변수 authorization_response_iss_parameter_supported(3절에서 정의)를 true로 설정한다.¶

authorization server는 다른 방법을 사용해 issuer identifier를 client에 추가로 제공할 수도 있다(MAY). 이러한 방법은 이 명세의 범위에 포함되지 않는다.¶

2.4. issuer identifier 검증

이 명세를 지원하는 client는 다음 규칙을 반드시(MUST) 따라야 한다. 수신한 인가 응답에 iss 매개변수가 있으면 그 값을 추출한다. 이어서 client는 다음과 같이 값을 디코딩하고 비교해야 한다(MUST). 부록 B([RFC6749])에 따라 "application/x-www-form-urlencoded" 형식의 값을 디코딩하고, 그 결과를 인가 요청을 보낸 대상 authorization server의 issuer identifier와 비교한다. 이때는 단순 문자열 비교를 사용해야 한다(MUST). 이 비교 방식은 6.2.1절([RFC3986])에서 정의한다. 값이 예상한 issuer identifier와 일치하지 않으면 client는 인가 응답을 거부해야 하며(MUST), authorization grant 절차를 계속 진행해서는 안 된다(MUST NOT). 오류 응답의 경우, client는 오류가 의도한 authorization server에서 발생했다고 가정해서는 안 된다(MUST NOT).¶

더 정확히 말하면, OAuth 메타데이터 [RFC8414]를 지원하는 authorization server와 통신하는 client는 반드시(MUST) iss 매개변수의 값을 서버의 메타데이터 문서에 있는 issuer 값과 비교해야 한다. OAuth 메타데이터를 사용하지 않는 경우, client는 반드시(MUST) 반환된 iss 값이 현재 흐름에서 예상한 값인지 배포 환경별 방식(예: 정적 구성)으로 판단해야 한다. 이와 관련해서는 4절도 참조한다.¶

client가 이 명세를 지원하는 authorization server와 지원하지 않는 authorization server 양쪽 모두와 통신하는 경우, 반드시(MUST) 각 authorization server의 iss 매개변수 지원 여부를 상태로 유지해야 한다. client는 반드시(MUST) 자신의 구성에서 해당 매개변수를 지원한다고 되어 있는 authorization server가 iss 매개변수 없이 보낸 인가 응답을 거부해야 한다. client에는 다음 조치가 권고된다(SHOULD). 해당 매개변수를 지원한다고 표시하지 않은 authorization server가 iss 매개변수를 포함해 보낸 인가 응답은 폐기한다. 다만 정상적인 authorization server도 메타데이터에 지원 여부를 표시하지 않고 iss 매개변수를 제공할 수 있다. 이러한 응답의 수락 여부는 로컬 정책이나 구성에서 정할 수 있으며, 구체적인 지침은 이 명세의 범위에 포함되지 않는다.¶

일반적으로 이 명세를 지원하는 client는 다음 두 방식 중 하나를 택할 수 있다(MAY). iss 매개변수가 없는 인가 응답을 수락하거나, 그러한 응답을 거부하고 인가 응답에 iss 매개변수를 제공하는 authorization server만 지원한다. 이러한 응답을 언제 수락할지는 로컬 정책이나 구성에서 정할 수 있으며, 구체적인 지침은 이 명세의 범위에 포함되지 않는다.¶

인가 엔드포인트에서 ID Token(ID 토큰)을 반환하는 OpenID Connect [OIDC.Core] 흐름에서는 iss 매개변수의 값이 반드시(MUST) ID Token의 iss 클레임 값과 항상 동일해야 한다.¶

4.1.2절([RFC6749])에서는 이미 다음 의무를 규정하고 있다(MUST). 이 명세를 지원하지 않는 client는 인식하지 못하는 iss 매개변수를 무시해야 한다.¶

참고: "JWT Secured Authorization Response Mode for OAuth 2.0 (JARM)" [JARM]은 모든 인가 응답 매개변수를 JSON Web Token(JWT)에 담아 전달하는 방식을 정의한다. 이 JWT에는 iss 클레임이 있으며, 이 클레임을 2.4절에 설명된 대로 검증하면 동일한 보호 효과를 얻을 수 있다. 따라서 JARM을 사용하는 경우 JWT 외부에 별도의 iss 매개변수를 둘 필요가 없다.¶

3. authorization server 메타데이터

authorization server가 이 명세를 지원한다는 사실을 알릴 수 있도록 authorization server 메타데이터 [RFC8414]에 다음 매개변수를 도입한다.¶

authorization_response_iss_parameter_supported:

authorization server가 인가 응답에 iss 매개변수를 2절에서 정의한 대로 제공하는지 나타내는 불리언 매개변수다. 생략하면 기본값은 false다.¶

4. 보안 고려사항

client는 반드시(MUST) iss 매개변수를 2.4절에 설명된 방식 그대로 검증해야 하며, 여러 authorization server가 같은 issuer identifier를 사용하도록 허용해서는 안 된다(MUST NOT). 특히 client에서 authorization server의 세부 정보를 수동으로 구성할 수 있는 경우, client는 반드시(MUST) 수락하는 iss 값이 authorization server마다 고유한지 확인해야 한다.¶

client는 iss 매개변수를 통해, 특정 token endpoint(토큰 엔드포인트)를 사용하고 경우에 따라 userinfo endpoint(사용자 정보 엔드포인트) [OIDC.Core] 같은 다른 엔드포인트도 사용하는 OAuth 흐름에 authorization server가 자신이 쓰이기를 "기대하는지" 판단할 수 있다. OAuth 메타데이터를 사용하는 경우, iss 매개변수로 발급자를 식별할 수 있으므로 다른 엔드포인트를 가리키는 해당 OAuth 메타데이터 문서도 식별할 수 있다. OAuth 메타데이터를 사용하지 않는 경우, client는 예를 들어 구성된 각 authorization server에 대해 예상 iss 값을 정적으로 설정해 사용할 수 있다.¶

인가 응답에 포함된 issuer identifier에는 변조를 막는 암호학적 보호가 적용되지 않는다. 일반적으로 [JARM]에 명시된 JWT 같은 메커니즘으로 인가 응답의 무결성을 보호할 수 있다. 그러나 mix-up attack에서 client는 대개 침해되지 않은 authorization server로부터 인가 응답을 받는다. 공격자가 client가 응답을 받기 전에 그 응답을 변조할 수 있다면, authorization code에도 직접 접근할 수 있다. 따라서 authorization code를 탈취하는 데 mix-up attack을 실행할 필요가 없다. 그러므로 mix-up attack을 방어하기 위해 인가 응답의 무결성을 보호할 필요는 없다.¶

mix-up attack에 대응하는 다른 방법도 있다. 인가 응답에 다른 수단으로 authorization server의 issuer identifier가 이미 포함되어 있고 이 식별자를 2.4절에 명시된 대로 확인한다면, iss 매개변수를 사용하고 검증할 필요가 없으며 이를 생략해도 된다(MAY). 예를 들어 인가 엔드포인트에서 ID Token을 반환하는 OpenID Connect 응답 유형(예: response_type=code id_token)을 사용하거나 [JARM]을 사용하는 경우가 이에 해당한다. 다만 client가 여러 issuer identifier를 포함한 인가 응답을 받았고 그 issuer identifier가 서로 일치하지 않는다면, client는 응답을 거부해야 한다(MUST). 이러한 대체 대응책의 세부 사항은 이 명세의 범위를 벗어난다.¶

mix-up attack은 둘 이상의 authorization server와 상호작용하는 client에만 해당한다. 그러나 하나의 authorization server와만 상호작용하는 client도 앞으로 두 번째 authorization server를 지원하게 될 수 있다. 둘 이상의 authorization server를 지원하면 mix-up attack에 취약해지므로 대응책을 적용해야 한다.¶

5. IANA 고려사항

5.1. OAuth authorization server 메타데이터

IANA는 [IANA.OAuth.Parameters]의 ‘OAuth authorization server 메타데이터’ 레지스트리에 다음 값을 등록했다. 이 레지스트리는 [RFC8414]에 따라 마련되었다.¶

메타데이터 이름:
authorization_response_iss_parameter_supported¶
메타데이터 설명:
authorization server가 인가 응답에 iss 매개변수를 제공하는지 나타내는 불리언 값.¶
변경 관리 주체:
IETF¶
명세 문서:
RFC 9207의 3절¶

5.2. OAuth 매개변수 등록

IANA는 iss 항목을 [IANA.OAuth.Parameters]의 ‘OAuth 매개변수’ 레지스트리에서 다음과 같이 갱신했다. 이 레지스트리는 [RFC6749]에 따라 마련되었다.¶

매개변수 이름:
iss¶
매개변수 사용 위치:
인가 요청, 인가 응답¶
변경 관리 주체:
IETF¶
명세 문서:
RFC 9207의 2절, [RFC9101] 및 4.1.1절([RFC7519]).¶
