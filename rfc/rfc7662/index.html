초록

이 명세는 protected resource(보호된 리소스)가 OAuth 2.0 authorization server(인가 서버)에 질의하여 OAuth 2.0 토큰이 활성 상태인지 확인하고 해당 토큰의 메타 정보를 알아내는 방법을 정의한다. OAuth 2.0을 배포한 환경에서는 이 방법을 사용하여 토큰의 인가 맥락에 관한 정보를 authorization server에서 protected resource로 전달할 수 있다.

이 문서의 상태

이 문서는 인터넷 표준 트랙 문서이다.

이 문서는 Internet Engineering Task Force (IETF)가 작성한 것으로, IETF 커뮤니티의 합의를 반영한다. 공개 검토를 거쳤으며 Internet Engineering Steering Group (IESG)이 발행을 승인했다. 인터넷 표준에 관한 자세한 내용은 RFC 5741의 2절에서 확인할 수 있다.

이 문서의 현재 상태, 정오표(있는 경우), 의견 제출 방법에 관한 정보는 http://www.rfc-editor.org/info/rfc7662에서 확인할 수 있다.

1. 소개

OAuth 2.0 [RFC6749]에서 토큰의 내용은 client(클라이언트)에 드러나지 않는다. 다시 말해 토큰 자체에 내용이나 구조가 있더라도 client는 이를 전혀 알 필요가 없다. 그러나 토큰에는 현재 유효 여부, 승인된 scope(범위), 토큰이 발급된 맥락에 관한 정보 등 많은 메타데이터가 붙을 수 있다. 이러한 정보는 제시된 토큰을 바탕으로 인가 결정을 내리는 protected resource에 매우 중요한 경우가 많다. OAuth 2.0은 resource server(리소스 서버)가 authorization server로부터 받은 토큰의 메타 정보를 알아내기 위한 프로토콜을 정의하지 않으므로, 이 공백을 메우기 위해 여러 접근 방식이 개발되었다. 예를 들어 JWT [RFC7519] 같은 구조화된 토큰 형식을 사용하거나, 토큰 정보를 전달하는 독자적인 서비스 간 통신 방식(공유 데이터베이스나 보호된 엔터프라이즈 서비스 버스 등)을 사용하는 방법이 있다.

이 명세는 권한을 부여받은 protected resource가 OAuth 2.0 client로부터 제시받은 토큰의 메타데이터를 확인하기 위해 authorization server에 질의할 수 있게 해 주는 프로토콜을 정의한다. 이 메타데이터에는 토큰이 현재 활성 상태인지(만료되었거나 그 밖의 이유로 철회되었는지), 토큰에 어떤 접근 권한이 부여되었는지(보통 OAuth 2.0 scope로 전달됨), 그리고 어떤 인가 맥락에서 토큰이 부여되었는지(누가 토큰을 인가했고 어느 client에 발급되었는지 포함)가 담긴다. token introspection(토큰 상태 조회)을 사용하면 이 정보가 토큰 자체에 담겨 있는지와 관계없이 protected resource가 이를 조회할 수 있으므로, 이 방식을 구조화된 토큰 값과 함께 사용하거나 독립적으로 사용할 수 있다. 또한 protected resource는 이 명세에서 설명하는 방식으로 특정 인가 결정의 맥락에서 token introspection을 수행하고 관련 메타데이터를 확인하여 적절한 인가 결정을 내릴 수 있다.

1.1. 표기 규칙

이 문서의 키워드 'MUST', 'MUST NOT', 'REQUIRED', 'SHALL', 'SHALL NOT', 'SHOULD', 'SHOULD NOT', 'RECOMMENDED', 'NOT RECOMMENDED', 'MAY', 'OPTIONAL'은 [RFC2119]에서 설명하는 대로 해석한다.

별도로 명시하지 않는 한, 모든 프로토콜 매개변수의 이름과 값은 대소문자를 구분한다.

1.2. 용어

이 절에서는 이 명세에서 사용하는 용어를 정의한다. 이 절은 구현이 따라야 할 요구 사항을 정하는 규범적 부분이다.

이 명세는 OAuth 2.0 [RFC6749]에서 정의한 "access token(접근 토큰)", "authorization endpoint", "authorization grant", "authorization server", "client", "client identifier", "protected resource", "refresh token(갱신 토큰)", "resource owner(리소스 소유자)", "resource server", "token endpoint(토큰 엔드포인트)"와 JSON Web Token (JWT) [RFC7519]에서 정의한 "claim names" 및 "claim values"라는 용어를 사용한다.

이 명세는 다음 용어를 정의한다.

Token Introspection
이 문서에서 정의하는 네트워크 프로토콜을 사용해 OAuth 2.0 토큰의 현재 상태를 조회하는 행위이다.
Introspection Endpoint
token introspection이 이루어지는 OAuth 2.0 endpoint다.

2. Introspection Endpoint

introspection endpoint(토큰 상태 조회 엔드포인트)는 OAuth 2.0 토큰을 나타내는 매개변수를 받아 해당 토큰이 현재 활성 상태인지 등 그 토큰에 관한 메타데이터를 담은 JSON [RFC7159] 문서를 반환하는 OAuth 2.0 endpoint이다. 활성 토큰의 정의는 authorization server에 따라 다르지만, 일반적으로 해당 authorization server가 발급했고, 만료되지 않았고, 철회되지 않았으며, introspection을 호출하는 protected resource에서 유효하게 사용할 수 있는 토큰을 뜻한다.

introspection endpoint는 4절에서 설명하는 전송 계층 보안 메커니즘으로 보호되어야 한다(MUST). protected resource가 introspection endpoint의 위치를 알아내는 방법은 이 명세의 범위에 포함되지 않는다.

2.1. Introspection 요청

protected resource는 HTTP POST [RFC7231] 요청으로 introspection endpoint를 호출하며, 매개변수는 [W3C.REC-html5-20141028]에서 정의한 "application/x-www-form-urlencoded" 데이터 형식으로 전송한다. protected resource는 토큰을 나타내는 매개변수와 함께, authorization server가 응답하는 데 도움이 되도록 자신이 알고 있는 추가 맥락을 나타내는 선택적 매개변수도 보낸다.

token
REQUIRED. 토큰의 문자열 값이다. access token의 경우 OAuth 2.0 [RFC6749] 5.1절에서 정의한 token endpoint가 반환하는 "access_token" 값이다. refresh token의 경우 OAuth 2.0 [RFC6749] 5.1절에서 정의한 token endpoint가 반환하는 "refresh_token" 값이다. 그 밖의 토큰 유형은 이 명세의 범위에 포함되지 않는다.
token_type_hint
OPTIONAL. introspection을 위해 제출된 토큰의 유형에 대한 힌트다. protected resource는 authorization server가 토큰 검색을 최적화할 수 있도록 이 매개변수를 보낼 수 있다(MAY). 서버가 주어진 힌트로 토큰을 찾지 못하면 지원하는 모든 토큰 유형으로 검색 범위를 넓혀야 한다(MUST). authorization server는 특히 토큰 유형을 자동으로 알아낼 수 있는 경우 이 매개변수를 무시할 수 있다(MAY). 이 필드의 값은 OAuth Token Revocation [RFC7009]에서 정의한 "OAuth Token Type Hints" 레지스트리에 정의되어 있다.

introspection endpoint는 질의에 추가 맥락을 제공하는 다른 선택적 매개변수를 받아들일 수 있다(MAY, OPTIONAL). 예를 들어, authorization server는 올바른 client가 토큰을 제시하고 있을 가능성을 판단하려고 protected resource에 접근하는 client의 IP 주소를 알고 싶을 수 있다. 이 매개변수나 그 밖의 매개변수를 정의하는 것은 이 명세의 범위에 포함되지 않으며, 서비스 문서 또는 이 명세의 확장에서 정의한다. authorization server가 토큰의 상태를 추가 정보 없이는 판단할 수 없다면, 2.2절에서 설명하는 대로 토큰이 활성 상태가 아님을 나타내는 introspection 응답을 반환하는 것이 권고된다(SHOULD).

토큰 스캔 공격을 방지하기 위해, 이 endpoint는 접근 시 어떤 형태로든 인가를 요구해야 한다(MUST). 예를 들어 OAuth 2.0 [RFC6749]에서 설명하는 client 인증이나 OAuth 2.0 Bearer Token Usage [RFC6750]에서 설명하는 bearer token과 같은 별도의 OAuth 2.0 access token을 요구할 수 있다. 이러한 인증 자격 증명을 관리하고 검증하는 방법은 이 명세의 범위에 포함되지 않는다.

다음 예는 protected resource가 OAuth 2.0 bearer token에 대해 질의하기 위해 token introspection endpoint를 호출하는 모습을 보여 준다. protected resource는 이 호출을 인가하기 위해 별도의 OAuth 2.0 bearer token을 사용한다.

다음은 비규범적 요청 예시다.

     POST /introspect HTTP/1.1
     Host: server.example.com
     Accept: application/json
     Content-Type: application/x-www-form-urlencoded
     Authorization: Bearer 23410913-abewfq.123483

     token=2YotnFZFEjr1zCsicMWpAA

이 예에서 protected resource는 client identifier와 client secret을 사용해 introspection endpoint에 자신을 인증한다. protected resource는 access token에 대해 질의 중임을 나타내는 토큰 유형 힌트도 보낸다.

다음은 비규범적 요청 예시다.

     POST /introspect HTTP/1.1
     Host: server.example.com
     Accept: application/json
     Content-Type: application/x-www-form-urlencoded
     Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW

     token=mF_9.B5f-4.1JqM&token_type_hint=access_token

2.2. Introspection 응답

서버는 다음 최상위 멤버를 포함하는 "application/json" 형식의 JSON 객체 [RFC7159]로 응답한다.

active
REQUIRED. 제시된 토큰이 현재 활성 상태인지 나타내는 Boolean 값이다. 토큰이 "active" 상태인지 판단하는 구체적인 기준은 authorization server의 구현과 이 서버가 토큰에 대해 보관하는 정보에 따라 달라진다. 그러나 일반적으로 "active" 속성의 반환 값이 "true"이면 해당 토큰을 이 authorization server가 발급했고, resource owner가 철회하지 않았으며, 정해진 유효 시간 범위(예: 발급 시각이 지난 뒤, 만료 시각 이전) 내에 있음을 뜻한다. 이러한 확인 절차의 구현에 대해서는 4절을 참조한다.
scope
OPTIONAL. 이 토큰에 연결된 scope를 공백으로 구분해 나열한 JSON 문자열이다. 형식은 OAuth 2.0 [RFC6749] 3.3절에서 설명한다.
client_id
OPTIONAL. 이 토큰을 요청한 OAuth 2.0 client의 client identifier이다.
username
OPTIONAL. 이 토큰을 인가한 resource owner를 사람이 읽을 수 있는 형태로 나타내는 식별자이다.
token_type
OPTIONAL. OAuth 2.0 [RFC6749] 5.1절에서 정의한 토큰의 유형이다.
exp
OPTIONAL. 이 토큰이 만료되는 시각을 나타내는 정수 타임스탬프다. JWT [RFC7519]에서 정의한 대로 UTC 기준 1월 첫날(1970년)부터 경과한 초 수로 표현한다.
iat
OPTIONAL. 이 토큰이 처음 발급된 시각을 나타내는 정수 타임스탬프다. JWT [RFC7519]에서 정의한 대로 UTC 기준 1월 첫날(1970년)부터 경과한 초 수로 표현한다.
nbf
OPTIONAL. 그 시각 전에는 토큰을 사용해서는 안 된다는 것을 나타내는 정수 타임스탬프다. JWT [RFC7519]에서 정의한 대로 UTC 기준 1월 첫날(1970년)부터 경과한 초 수로 표현한다.
sub
OPTIONAL. JWT [RFC7519]에서 정의하는 토큰의 subject이다. 일반적으로 이 토큰을 인가한 resource owner의 기계 판독용 식별자이다.
aud
OPTIONAL. JWT [RFC7519]에서 정의하는 바에 따라 이 토큰의 사용 대상으로 지정된 audience를 나타내는 서비스별 문자열 식별자 또는 문자열 식별자 목록이다.
iss
OPTIONAL. JWT [RFC7519]에서 정의하는 바에 따라 이 토큰의 발급자를 나타내는 문자열이다.
jti
OPTIONAL. JWT [RFC7519]에서 정의하는 토큰의 문자열 식별자이다.

개별 구현은 자체 서비스 전용 응답 이름을 이 JSON 객체의 최상위 멤버로 추가하여 이 구조를 확장할 수 있다(MAY). 여러 도메인에 걸쳐 사용할 응답 이름은 3.1절에서 정의하는 "OAuth Token Introspection Response" 레지스트리에 등록해야 한다(MUST).

authorization server는 서로 다른 protected resource가 동일한 요청을 하더라도 각각 다르게 응답할 수 있다(MAY). 예를 들어, protected resource가 동작에 필요한 것 이상으로 전체 네트워크에 관한 정보를 알아내지 못하게 하려면, authorization server는 주어진 토큰의 scope 중 어떤 것을 반환할지 protected resource마다 제한할 수 있다(MAY).

protected resource는 성능을 높이고 introspection endpoint의 부하를 줄이기 위해 응답을 캐시할 수 있다(MAY). 다만 그렇게 하면 protected resource가 인가 결정에 사용하는 정보의 최신성이 떨어진다. 응답을 캐시할 때의 이점과 비용에 대해서는 4절을 참조한다.

예를 들어, 다음 응답에는 활성 토큰에 관한 일련의 정보가 담겨 있다.

다음은 비규범적 응답 예시다.

     HTTP/1.1 200 OK
     Content-Type: application/json

     {
      "active": true,
      "client_id": "l238j323ds-23ij4",
      "username": "jdoe",
      "scope": "read write dolphin",
      "sub": "Z5O3upPC88QrAjx00dis",
      "aud": "https://protected.example.net/resource",
      "iss": "https://server.example.com/",
      "exp": 1419356238,
      "iat": 1419350238,
      "extension_field": "twenty-seven"
     }

introspection 호출은 적절히 인가되었지만 토큰이 활성 상태가 아니거나, 이 서버에 존재하지 않거나, protected resource에 해당 토큰의 introspection이 허용되지 않았다면, authorization server는 "active" 필드를 "false"로 설정한 introspection 응답을 반환해야 한다(MUST). authorization server의 상태가 제삼자에게 지나치게 많이 노출되지 않도록, authorization server는 토큰이 비활성 상태인 이유를 비롯하여 비활성 토큰에 관한 어떤 추가 정보도 포함하지 않는 것이 권고된다(SHOULD NOT).

다음은 철회되었거나 그 밖의 이유로 유효하지 않은 토큰에 대한 비규범적 응답 예시다.

     HTTP/1.1 200 OK
     Content-Type: application/json

     {
      "active": false
     }

2.3. 오류 응답

protected resource가 OAuth 2.0 client 자격 증명으로 introspection endpoint에 인증을 시도했는데 그 자격 증명이 유효하지 않다면, authorization server는 OAuth 2.0 [RFC6749] 5.2절에서 설명하는 대로 HTTP 401 (Unauthorized)로 응답한다.

protected resource가 OAuth 2.0 bearer token으로 introspection endpoint에 대한 호출을 인가하고, 인가에 사용한 토큰에 충분한 권한이 없거나 그 밖의 이유로 해당 요청에 유효하지 않다면, authorization server는 OAuth 2.0 Bearer Token Usage [RFC6750] 3절에서 설명하는 대로 HTTP 401 상태 코드로 응답한다.

비활성 상태이거나 그 밖의 이유로 유효하지 않은 토큰(또는 protected resource가 알도록 허용되지 않은 토큰)에 관한 질의의 형식이 올바르고 적절히 인가되었다면, 이 명세에서는 이를 오류 응답의 대상으로 보지 않는다. 이 경우 authorization server는 대신 2.2절에서 설명하는 대로 "active" 필드를 "false"로 설정한 introspection 응답을 반환해야 한다(MUST).

3. IANA 고려 사항

3.1. OAuth Token Introspection Response 레지스트리

이 명세는 “OAuth Token Introspection Response” 레지스트리를 신설한다.

OAuth 등록용 client 메타데이터의 이름과 설명은 한 명 이상의 Designated Expert(지정 전문가)의 자문에 따라 oauth-ext-review@ietf.org 메일링 리스트에서 두 주 동안 검토를 거쳐 Specification Required [RFC5226] 절차로 등록한다. 다만 발행 전에 이름을 배정할 수 있도록, Designated Expert는 그러한 명세가 발행될 것이라고 판단하면 등록을 승인할 수 있다.

검토를 위해 메일링 리스트에 보내는 등록 요청에는 적절한 제목을 사용하는 것이 바람직하다(예: “Request to register OAuth Token Introspection Response name: example”).

Designated Expert는 검토 기간 내에 등록 요청을 승인하거나 거부하고, 그 결정을 검토용 메일링 리스트와 IANA에 알린다. 거부할 때는 이유를 설명하고, 해당하는 경우 요청이 승인되려면 어떻게 해야 하는지 제안하는 것이 바람직하다.

IANA는 Designated Expert가 보낸 레지스트리 변경 사항만 접수해야 하며, 모든 등록 요청은 검토용 메일링 리스트로 보내도록 안내하는 것이 바람직하다.

3.1.1. 등록 양식

이름:
등록을 요청하는 이름(예: “example”). 이 이름은 대소문자를 구분한다. 대소문자를 무시했을 때 이미 등록된 다른 이름과 일치하는 이름은 접수하지 않는 것이 바람직하다(SHOULD NOT). [RFC7519]에서 신설한 “JSON Web Token Claims” 레지스트리에 등록된 Claim과 일치하는 이름은 정의와 의미가 해당 Claim과 유사한 것이 바람직하다(SHOULD).
설명:
메타데이터 값에 대한 간략한 설명(예: “설명 예시”).
변경 관리 주체:
Standards Track RFC에는 “IESG”라고 기재한다. 그 밖의 문서에는 책임 주체의 이름을 기재한다. 우편 주소, 이메일 주소, 홈페이지 URI 등의 세부 정보도 포함할 수 있다.
명세 문서:
token endpoint의 인가 방식을 명시한 문서에 대한 참조. 가능하면 문서 사본을 가져오는 데 사용할 수 있는 URI를 포함한다. 관련 절을 표시할 수도 있지만 필수는 아니다.

4. 보안 고려 사항

OAuth 2.0 시스템을 구현하는 타당한 방식이 여러 가지이므로, authorization server가 토큰이 현재 “활성” 상태인지 판단하는 방식도 여러 가지다. 그러나 token introspection을 사용하는 resource server는 토큰 상태 판단을 authorization server에 의존하므로, authorization server는 토큰 상태에 적용되는 모든 검사를 수행해야 한다(MUST). 예를 들어 다음과 같은 검사가 있다:

o 토큰이 만료될 수 있다면 authorization server는 토큰이 만료되었는지 판단해야 한다(MUST).

o 토큰을 사용 가능 시점보다 먼저 발급할 수 있다면 authorization server는 토큰의 유효 기간이 이미 시작되었는지 판단해야 한다(MUST).

o 발급 후 토큰을 철회할 수 있다면 authorization server는 실제로 철회되었는지 판단해야 한다(MUST).

o 토큰이 서명되었다면 authorization server는 그 서명을 검증해야 한다(MUST).

o 토큰을 특정 resource server에서만 사용할 수 있다면 authorization server는 introspection을 요청하는 resource server에서 해당 토큰을 사용할 수 있는지 판단해야 한다(MUST).

authorization server가 적용해야 할 검사 중 하나라도 수행하지 않으면, resource server는 그 응답을 근거로 잘못된 보안 판단을 내릴 수 있다. 위의 검사가 모든 OAuth 2.0 배포 환경에 적용되는 것은 아니며, 이들 검사와 그 밖의 검사 중 무엇이 적용되는지는 authorization server가 판단한다.

introspection endpoint를 보호하지도 않고 호출 빈도도 제한하지 않으면 공격자가 토큰 후보 값을 하나씩 조회해 유효한 토큰을 찾아내는 데 이 endpoint를 이용할 수 있다. 이를 방지하려면 authorization server는 introspection endpoint에 접근해야 하는 protected resource에 인증을 요구해야 하며(MUST), protected resource가 introspection endpoint를 호출할 권한을 별도로 부여받도록 요구하는 것이 바람직하다(SHOULD). 이러한 인증 자격 증명의 세부 사항은 이 명세의 범위를 벗어나지만, 일반적으로 token endpoint에 쓰이는 유효한 client 인증 메커니즘, OAuth 2.0 access token 또는 그 밖의 HTTP 인가·인증 메커니즘을 사용할 수 있다. 하나의 소프트웨어가 client와 protected resource 역할을 모두 수행하는 경우, token endpoint와 introspection endpoint에 동일한 자격 증명을 재사용할 수 있다(MAY). 다만 이렇게 하면 소프트웨어에서 client 역할을 하는 부분과 protected resource 역할을 하는 부분의 활동이 구분되지 않을 수 있으며, authorization server는 각 역할에 별도의 자격 증명을 요구할 수 있다(MAY).

introspection endpoint는 OAuth 2.0 토큰을 매개변수로 받아 인가 결정에 쓰이는 정보를 응답으로 반환하므로, 서버는 Transport Layer Security (TLS) 1.2 [RFC5246]를 지원해야 한다(MUST). 또한 서버의 보안 요구사항을 충족하는 다른 전송 계층 메커니즘을 추가로 지원할 수 있다(MAY). TLS를 사용할 때 client 또는 protected resource는 [RFC6125]에 따라 TLS/SSL 서버 인증서를 검증해야 한다(MUST). 구현 시 고려할 보안 사항은 Recommendations for Secure Use of TLS and DTLS [BCP195]에서 확인할 수 있다.

access token 값이 쿼리 매개변수를 통해 서버 측 로그에 유출되는 일을 방지하기 위해, token introspection을 제공하는 authorization server는 introspection endpoint에서 HTTP GET을 금지하고 그 대신 HTTP POST 메서드를 사용하도록 요구할 수 있다(MAY).

authorization server의 내부 상태가 노출되지 않도록, 비활성 토큰에 대한 introspection 응답에는 필수인 “active” Claim(값은 “false”로 설정) 외에 다른 Claim을 포함하지 않는 것이 바람직하다(SHOULD NOT).

protected resource는 introspection endpoint의 응답을 캐시할 수 있으므로(MAY), 이 프로토콜을 사용하는 OAuth 2.0 시스템의 설계자는 이러한 보안 정보를 캐시할 때 성능과 보안 사이에 생기는 상충 관계를 고려해야 한다(MUST). 캐시 유지 시간을 짧게 잡으면 protected resource가 introspection endpoint에 더 자주 조회해야 하므로 더 최신 정보를 얻지만, 네트워크 트래픽과 introspection endpoint의 부하는 증가한다. 캐시를 더 적극적으로 사용해 유지 시간을 길게 잡으면 네트워크 트래픽과 introspection endpoint의 부하는 최소화되지만, 토큰에 관한 정보가 오래된 상태로 남을 위험이 있다. 예를 들어 protected resource가 캐시된 응답 값에 의존해 인가 결정을 내리는 동안 토큰이 철회될 수 있다. 그러면 철회된 토큰을 protected resource에서 여전히 사용할 수 있는 시간 구간이 생긴다. 따라서 접근 대상인 protected resource와 관련된 우려와 그 민감도, 그리고 캐시가 유효한 동안 토큰이 철회되거나 무효화될 가능성을 고려해 허용 가능한 캐시 유효 기간을 신중하게 정해야 한다. 민감도가 매우 높은 환경에서는 protected resource에서 캐시를 아예 비활성화해 오래된 캐시 정보를 사용할 위험을 완전히 없애는 방법을 선택할 수 있다. 이 경우에도 네트워크 트래픽과 서버 부하가 증가한다. 만약 응답에 “exp” 매개변수(만료)가 포함되어 있다면, 응답을 그 값이 나타내는 시각 이후까지 캐시해서는 안 된다(MUST NOT).

token introspection을 제공하는 authorization server는 이 호출에서 자신에게 제시되는 토큰 값을 해석할 수 있어야 한다. 이를 수행하는 구체적인 방식은 구현 세부 사항으로, 이 명세의 범위를 벗어난다. 비정형 토큰이라면 토큰의 맥락 정보가 들어 있는 데이터 저장소에 대해 서버 측에서 간단한 데이터베이스 조회를 수행할 수 있다. 구조화된 토큰이라면 서버가 토큰을 파싱하고 서명이나 그 밖의 보호 메커니즘을 검증한 뒤 토큰에 담긴 정보를 protected resource에 돌려줄 수 있다. 이렇게 하면 client와 마찬가지로 protected resource도 토큰의 내용을 직접 알 필요가 없다. introspection 과정에 필요한 정보가 토큰에 암호화되어 있다면, authorization server는 그 정보에 접근하기 위해 토큰을 복호화하고 검증할 수 있어야 한다. 또한 authorization server가 토큰에 관한 정보를 저장하지도 않고 토큰 자체를 파싱해 그 정보에 접근할 수도 없다면, introspection 서비스를 제공하기 어려울 것이다.

5. 프라이버시 고려 사항

introspection 응답에는 resource owner의 사용자 식별자처럼 개인정보 보호에 민감한 정보가 포함될 수 있다. 이 경우 해당 정보가 공개 대상이 아닌 사람이나 조직에 노출되지 않도록 조치를 취해야 한다(MUST). 한 가지 방법은 사용자 식별자를 내부 의미를 알 수 없는 서비스별 문자열로 전송하는 것이다. 이때 protected resource마다 다른 식별자를 반환할 수 있다.

protected resource가 이 명세의 확장을 사용해 client 요청에 관한 추가 정보(예: client의 IP 주소)를 authorization server에 보내는 경우, 해당 정보와 관련해 개인정보 보호 측면에서 추가로 고려할 사항이 생길 수 있으며, 그 확장에서 이를 자세히 설명하는 것이 바람직하다. 다만 이러한 확장의 성격과 그에 따른 영향은 이 명세의 범위에 속하지 않는다.

개인정보 보호 문제를 최소화하는 가장 간단한 방법은 introspection 응답에 개인정보 보호에 민감한 정보를 넣지 않는 것이다.

6.2. 참고용 문헌

   [BCP195]   Sheffer, Y., Holz, R., and P. Saint-Andre,
              "Recommendations for Secure Use of Transport Layer
              Security (TLS) and Datagram Transport Layer Security
              (DTLS)", BCP 195, RFC 7525, May 2015,
              <http://www.rfc-editor.org/info/bcp195>.

부록 A. proof-of-possession token과 함께 사용하기

OAuth 2.0 Bearer Token Usage [RFC6750]에서 정의하는 것과 같은 bearer token의 경우, protected resource는 introspection 서비스에 제출할 수 있도록 토큰의 비밀 부분 전체를 보유한다. 반면 proof-of-possession 방식의 토큰이라면 protected resource가 갖는 것은 요청에 사용된 토큰 식별자와 해당 요청의 암호학적 서명뿐이다. 이 요청의 서명을 검증하기 위해 protected resource는 토큰 식별자를 authorization server의 introspection endpoint에 제출하여 해당 토큰에 필요한 키 정보를 얻을 수 있을 것이다. 이 사용 방식의 세부 사항은 이 명세의 범위에 속하지 않으며, proof-of-possession token의 정의와 연계하여 이 명세의 확장에서 규정할 것이다.

이 문서에 의견을 주고 검토해 준 OAuth Working Group과 User Managed Access Working Group, 그리고 이 명세의 client 및 server 구성 요소를 구현한 여러 분께 감사드린다. 저자는 특히 Amanda Anganes, John Bradley, Thomas Broyer, Brian Campbell, George Fletcher, Paul Freemantle, Thomas Hardjono, Eve Maler, Josh Mandel, Steve Moore, Mike Schwartz, Prabath Siriwardena, Sarah Squire, Hannes Tschofennig에게 감사드린다.
