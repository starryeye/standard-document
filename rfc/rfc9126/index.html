초록

이 문서는 client가 직접 요청을 통해 OAuth 2.0 인가 요청의 페이로드를 authorization server(인가 서버)에 미리 전송할 수 있게 하는 PAR endpoint(인가 요청 사전 전송 엔드포인트)를 정의한다. 이 endpoint는 client에 request URI를 제공하며, client는 이후 authorization endpoint(인가 엔드포인트)를 호출할 때 이 URI로 해당 데이터를 참조한다.¶

1. 소개

이 문서는 OAuth [RFC6749] client가 인가 요청의 페이로드를 authorization server에 직접 전송할 수 있게 하는 PAR endpoint를 정의한다. 그 응답으로 받은 request URI 값은 이후 user agent(사용자 에이전트)를 통해 authorization endpoint를 호출할 때 인가 요청 페이로드 데이터를 가리키는 참조로 사용한다.¶

OAuth [RFC6749]에서는 일반적으로 user agent에서 리디렉션을 통해 인가 요청 매개변수를 URI 쿼리 매개변수로 전송한다. 이 방식은 간단하지만 다음과 같은 문제가 있다.¶

  • 무결성과 진정성을 암호학적으로 보호하지 않는다. 예를 들어 공격자는 scope 값을 바꿔 요청된 접근 범위를 변경하거나 결제 거래의 맥락을 바꿔치기할 수 있다. client나 사용자가 이런 변경 중 일부를 감지할 수 있도록 프로토콜에서 제공하는 기능이 있지만, 절차의 초기 단계에서 변경 자체를 막는 편이 더 확실하다.¶
  • 요청 매개변수의 기밀성을 보장하는 장치가 없다. authorization endpoint에는 HTTPS가 필수지만, 요청 데이터는 평문 상태로 user agent를 거친다. 이때 쿼리 문자열 데이터가 웹 서버 로그에 남거나 referrer를 통해 다른 사이트로 뜻하지 않게 유출될 수 있다. 인가 요청에 개인 식별 정보나 그 밖의 규제 대상 데이터가 포함되면 이러한 유출의 영향은 클 수 있다. 신원 확인, 오픈 뱅킹 및 이와 유사한 시나리오에서는 실제로 그런 데이터가 포함될 가능성이 높다.¶
  • 인가 요청 URL이 상당히 길어질 수 있으며, 특히 세분화된 인가 데이터가 필요한 시나리오에서는 이 때문에 요청 처리 오류가 발생할 수 있다.¶

JWT-Secured Authorization Request(JAR) [RFC9101]는 OAuth client가 인가 요청 매개변수를 Request Object에 담을 수 있게 해 보안 문제를 해결한다. Request Object는 서명된 JSON Web Token(JWT) [RFC7519]으로, 선택적으로 암호화할 수 있다. JAR는 크기 제한에 대응하기 위해 client가 Request Object 자체 대신 이를 가리키는 참조를 보낼 수 있도록 request_uri 매개변수를 도입한다.¶

이 문서는 인가 요청의 페이로드를 authorization server에 직접 전송하고, 이후 인가 요청에서 authorization server에 사용할 수 있는 request_uri 값을 받는 상호 운용 가능한 방식을 제공해 JAR를 보완한다.¶

PAR는 client가 인가 요청의 기밀성과 무결성을 간편하게 보호할 수 있게 하여 OAuth의 보안을 강화한다. 더 높은 수준의 보안, 특히 암호학적으로 검증된 부인 방지가 필요한 client는 [RFC9101]에 정의된 JWT 기반 Request Object를 PAR와 함께 사용할 수 있다.¶

PAR를 사용하면 authorization server는 사용자가 관여하기 전에 client를 인증할 수 있다. 인가 과정에서 client의 신원을 더 확실히 확인할 수 있으므로 authorization server는 정당하지 않은 요청을 훨씬 더 일찍 거부할 수 있다. 이를 통해 client를 사칭하거나 인가 요청을 변조 또는 악용하려는 시도를 막을 수 있다.¶

user agent를 통해 authorization endpoint에 HTTP POST 요청을 보내는 방법도 앞서 설명한 요청 크기 제한에 대응하는 데 사용할 수 있다. 이 방법은 3.1절 ([RFC6749]) 및 [OIDC]의 3.1.2.1절에 나와 있다. 다만 [RFC6749]에서 이 방법은 선택 사항일 뿐이다. 지원되는 경우에도 일반적인 웹 애플리케이션에서는 쓸 만하지만, 설치형 모바일 애플리케이션에서 쓰기에는 지나치게 어렵다. [RFC8252]에 설명된 대로, 이러한 앱은 플랫폼별 API를 사용해 시스템 브라우저에서 인가 요청 URI를 연다. 그러나 모바일 앱이 브라우저를 실행하면 그에 따른 첫 요청에는 GET 메서드만 사용할 수 있다. 인가 요청에 POST를 쓰려면, 우선 앱이 제어하는 URI를 브라우저에서 GET로 열도록 하면서 큰 인가 요청 페이로드를 어떻게든 전달해야 한다. 그 응답에는 authorization server로 교차 사이트 폼 POST 요청을 시작하는 데 필요한 콘텐츠와 스크립트가 들어 있어야 한다. PAR는 사용하기가 더 간단하며, 위에서 설명한 추가 보안 이점도 제공한다.¶

1.1. 도입 예제

기존 OAuth 2.0에서는 일반적으로 client가 user agent로 하여금 authorization server의 authorization endpoint에 다음과 같은 HTTP 요청을 보내게 하여 인가 요청을 시작한다(추가 줄바꿈과 들여쓰기는 표시용일 뿐이다).¶

 GET /authorize?response_type=code
  &client_id=CLIENT1234&state=duk681S8n00GsJpe7n9boxdzen
  &redirect_uri=https%3A%2F%2Fclient.example.org%2Fcb HTTP/1.1
 Host: as.example.com
¶

대신 client는 다음 예와 같이 PAR endpoint로 POST 요청을 보내는 방식으로 인가 요청을 authorization server에 직접 전송할 수 있다(추가 줄바꿈과 공백은 표시용일 뿐이다). 요청이 authorization server로 직접 전달되므로 client는 자신을 인증할 수 있다(예를 들어 아래와 같이 JWT client assertion 기반 인증을 사용할 수 있다).¶

 POST /as/par HTTP/1.1
 Host: as.example.com
 Content-Type: application/x-www-form-urlencoded

 &response_type=code
 &client_id=CLIENT1234&state=duk681S8n00GsJpe7n9boxdzen
 &redirect_uri=https%3A%2F%2Fclient.example.org%2Fcb
 &client_assertion_type=
  urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer
 &client_assertion=eyJraWQiOiI0MiIsImFsZyI6IkVTMjU2In0.eyJpc3MiOiJDTE
  lFTlQxMjM0Iiwic3ViIjoiQ0xJRU5UMTIzNCIsImF1ZCI6Imh0dHBzOi8vc2VydmVyL
  mV4YW1wbGUuY29tIiwiZXhwIjoxNjI1ODY4ODc4fQ.Igw8QrpAWRNPDGoWGRmJumLBM
  wbLjeIYwqWUu-ywgvvufl_0sQJftNs3bzjIrP0BV9rRG-3eI1Ksh0kQ1CwvzA
¶

authorization server는 request URI를 응답으로 반환한다.¶

 HTTP/1.1 201 Created
 Cache-Control: no-cache, no-store
 Content-Type: application/json

 {
   "request_uri": "urn:example:bwc4JK-ESC0w8acc191e-Y1LTC2",
   "expires_in": 90
 }
¶

client는 request URI 값을 사용해 후속 인가 요청을 만든다. 이를 위해 user agent로 하여금 authorization server의 authorization endpoint에 다음과 같은 HTTP 요청을 보내게 한다(추가 줄바꿈과 들여쓰기는 표시용일 뿐이다).¶

 GET /authorize?client_id=CLIENT1234
  &request_uri=urn%3Aexample%3Abwc4JK-ESC0w8acc191e-Y1LTC2 HTTP/1.1
 Host: as.example.com
¶

1.2. 표기 규칙과 용어

이 문서의 핵심어 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY" 및 "OPTIONAL"은 여기에서와 같이 모두 대문자로 표기된 경우에만 BCP 14 [RFC2119] [RFC8174]에 명시된 대로 해석한다.¶

이 명세는 "The OAuth 2.0 Authorization Framework" [RFC6749]에서 정의한 "access token", "authorization server", "authorization endpoint", "authorization request", "token endpoint(토큰 발급 엔드포인트)", "client"라는 용어를 사용한다.¶

2. PAR endpoint

PAR endpoint는 authorization server의 HTTP API다. 이 API는 HTTP POST 요청을 받으며, 요청 메시지 본문의 매개변수는 application/x-www-form-urlencoded 형식을 따른다. 이 형식은 부록 B ([RFC6749])에 설명된 대로 문자 인코딩에 UTF-8을 사용한다. PAR endpoint URL은 반드시(MUST) "https" 스킴을 사용해야 한다.¶

PAR를 지원하는 authorization server에는 다음이 권장된다(SHOULD). 자체 PAR endpoint의 URL을 authorization server 메타데이터 문서 [RFC8414]에 포함하되, pushed_authorization_request_endpoint 매개변수를 사용한다. 이 매개변수는 5절에서 정의한다.¶

이 endpoint는 [RFC6749]에 정의된 authorization endpoint용 인가 요청 매개변수뿐 아니라 authorization endpoint에 대해 정의된 모든 적용 가능한 확장도 받는다. 이러한 확장의 예로는 Proof Key for Code Exchange(PKCE) [RFC7636], Resource Indicators [RFC8707], OpenID Connect(OIDC) [OIDC]가 있다. 또한 이 endpoint는 선택 사항으로(MAY) [RFC9101] 및 이 문서의 3절에 따라 인가 요청 매개변수 전체를 Request Object로 전송하는 방식도 지원할 수 있다.¶

[RFC6749]가 token endpoint 요청에 대해 정의한 client authentication(클라이언트 인증) 규칙은 적용 가능한 인증 방법을 포함하여 PAR endpoint에도 적용된다. 해당되는 경우 client 메타데이터 매개변수 token_endpoint_auth_method [RFC7591]는 client가 PAR endpoint 요청을 비롯해 authorization server에 직접 요청을 보낼 때 사용할 등록된 인증 방법을 나타낸다. 마찬가지로 authorization server 메타데이터 매개변수 token_endpoint_auth_methods_supported [RFC8414]는 PAR endpoint 요청을 비롯해 client의 직접 요청을 받을 때 authorization server가 지원하는 client authentication 방법을 나열한다.¶

2026년 표준 업데이트 · 번역자 안내

아래 문단은 2021년 발행본의 규정입니다. RFC 10070 §5에 따라 PAR endpoint에서 JWT client assertion으로 인증할 때는 authorization server의 issuer identifier URL만 aud 값으로 사용해야 합니다. token endpoint나 PAR endpoint URL로 대체할 수 없으며, issuer identifier를 유일한 값으로 담지 않은 JWT는 서버가 거부해야 합니다.

RFC 10070 §5 한국어판 · 공식 영문

역사적인 이유로 JWT client assertion 기반 인증에 어떤 audience(의도된 수신자) 값을 사용해야 하는지가 모호할 수 있다. 이 인증은 2.2절 ([RFC7523])에 정의되어 있으며, 인증 방법 이름으로 private_key_jwt 또는 client_secret_jwt를 사용한다([OIDC] 9절 참조). 이러한 모호성을 해소하기 위해 [RFC8414]에 따른 authorization server의 issuer identifier(발급자 식별자) URL을 audience 값으로 사용하는 것이 권장된다(SHOULD). 상호 운용성을 높이기 위해 authorization server는 자신의 issuer identifier, token endpoint URL, PAR endpoint URL 중 어느 것이든 자신이 의도된 audience임을 나타내는 값으로 받아들여야 한다(MUST).¶

2.1. 요청

client는 인가 요청을 구성하는 매개변수를 PAR endpoint에 직접 보낸다. 일반적인 매개변수 집합에는 아래 예와 같이 client_id, response_type, redirect_uri, scope, state, code_challenge 및 code_challenge_method가 포함될 수 있다. 다만 이 방식으로 전송하는 인가 요청은 [RFC6749]과 적용 가능한 모든 확장에 정의된 매개변수를 포함해 authorization endpoint에서 사용할 수 있는 매개변수라면 어느 것이든 사용해 구성할 수 있다. 인가 요청 매개변수 request_uri는 한 가지 예외로, 제공해서는 안 된다(MUST NOT).¶

요청에는 해당 client의 client authentication에 필요한 추가 매개변수도 적절히 포함한다(예: client_secret 또는 client_assertion과 client_assertion_type). 이러한 매개변수는 token endpoint에서 사용하도록 정의 및 등록되어 있지만, client authentication에만 적용된다. 사전 전송된 인가 요청에 이러한 매개변수가 포함되어 있으면 client authentication에만 사용하며, 인가 요청 자체와는 관계가 없다. client authentication과 무관한 token endpoint 매개변수에는 사전 전송된 인가 요청에서의 의미가 정의되어 있지 않다. client_id 매개변수는 인가 요청과 token endpoint 요청 모두에서 같은 의미로 정의된다. 인가 요청의 필수 매개변수이므로 사전 전송된 인가 요청에서도 필수다.¶

client는 UTF-8 문자 인코딩을 사용해 HTTP POST 요청의 메시지 본문을 x-www-form-urlencoded 형식에 맞춘 매개변수로 구성한다. 이 형식은 부록 B([RFC6749])에서 설명한다. 해당하는 경우에는 token endpoint 요청에 적용하는 것과 같은 규칙에 따라 요청 헤더나 본문에 자신의 인증 자격 증명도 추가한다.¶

authorization server는 요청을 다음과 같이 처리해야 한다(MUST):¶

  1. token endpoint에서와 같은 방식으로 client를 인증한다(2.3절([RFC6749])).¶
  2. 인가 요청 매개변수 request_uri가 주어지면 요청을 거부한다.¶
  3. 사전 전송된 요청을 authorization endpoint로 전송된 인가 요청과 같은 방식으로 검증한다. 예를 들어 authorization server는 redirect URI가 해당 client에 설정된 redirect URI 중 하나와 일치하는지, 그리고 client가 접근을 요청하는 scope에 대한 권한이 있는지 확인한다. 이 검증을 통해 authorization server는 권한이 없거나 부정한 요청을 일찍 거부할 수 있다. authorization server는 사전 전송된 요청을 처리할 때 수행할 수 없는 검증 단계는 생략할 수 있다(MAY). 다만 생략한 검증은 이후 authorization endpoint에서 인가 요청을 처리할 때 수행해야 한다(MUST).¶

authorization server는 인증 자격 증명이 있는 client가 인가 요청을 사전 전송할 때마다 그 인가 요청에 사용할 redirect URI를 정할 수 있도록 허용할 수 있다(MAY). 2.4절에서 더 자세히 설명하듯, 이는 [RFC6749]과 달리 이 명세에서는 실제 인가 요청이 이루어지기 전에 authorization server가 client를 인증하고 client의 요청을 검증할 수 있기 때문이다.¶

2.2. 성공 응답

검증이 성공하면 서버는 반드시(MUST) request URI를 생성하고 HTTP 상태 코드 201에 해당하는 응답에 이를 포함한다. 다음 매개변수는 application/json 미디어 유형의 HTTP 응답 메시지 본문에 최상위 멤버로 포함된다. 이 미디어 유형은 [RFC8259]에서 정의한다.¶

request_uri
POST로 전송한 인가 요청에 대응하는 request URI다. 이후의 인가 요청에서 이 URI는 해당 요청 데이터를 가리키는 일회용 참조로 쓰인다. 인가 절차에서 인가 요청 데이터를 가져오는 방식은 authorization server의 재량에 따르며 이 명세의 범위를 벗어난다. 이 URI를 통해 다른 당사자가 인가 요청 데이터에 접근할 수 있도록 할 필요는 없다.¶
expires_in
request URI의 유효 기간을 초 단위의 양의 정수로 나타내는 JSON 숫자다. request URI의 유효 기간은 authorization server의 재량에 따르지만 일반적으로 비교적 짧다(예: 5초에서 600초 사이).¶

request_uri 값의 형식은 authorization server의 재량에 따르지만, 유효한 값을 예측하거나 추측하는 것이 계산상 현실적으로 불가능하도록 암호학적으로 강력한 의사난수 알고리즘으로 생성한 부분이 포함되어야 한다(MUST). 자세한 내용은 10.10절([RFC6749])을 참조한다. authorization server는 재량에 따라(MAY) request_uri 값을 urn:ietf:params:oauth:request_uri:<reference-value> 형식으로 구성할 수 있다. 이때 <reference-value>는 해당 인가 요청 데이터를 가리키는 URI의 난수 부분이다.¶

request_uri 값은 그 인가 요청을 POST로 전송한 client에 바인딩되어야 한다(MUST).¶

다음은 이러한 응답의 예다.¶

 HTTP/1.1 201 Created
 Content-Type: application/json
 Cache-Control: no-cache, no-store

 {
  "request_uri":
    "urn:ietf:params:oauth:request_uri:6esc_11ACC5bwc014ltc14eY22c",
  "expires_in": 60
 }
¶

2.3. 오류 응답

authorization server는 5.2절([RFC6749])에서 token endpoint 오류 응답에 대해 명시한 것과 같은 형식으로 오류 응답을 반환한다. 오류 코드는 그 절 또는 4.1.2.1절([RFC6749])에서 적절한 것을 사용한다. 4.1.2.1절([RFC6749])에서 오류와 함께 요청한 client로 자동 리디렉션하는 것을 금지하여 오류 코드를 정의하지 않은 경우(예: redirect URI가 누락되었거나 유효하지 않거나 일치하지 않아 요청이 실패한 경우)에는 invalid_request를 기본 오류 코드로 사용할 수 있다. 사전 전송된 인가 요청의 초기 처리에 OAuth 확장이 관여하는 경우에는 그 확장에서 정의한 오류 코드도 사용할 수 있다. 사전 전송된 인가 요청의 초기 처리에는 resource owner와의 상호작용이 없으므로, consent_required([OIDC]에서 정의)처럼 사용자와의 상호작용에 관련된 오류 코드는 반환하지 않는다.¶

authorization server나 client 정책에 따라 client가 서명된 Request Object를 사용해야 한다면([RFC9101], 10.5절 참조), authorization server는 반드시(MUST) 3절의 정의를 따르는 요청만 수락한다. 그 밖의 요청은 반드시(MUST) HTTP 상태 코드 400과 오류 코드 invalid_request를 사용해 거부한다.¶

위에서 설명한 코드 외에 PAR endpoint는 다음 HTTP 상태 코드도 사용할 수 있다.¶

405:
요청에 POST 메서드를 사용하지 않았다면 authorization server는 HTTP 405 (Method Not Allowed) 상태 코드로 응답한다.¶
413:
요청 크기가 authorization server에서 허용하는 상한을 초과했다면 authorization server는 HTTP 413 (Payload Too Large) 상태 코드로 응답한다.¶
429:
특정 기간에 한 client가 보낸 요청 수가 authorization server에서 허용하는 수를 초과하면 authorization server는 HTTP 429 (Too Many Requests) 상태 코드로 응답한다.¶

다음은 PAR endpoint가 반환하는 오류 응답의 예다.¶

 HTTP/1.1 400 Bad Request
 Content-Type: application/json
 Cache-Control: no-cache, no-store

 {
   "error": "invalid_request",
   "error_description":
     "The redirect_uri is not valid for the given client"
 }
¶

2.4. client redirect URI 관리

OAuth 2.0 [RFC6749]에서는 특정 상황에서 client가 등록되지 않은 redirect_uri 값을 사용하거나, authorization server가 authorization endpoint에 제시된 client의 redirect_uri 값에 자체 일치 판정 규칙을 적용할 수 있다. 하지만 OAuth 보안 BCP [OAUTH-SECURITY-TOPICS]와 OAuth 2.1 명세 [OAUTH-V2]은 모두 authorization server가 redirect_uri 매개변수를 특정 client에 대해 미리 설정한 redirect URI 중 하나와 정확히 일치하는지 확인하도록 요구한다. 이 방식은 client 사칭 시도를 조기에 탐지하고 토큰 유출과 open redirection을 방지한다. 다만 redirect URI는 일반적으로 client 정책에서 가장 자주 바뀌는 부분이므로, 이 방식 때문에 client 관리가 더 번거로워질 수 있다.¶

authorization server와 인증 자격 증명을 설정한 client가 PAR을 사용하는 경우에는 정확히 일치해야 한다는 요구 사항을 완화할 수 있다(MAY). 이는 일반적인 인가 요청과 달리 authorization server가 인가 절차를 시작하기 전에 client를 인증하므로, 적법한 client와 통신 중임을 확인할 수 있기 때문이다. authorization server는 재량에 따라(MAY) 이러한 client가 authorization server에 이전에 등록되지 않은 redirect_uri 값을 지정하도록 허용할 수 있다. 이렇게 하면 client의 유연성이 높아지고(예: 실행 중에 authorization server별로 서로 다른 redirect_uri 값을 생성할 수 있다) client 관리도 간소화될 수 있다. 제공된 redirect_uri 값에 제한을 적용할지는 authorization server의 재량에 따른다. 예를 들어 authorization server는 특정 URI 접두사를 요구하거나, 실행 중에는 쿼리 매개변수만 바꿀 수 있게 할 수 있다(MAY).¶

참고: 트랜잭션별로 redirect URI를 설정할 수 있으면 신뢰할 수 있는 제3자가 client ID와 그에 해당하는 자격 증명 및 정책을 관리하는 상황에서도 유용하다. 그 예로는 client 권한이 포함된 client 인증서를 통한 관리가 있다. 이렇게 외부에서 관리되는 client는 별도의 등록 단계 없이도 해당 제3자를 신뢰하는 authorization server와 통신할 수 있다.¶

4. 인가 요청

client는 authorization server가 반환한 request_uri 값을 사용하여 [RFC9101]에 정의된 방식으로 인가 요청을 구성한다. 다음 예제에서는 client가 user agent에 아래 HTTP 요청을 보내도록 지시하는 모습을 보여 준다(추가된 줄바꿈과 들여쓰기는 표시용이다).¶

 GET /authorize?client_id=s6BhdRkqt3&request_uri=urn%3Aietf%3Aparams
  %3Aoauth%3Arequest_uri%3A6esc_11ACC5bwc014ltc14eY22c HTTP/1.1
 Host: as.example.com
¶

인가 요청 내용 중 code_challenge 매개변수 값과 같은 일부 요소는 특정 인가 요청에만 고유하므로, client는 반드시(MUST) request_uri 값을 한 번만 사용해야 한다. authorization server에 권장되는 동작(SHOULD)은 request_uri 값을 일회용으로 취급하는 것이다. 다만 사용자가 자신의 user agent에서 다시 로드하거나 새로 고침하여 발생한 중복 요청은 허용할 수 있다(MAY). 만료된 request_uri는 유효하지 않은 것으로 간주해 반드시 거부해야 한다(MUST).¶

authorization server는 사전 전송에서 비롯된 인가 요청도 다른 인가 요청과 동일하게 검증해야 한다(MUST). authorization server는 해당 요청이 사전 전송된 요청임을 확인할 수 있고, 요청과 authorization server의 정책 어느 쪽에도 생략할 단계의 결과에 영향을 주는 변경이 없었음을 확인할 수 있다면, 요청이 사전 전송되었을 때 수행한 검증 단계를 생략할 수 있다(MAY).¶

authorization server는 정책으로 전체 client에 일괄 적용하거나 client별로 적용하여, client가 인가 요청 데이터를 전달하는 유일한 수단으로 PAR를 지정할 수 있다(MAY). 이 경우 authorization endpoint로 들어온 요청의 request_uri 매개변수에 PAR endpoint에서 얻은 값이 들어 있지 않거나 해당 매개변수가 없으면, authorization server는 invalid_request 오류 코드를 사용하여 요청 처리를 거부한다.¶

참고: authorization server와 client는 선택적으로(MAY) 5절과 6절에 정의된 메타데이터를 사용해 원하는 동작을 나타낼 수 있다.¶

5. authorization server 메타데이터

PAR에 관한 서버의 지원 여부와 정책을 나타내기 위해 다음 authorization server 메타데이터 매개변수 [RFC8414]를 도입한다.¶

pushed_authorization_request_endpoint
client가 인가 요청을 POST하여 authorization server에서 사용할 수 있는 request_uri 값으로 교환할 수 있는 PAR endpoint의 URL이다.¶
require_pushed_authorization_requests
authorization server가 PAR를 통해서만 인가 요청 데이터를 받는지를 나타내는 불리언 매개변수다. 생략 시 기본값은 false다.¶

client는 pushed_authorization_request_endpoint가 있다는 사실만으로도 PAR 흐름을 사용할 수 있다고 판단할 수 있다. PAR endpoint에서 얻은 request_uri 값은 request_uri_parameter_supported나 require_request_uri_registration [OIDC.Disco] 등 다른 authorization server 메타데이터에 관계없이 authorization endpoint에서 사용할 수 있다.¶

6. client 메타데이터

Dynamic Client Registration Protocol [RFC7591]은 OAuth 2.0 client 메타데이터를 authorization server에 동적으로 등록하기 위한 API를 정의한다. [RFC7591]과 그 등록된 확장이 정의하는 메타데이터는 client에 관한 일반적인 데이터 모델을 이루기도 한다. 이 모델은 Dynamic Client Registration Protocol을 사용하지 않는 경우에도 authorization server 구현에 유용하다. 그러한 구현은 대개 client 구성을 관리하는 사용자 인터페이스를 어떤 형태로든 제공한다. 이 문서에서는 해당 client에 인가 요청 사전 전송이 필수인지를 나타내기 위해 다음 client 메타데이터 매개변수를 도입한다.¶

require_pushed_authorization_requests
client가 인가 요청을 시작하는 데 사용할 수 있는 유일한 수단이 PAR인지를 나타내는 불리언 매개변수다. 생략 시 기본값은 false다.¶

7. 보안 고려 사항

7.1. Request URI 추측

공격자는 유효한 request URI 값을 추측한 뒤 재사용하여 해당 client를 사칭하려 할 수 있다. authorization server는 반드시(MUST) request URI의 엔트로피에 관한 JAR [RFC9101], 10.2절 (d)항의 고려 사항을 반영해야 한다.¶

7.2. Open Redirection

공격자는 인가 코드를 얻거나 사용자를 대상으로 다른 공격을 시도하기 위해 자신이 통제하는 사이트를 가리키는 redirect URI를 등록하려 할 수 있다. 사전 전송된 인가 요청에 새 redirect URI가 들어 있으면, authorization server는 그 요청을 보낸 client가 인증된 경우에만 해당 URI를 수락해야 한다(MUST).¶

7.3. Request Object 재사용 공격

공격자는 정상적인 인가 요청에서 가로챈 request URI를 재사용할 수 있다. 이러한 공격에 대응하려면 authorization server가 request URI를 일회용으로 만드는 것이 권장된다(SHOULD).¶

7.4. client 정책 변경

Request Object를 제출한 시점과 해당 Request Object를 사용하는 인가 요청이 이루어지는 시점 사이에 client 정책이 변경될 수 있다. 따라서 authorization server는 인가 요청을 처리할 때 request 매개변수가 client 정책에 부합하는지 확인하는 것이 좋다.¶

7.5. Request URI 바꿔치기

공격자는 한 요청에서 request URI를 가로챈 뒤 이를 다른 인가 요청에 바꿔 넣을 수 있다. 예를 들어 OpenID Connect에서는 높은 인증 보증 수준을 요구하는 request URI를 더 낮은 수준을 요구하는 것으로 바꿀 수 있다. 이 공격을 방지하기 위해 client에 권장되는 방법(SHOULD)은 사전 전송하는 Request Object에 PKCE [RFC7636], 고유한 state 매개변수 [RFC6749] 또는 OIDC의 "nonce" 매개변수 [OIDC]를 사용하는 것이다.¶

8. 개인정보 보호 고려 사항

OAuth 2.0은 복잡하고 유연한 프레임워크다. 한 주체가 다른 두 주체 사이에서 데이터 접근에 대한 사용자의 인가를 중개하도록 설계된 만큼, 개인정보 보호에 미치는 영향이 광범위하다. 이 문서는 전체 프레임워크에서 하나의 메시지 시퀀스를 시작하는 다른 방법만 정의하므로, OAuth 전반의 개인정보 보호 고려 사항은 이 문서의 범위를 벗어난다. 다만 PAR를 사용하면 의도치 않은 정보 노출 가능성을 줄여 개인정보 보호를 개선할 수 있다. 인가 요청 데이터가 user agent를 평문으로 통과하는 URL의 쿼리 구성 요소에 담기는 대신, 보안 연결을 통해 client와 authorization server 사이에 직접 전송되는 HTTP 요청의 메시지 본문에 담기기 때문이다.¶
