1. 서론

OAuth 2.0 인가 프레임워크 [RFC6749]를 수년에 걸쳐 배포하고 구현한 경험을 통해, 특정 상황에서는 client가 요청 중인 access token(액세스 토큰)을 어디에서 사용하려는지 authorization server에 명시적으로 알려야 할 필요가 있음이 드러났다. authorization server가 상당수의 다양한 리소스를 지원하는 경우가 그 예이다.¶

access token을 처리할 보호된 리소스(resource server(리소스 서버), 애플리케이션, API 등)를 알면 authorization server는 해당 리소스에 필요한 형태로 토큰을 구성할 수 있다. 예를 들어 특정 리소스에 맞게 토큰이나 그 내부의 내용을 암호화하려면 어느 리소스가 토큰을 받아 복호화할지 알아야 한다. 또한 토큰에 들어 있거나 토큰이 참조하는 데이터에 대한 요구 사항은 리소스마다 다른 경우가 많다. 따라서 client가 어느 리소스에서 토큰을 사용하려는지 알면 authorization server는 그에 맞춰 토큰을 발급할 수 있다.¶

access token의 수신 대상이 누구인지 구체적으로 알면 토큰 자체의 보안도 강화할 수 있다. 현재 가장 널리 쓰이는 OAuth access token 유형인 Bearer token은 토큰을 가진 주체라면 누구나 관련 리소스에 접근할 수 있게 한다. 오용을 방지하려면 몇 가지 중요한 보안 전제가 충족되어야 한다. 그중 하나는 access token이 특정 보호된 리소스에서 특정 접근 범위 내에서만 유효해야 한다는 것이다. 예를 들어 5.2절([RFC6750])에서는 토큰 리디렉션을 방지하기 위해 토큰에 수신 대상을 포함하도록 규정한다. access token을 처리할 리소스가 어느 것인지 전달받으면 authorization server는 해당 토큰의 audience(토큰 대상)를 그 리소스로 제한하여 다른 리소스에서는 토큰을 사용하지 못하게 할 수 있다.¶

3.3절([RFC6749])에 정의된 OAuth scope에 보호된 리소스의 위치나 식별 정보까지 전달하는 역할을 맡기기도 한다. 하지만 이 방식이 항상 가능하거나 바람직한 것은 아니다. scope는 보통 접근 권한을 어디에서 행사할지를 나타내기보다 어떤 접근 권한을 요청하는지를 나타낸다(예를 들어 email, admin:org, user_photos, channels:read, channels:write은 실제로 쓰이는 scope 값 중 일부로, 접근 유형만 나타낼 뿐 위치나 식별 정보는 나타내지 않는다).¶

상황이나 배포 환경에 따라서는 client가 요청하는 access token을 어디에서 사용하려는지 authorization server에 알릴 수단이 중요하고 유용하다. 여러 OAuth 2.0 구현 및 배포 환경에서 이미 이 목적으로 자체 매개변수를 사용한다. 이 명세는 앞으로 이러한 독자적 방식 대신 사용할 수 있는 표준화된 상호운용 가능 방식을 제시하고자 한다.¶

1.1. 요구 사항 표기와 규칙

이 문서의 키워드 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", "OPTIONAL"은 여기에 표시한 것처럼 모두 대문자로 표기된 경우에만 BCP 14 [RFC2119] [RFC8174]에 명시된 의미로 해석한다.¶

1.2. 용어

이 명세에서는 The OAuth 2.0 Authorization Framework [RFC6749]에 정의된 "access token", "refresh token(리프레시 토큰)", "authorization server", "resource server", "authorization endpoint(인가 엔드포인트)", "authorization request", "authorization response", "token endpoint(토큰 엔드포인트)", "grant type(그랜트 유형)", "access token request", "access token response", "client"라는 용어를 사용한다.¶

2. 리소스 매개변수

client는 authorization server에 보내는 요청에 다음 매개변수를 포함하여 접근을 요청하는 보호된 리소스(resource server, 애플리케이션, API 등)를 나타낼 수 있다(MAY).¶

resource
접근을 요청하는 대상 서비스나 리소스를 나타낸다. 이 값은 반드시 절대 URI여야 한다(MUST). 절대 URI는 4.3절([RFC3986])에서 규정한다. 이 URI에는 프래그먼트 구성요소를 포함해서는 안 된다(MUST NOT). 쿼리 구성요소는 포함하지 않는 것이 바람직하다(SHOULD NOT). 다만 하나 이상의 쿼리 매개변수로 애플리케이션에 대한 요청 범위를 한정하는 경우와 같이, 쿼리 구성요소가 리소스 매개변수의 일부로서 유용하고 필요한 경우도 있다. resource 매개변수의 URI 값은 리소스가 무엇인지 나타내는 식별자이다. 이 식별자는 대상 리소스를 호스팅하는, 네트워크로 접근할 수 있는 위치에 대응하는 로케이터일 수 있다(MAY). 여러 resource 매개변수를 사용하여 요청하는 토큰을 여러 리소스에서 사용하려는 것임을 나타낼 수 있다(MAY).¶

이 매개변수의 값은 client가 접근을 요청하는 리소스를 식별한다. 이 매개변수는 보호된 리소스의 위치를 전달할 수 있으며, 일반적으로 https URL이나 더 추상적인 식별자를 사용한다. 이를 통해 authorization server는 해당 리소스에 맞는 정책을 적용할 수 있다. 예를 들어 발급할 토큰의 유형과 내용, 암호화 여부와 방식을 결정하고 적절한 audience 제한을 적용할 수 있다.¶

client는 접근하려는 API 전체 또는 리소스 집합을 나타내는 URI 중 제공할 수 있는 가장 구체적인 URI를 제시하는 것이 바람직하다(SHOULD). 실제로 client는 자신이 상호작용하는 애플리케이션이나 리소스의 기본 URI를 알고 있으며, 이 URI를 resource 매개변수 값으로 쓰기에 적합하다. 리소스에 대해 알고 있는 정보에 비추어 다른 값이 필요한 경우가 아니라면, client는 API의 기본 URI를 resource 매개변수 값으로 사용하는 것이 바람직하다(SHOULD). 예를 들어 그 리소스가 해당 호스트의 유일한 애플리케이션이라면 https://api.example.com/ 값을 사용한다. 반면 그 호스트에 있는 여러 애플리케이션 중 하나라면 https://api.example.com/app/처럼 더 구체적인 값을 사용한다. API에 여러 엔드포인트가 있는 경우도 한 예이다. 가령 System for Cross-domain Identity Management(SCIM) [RFC7644]에 https://apps.example.com/scim/Users, https://apps.example.com/scim/Groups, https://apps.example.com/scim/Schemas 같은 엔드포인트가 있다면, client는 발급받는 access token이 SCIM API의 모든 엔드포인트에서 유효하도록 리소스로 https://apps.example.com/scim/를 사용한다.¶

다음 오류 코드를 사용하면 authorization server가 인가 요청이나 access token 요청에 응답할 때 요청된 리소스에 문제가 있음을 나타낼 수 있다. 또한 client가 유효하지 않은 리소스와 scope의 조합을 요청했음을 알리는 데에도 사용할 수 있다.¶

invalid_target
요청된 리소스가 유효하지 않거나, 누락되었거나, 알려지지 않았거나, 형식이 잘못되었다.¶

authorization server는 발급하는 access token의 audience를 다음과 같이 제한하는 것이 바람직하다(SHOULD). resource 매개변수가 가리키는 리소스만 audience에 포함한다. JSON Web Token [RFC7519]에서는 aud 클레임으로 audience 제한을 전달할 수 있고, token introspection(토큰 인트로스펙션) [RFC7662] 응답에서는 이름이 같은 최상위 멤버가 audience 제한 정보를 제공한다. authorization server는 resource 값을 그대로 audience로 사용하거나, 그 값을 해당 리소스를 나타내는 더 일반적인 URI 또는 추상 식별자에 매핑할 수 있다.¶

2.1. 인가 요청

authorization endpoint로 보내는 인가 요청에 resource 매개변수를 사용하면, 접근을 요청하는 보호된 리소스가 무엇인지 나타낸다. 암시적 흐름(4.2절, OAuth 2.0 [RFC6749])을 통해 authorization endpoint가 access token을 직접 반환하는 경우, 요청된 리소스는 해당 access token에 적용된다. 코드 흐름(4.1절, OAuth 2.0 [RFC6749])에서는 authorization endpoint가 authorization grant(인가 부여)의 중간 표현인 authorization code(인가 코드)를 반환하므로, 요청된 리소스는 authorization grant 전체에 적용된다.¶

JWT Secured Authorization Request [JWT-SAR]를 사용하는 경우처럼 인가 요청을 JSON Web Token(JWT)으로 보내는 경우, resource 매개변수의 값이 하나면 JSON 문자열로, 여러 개면 문자열 배열로 표현한다.¶

client가 인가를 요청하면서 resource 매개변수를 생략하면 authorization server는 특정 리소스 없이 요청을 처리하거나 미리 정의된 기본 리소스 값을 사용하여 요청을 처리할 수 있다(MAY). 그 대신 authorization server는 client에게 접근하려는 리소스를 명시하도록 요구할 수 있고(MAY), 매개변수를 생략한 요청은 다음과 같이 거부할 수 있다(MAY). 거부 시에는 invalid_target 오류를 반환한다. authorization server는 이 데이터를 이용해 client가 사용자를 대신하여 접근하려는 리소스를 사용자에게 알리거나, 정책을 적용하거나(예: 알려지지 않은 리소스 때문에 요청을 거부함), 이후 access token 요청에 사용할 수 있는 리소스 집합을 결정할 수 있다.¶

authorization server가 전달받은 값을 파싱하지 못하거나 해당 리소스를 허용할 수 없다고 판단하면, 오류 코드 invalid_target를 error 매개변수 값으로 담은 오류 응답으로 요청을 거부하는 것이 바람직하다. 오류의 원인에 관한 추가 정보는 error_description을 사용해 제공할 수 있다.¶

client가 authorization server에 https://api.example.com/app/에서 사용할 access token을 원한다고 알리는 인가 요청의 예를 아래 그림 1에 제시한다(추가 줄바꿈과 들여쓰기는 보기 쉽게 하기 위한 것일 뿐이다).¶

아래 그림 2는 code 응답 유형을 사용하는 인가 요청의 예이다. 이 예에서 client는 resource owner(리소스 소유자)의 연락처 및 캘린더 데이터에 대한 접근을 요청하며, 대상 리소스는 https://cal.example.com/ 및 https://contacts.example.com/이다(추가 줄바꿈과 들여쓰기는 보기 쉽게 하기 위한 것일 뿐이다).¶

2.2. access token 요청

어떤 grant type이든 token endpoint에 보내는 access token 요청에 resource 매개변수를 사용하면, 이 매개변수는 client가 요청한 access token을 사용하려는 대상 서비스 또는 보호된 리소스를 나타낸다.¶

access token 요청을 처리할 때 어떤 리소스 값을 허용할지는 authorization server가 로컬 정책이나 설정에 따라 전적으로 자체 재량으로 결정한다. refresh_token 또는 authorization_code grant type의 요청에서는 이 정책에 따라 허용하는 리소스를 resource owner가 최초에 인가한 리소스 전체 또는 그 일부로 제한할 수 있다. authorization_code 방식으로 요청된 리소스가 최초에 인가된 리소스 집합의 부분집합이면, authorization server는 요청된 그 부분집합을 기준으로 access token을 발급한다. 반면 refresh token이 반환되는 경우에는 그 토큰이 최초 authorization grant 전체에 결부된다.¶

토큰을 요청할 때 client는 resource 매개변수로 토큰을 사용하려는 대상 서비스를 지정하고, scope 매개변수로 요청하는 토큰에 원하는 scope를 지정할 수 있다. 이는 요청된 scope를 가지며 요청한 모든 대상 서비스에서 사용할 수 있는 토큰을 달라는 뜻이다. 결과적으로 토큰에 요청하는 접근 권한은 모든 대상 서비스와 모든 scope의 데카르트 곱이다. access token을 발급할 때 authorization server는 가능한 한 그 토큰의 scope 값을 해당 리소스가 처리할 수 있고 알 필요가 있는 값으로 축소하는 것이 바람직하다. (여기서 "downscope"란 resource owner가 최초에 인가한 것보다 적은 권한을 부여한다는 뜻이다.) scope 값 목록은 resource owner가 목록에 나열된 여러 서비스를 이용한다는 단서가 된다. 토큰의 scope를 특정 서비스에 필요한 만큼만 줄이면 이 정보가 다른 서비스에 드러나는 정도를 제한할 수 있으므로 개인정보 보호가 한층 강화된다. 5.1절([RFC6749])에서 규정한 대로, access token의 실제 scope가 client가 요청한 scope와 다르면 authorization server는 scope 응답 매개변수 값으로 그 실제 scope를 client에 알려야 한다.¶

3. 보안 고려 사항

어떤 리소스에 정당하게 제시된 access token의 audience가 제한되어 있으면, 그 리소스는 해당 토큰을 가져다가 다른 곳에 제시해 다른 리소스에 부당하게 접근할 수 없다. resource 매개변수를 사용하면 client는 요청한 access token을 사용할 보호된 리소스를 나타낼 수 있고, 이를 바탕으로 authorization server는 토큰에 적절한 audience 제한을 적용할 수 있다.¶

일부 서버는 사용자 콘텐츠를 호스팅하거나 여러 테넌트를 지원할 수 있다. 한 테넌트가 access token을 사용해 다른 테넌트 소유의 리소스에 부당하게 접근하는 공격을 막으려면, 경로 구성 요소처럼 테넌트를 식별하는 URI 부분을 모두 포함한 구체적인 리소스 URI를 사용하는 것이 중요하다. 그러면 테넌트를 식별할 수 있도록 access token의 audience를 제한할 수 있으며, 다른 테넌트 소유의 리소스에서는 audience가 유효하지 않아 그 토큰을 사용할 수 없다.¶

토큰 요청에 resource 매개변수를 여러 번 포함할 수 있지만, resource 매개변수는 하나만 사용하는 것이 권장된다. Bearer 토큰의 의도된 수신자(audience)가 여럿이면 토큰은 둘 이상의 보호된 리소스에서 유효하므로, 그중 어느 리소스든 이 토큰으로 나머지 리소스 중 어느 곳에든 접근할 수 있다. 따라서 audience가 여럿인 access token을 사용하려면 관련 당사자들 사이에 높은 수준의 신뢰가 필요하다. 또한 authorization server는 여러 리소스가 지정된 토큰 요청을 처리하지 않으려 할 수도 있고, 처리할 수 없을 수도 있다.¶

가능하면 resource 매개변수는 네트워크 주소로 접근할 수 있는 보호된 리소스의 위치에 대응하는 것이 바람직하다. 그러면 client는 요청 대상 리소스가 해당 네트워크 위치를 제어하는지 검증할 수 있으므로, 악의적인 엔드포인트가 다른 리소스용 토큰을 확보할 위험이 줄어든다. resource 매개변수에 추상 식별자가 들어 있으면, 토큰을 전송하는 모든 네트워크 엔드포인트가 그 식별자의 의도된 audience인지 별도의 경로로 검증할 책임은 client에 있다.¶

4. 개인정보 보호 고려 사항

일반적인 OAuth 배포 환경에서 authorization server는 사용자와 client의 행동을 상당 부분 관찰하고 추적할 수 있는 위치에 있다. 이는 대체로 OAuth의 본질에서 비롯되며, 이 문서는 그 점에 거의 영향을 미치지 않는다. 다만 access token에 token introspection을 사용하지 않는 경우처럼 일부 상황에서는, 여기에서 정의한 resource 매개변수를 사용하면 이를 사용하지 않을 때보다 행동을 다소 더 세밀하고 구체적으로 추적할 수 있다.¶
