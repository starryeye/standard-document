초록

이 명세는 OAuth 2.0 authorization server(인가 서버)에 security token(보안 토큰)을 요청하여 발급받는 방법을 정함으로써 HTTP 및 JSON 기반 Security Token Service(보안 토큰 서비스) (STS) 프로토콜을 정의한다. 여기에는 impersonation(가장)과 delegation(위임)을 사용하는 security token도 포함된다.¶

1. 서론

security token은 서로 다른 환경이나 보안 도메인 사이에서 신원 및 보안 정보를 쉽게 공유하도록 하는 정보의 집합이다. 대표적인 예로 JSON Web Token(JWT) [JWT] 및 Security Assertion Markup Language(SAML) 2.0 어설션 [OASIS.saml-core-2.0-os]이 있다. security token에는 일반적으로 무결성을 확보하기 위해 서명하며, 기밀성을 확보하기 위해 암호화를 병행하기도 한다. [RFC7521]에서처럼 security token을 어설션이라고 부르기도 한다.¶

Security Token Service(STS)는 전달받은 security token을 검증하고 그에 응답해 새 security token을 발급할 수 있는 서비스다. 이를 통해 client는 서로 다른 환경 또는 보안 도메인에 있는 리소스에 적합한 접근 자격 증명을 얻을 수 있다. 웹 서비스 client는 토큰 교환을 위해 STS와 통신하는 프로토콜로 WS-Trust [WS-Trust]를 사용해 왔다. WS-Trust가 XML과 SOAP을 사용하는 반면, 최근 웹 개발은 RESTful(Representational State Transfer) 패턴과 JSON을 사용하는 추세다. OAuth 2.0 Authorization Framework [RFC6749]와 OAuth 2.0 Bearer Tokens [RFC6750]는 서드파티 애플리케이션의 HTTP 및 RESTful 리소스 접근을 인가하는 데 널리 쓰이는 표준으로 자리 잡았다. 기존 OAuth 2.0 방식은 resource owner(리소스 소유자)의 인가를 나타내는 어떤 형태의 정보를 access token으로 교환하는 것으로, 실무에서 매우 유용한 방식임이 입증되었다. 그러나 기존의 입력과 출력은 그대로 사용하기에는 제약이 다소 커서 security token 교환 프레임워크를 완전히 수용하기 어렵다.¶

이 명세는 OAuth 2.0을 확장하여 client가 STS 역할을 하는 authorization server에 security token을 요청하고 발급받을 수 있도록 하는 프로토콜을 정의한다. OAuth 2.0과 마찬가지로 이 명세는 client를 쉽게 개발할 수 있도록 하는 데 중점을 두며, 오늘날 거의 모든 개발 환경에서 쓸 수 있는 HTTP client와 JSON 파서만 필요로 한다. 이 명세에서 정의하는 STS 프로토콜 자체는 RESTful하지 않다(STS는 REST 접근법에 그다지 잘 맞지 않는다). 다만 RESTful 시스템을 다뤄 온 개발자에게 익숙할 만한 통신 패턴과 데이터 형식을 사용한다.¶

이 명세는 토큰 교환 요청을 위한 새로운 grant type(인가 부여 유형)과 그러한 요청을 token endpoint(토큰 엔드포인트)에 보낼 때 사용하는 구체적인 매개변수를 정의한다. 토큰 교환 응답은 token endpoint가 보내는 일반적인 OAuth 2.0 응답에, client에 정보를 제공하기 위해 이 명세에서 정의하는 몇 가지 매개변수를 추가한 것이다.¶

토큰 교환 과정에서는 토큰 교환을 요청하는 주체를 client로 본다. 그렇다고 이 프로파일을 기존 OAuth client만 사용할 수 있는 것은 아니다. 예를 들어 OAuth resource server(리소스 서버)는 보호된 리소스 요청에서 받은 access token을 백엔드 서비스 호출에 사용하기 적합한 새 토큰으로 교환하기 위해 토큰 교환 과정에서 client 역할을 맡을 수 있다. 새 토큰은 다운스트림 서비스에 맞춰 권한 범위가 더 좁게 설정된 access token일 수도 있고, 완전히 다른 종류의 토큰일 수도 있다.¶

이 명세의 범위는 OAuth 2.0을 사용하는 STS 방식의 토큰 교환을 위한 기본 요청·응답 프로토콜을 정의하는 데 한정된다. delegation의 의미를 표현할 수 있도록 몇 가지 새로운 JWT claim을 정의하지만, 토큰 자체(authorization server에 제시하는 토큰과 client가 발급받는 토큰 모두)의 구체적인 구문, 의미, 보안 특성은 명시적으로 범위에서 제외하며, 구현이 배포될 때 적용되는 신뢰 모델에는 어떠한 요구사항도 부과하지 않는다. 추가 프로파일은 관련 당사자와 신뢰 관계의 구체적 특성에 관하여 더 자세한 요구사항을 정할 수 있다. 예를 들어 토큰 서명이나 암호화 또는 둘 다가 필요한지, 소유 증명(proof-of-possession) 방식의 토큰을 요구하거나 발급할지 등이 이에 해당한다. 다만 이러한 세부사항은 흔히 배포 환경별 요구에 맞춰 정책으로 결정되며, 그에 따라 설정하거나 구현한다.¶

이렇게 얻은 security token은 여러 맥락에서 사용할 수 있으며, 각 사용 맥락의 세부사항 역시 이 명세의 범위를 벗어난다.¶

1.1. delegation과 impersonation의 의미 차이

앞 절에서 언급했듯이, STS의 일반적인 사용 사례 중 하나는 resource server A가 요청을 보낸 사용자 B를 대신하여 백엔드 서비스 C를 호출할 수 있게 하는 것이다. 해당 사이트의 정책과 인가 인프라에 따라, A가 자신의 자격 증명을 사용해 C에 접근하되 B를 대신해 행동한다는 사실을 어떤 형태로든 표시하는 방식("delegation")이 바람직할 수 있다. 또는 A가 C에 대한 제한된 접근 자격 증명을 부여받되, 그 자격 증명이 여전히 B를 인가된 주체로 식별하는 방식("impersonation")이 바람직할 수 있다. delegation과 impersonation은 여러 참여자가 관여하는 다른 시나리오에서도 유용할 수 있다.¶

principal(보안 주체) A가 principal B인 것처럼 행동하는 impersonation에서는, A가 정해진 권한의 맥락에서 B가 가진 모든 권한을 부여받으며 그 맥락에서 B와 구별되지 않는다. 따라서 그런 토큰을 받는 개체 입장에서는 실제로 B를 상대하는 셈이다. 신원 시스템의 일부 구성원은 impersonation이 이루어지고 있다는 사실을 알 수도 있지만, 반드시 알아야 하는 것은 아니다. A가 B로서 행위할 때 토큰이 인가한 권한의 맥락에서 A는 실질적으로 B다. A가 B로서 행위할 수 있는 범위나 시간에 제한을 두거나, 심지어 한 번만 허용할 수도 있다. 이러한 제한은 토큰의 내용이나 별도 경로의 메커니즘으로 적용할 수 있다.¶

delegation과 impersonation은 밀접하게 관련되어 있지만 의미는 서로 다르다. delegation에서 principal A는 B와 구별되는 고유한 신원을 유지한다. B가 자기 권한의 일부를 A에게 위임했을 수는 있지만, 실제로 행위하는 쪽은 B를 대리하는 A라는 점이 명확하다. 말하자면 A는 B의 대리인이다.¶

delegation과 impersonation이 모든 상황을 포괄하는 것은 아니다. 예를 들어 principal이 자신을 위해 직접 행동한다면 delegation과 impersonation 어느 쪽도 적용되지 않는다. 다만 토큰 교환에서는 이 두 방식이 더 흔히 쓰이므로 이 명세에서 더 직접적으로 다룬다.¶

토큰에서 delegation을 표현할 때는 대개 토큰의 주된 대상에 관한 정보와, 그 대상에게서 권한 일부를 위임받은 actor에 관한 정보를 모두 포함한다. 이렇게 여러 대상의 정보로 이루어진 토큰을 composite token(복합 토큰)이라 부르기도 한다. 일반적으로 요청에서 subject_token은 토큰 요청자가 대리하는 당사자의 신원을 나타내고, actor_token은 발급된 토큰의 접근 권한을 위임받는 당사자의 신원을 나타낸다. authorization server가 발급하는 composite token에는 양쪽 당사자의 정보가 모두 들어간다. composite token을 발급할지 여부와 발급 시점은 authorization server의 재량과 적용되는 정책 및 구성에 따른다.¶

composite token을 구체적으로 어떻게 표현할지, 나아가 그런 토큰을 발급할지 여부는 구현의 세부 사항과 토큰의 종류에 따라 달라진다. JWT가 아닌 composite token의 표현 방식은 이 명세의 범위를 벗어난다. 다만 actor_token 요청 매개변수로 원하는 actor에 관한 정보를 제공할 수 있고, JWT의 act claim으로 delegation의 연쇄를 표현할 수 있다.¶

2. 토큰 교환 요청과 응답

2.1. 요청

client는 4.5절([RFC6749])에서 정의한 확장 grant type 메커니즘을 사용하여 authorization server의 token endpoint에 토큰 요청을 보내 security token을 요청한다.¶

authorization server에 대한 client 인증에는 OAuth 2.0이 제공하는 일반적인 메커니즘을 사용한다. 2.3.1절([RFC6749])에서는 client의 비밀번호 기반 인증을 정의한다. 다만 client 인증은 확장할 수 있으므로 다른 메커니즘도 가능하다. 예를 들어 [RFC7523]은 bearer JSON Web Token(JWT) [JWT]을 사용하는 client 인증을 정의한다. 어떤 client 인증 방식을 지원할지, 인증되지 않았거나 신원이 확인되지 않은 client를 허용할지는 배포 시 authorization server가 재량으로 결정한다. client 인증을 생략하면 보안이 훼손된 토큰을 가진 사람은 누구나 그 보안이 훼손된 토큰으로 STS를 통해 다른 토큰을 얻을 수 있다는 점에 유의한다. 따라서 client를 인증하면 STS는 어떤 개체가 다른 개체에 대해 impersonation을 하거나 그 개체로부터 delegation을 받을 수 있는지 추가로 인가를 확인할 수 있다.¶

client는 HTTP POST 메서드로 token endpoint에 확장 grant type을 사용한 토큰 교환 요청을 보낸다. 아래 매개변수는 HTTP 요청의 엔터티 본문에 application/x-www-form-urlencoded 형식으로 포함한다. 이때 부록 B([RFC6749])에 설명된 대로 UTF-8 문자 인코딩을 사용한다.¶

grant_type
REQUIRED. 값 urn:ietf:params:oauth:grant-type:token-exchange는 토큰 교환을 수행한다는 뜻이다.¶
resource
OPTIONAL. client가 요청한 security token을 사용하려는 대상 서비스나 리소스를 가리키는 URI다. 이를 통해 authorization server는 발급할 토큰의 유형과 내용, 암호화 여부와 방식 등을 정하는 등 대상에 맞는 정책을 적용할 수 있다. 많은 경우 client는 자신이 상호작용하는 시스템의 논리적 구성을 모르며, 토큰을 사용하려는 서비스의 URI만 안다. resource 매개변수를 사용하면 client는 발급된 토큰을 어디에서 사용할지 authorization server에 알릴 수 있다. 이를 위해 토큰 교환 요청에 해당 위치를, 실제로 그 리소스에 접근할 때 사용할 것과 동일한 형식(대개 https URL)으로 제공한다. 일반적으로 authorization server는 리소스 URI 값을 적절한 정책에 매핑할 수 있다. resource 매개변수의 값은 절대 URI여야 한다(MUST). 여기서 절대 URI란 4.3절([RFC3986])에서 규정한 것을 말한다. 쿼리 구성요소는 포함해도 되지만(MAY), 프래그먼트 구성요소는 포함해서는 안 된다(MUST NOT). resource 매개변수를 여러 개 사용해 발급된 토큰을 나열된 여러 리소스에서 사용하려는 것임을 나타낼 수 있다. [OAUTH-RESOURCE]에서 resource 매개변수의 배경과 용도에 관한 자세한 내용을 확인할 수 있다.¶
audience
OPTIONAL. client가 요청한 security token을 사용하려는 대상 서비스의 논리적 이름이다. resource 매개변수와 용도는 비슷하지만 여기서는 client가 대상 서비스의 논리적 이름을 제공한다. 이 이름을 해석하려면 client와 authorization server 모두 그 값의 의미를 알아야 한다. OAuth client identifier, SAML entity identifier [OASIS.saml-core-2.0-os], OpenID Connect Issuer Identifier [OpenID.Core] 등은 audience 매개변수의 값으로 사용할 수 있는 예다. 다만 값이 의도한 유형으로 올바르게 해석되려면, 특정 authorization server에서 사용하는 audience 값은 그 서버 내에서 고유해야 한다. audience 매개변수를 여러 개 사용해 발급된 토큰을 나열된 여러 audience에서 사용하려는 것임을 나타낼 수 있다. audience와 resource 매개변수를 함께 사용해 논리적 이름과 리소스 URI를 섞어 여러 대상 서비스를 지정할 수 있다.¶
scope
OPTIONAL. 3.3절([RFC6749])에서 정의한 대로, 공백으로 구분되며 대소문자를 구별하는 문자열의 목록이다. client는 이 목록으로 토큰을 사용할 서비스나 리소스의 맥락에서 요청한 security token에 어떤 scope를 원하는지 지정할 수 있다. scope의 값과 그 의미는 서비스마다 다르며, 해당 서비스 문서에 설명되어 있을 것으로 본다.¶
requested_token_type
OPTIONAL. 3절에 설명된 대로, 요청한 security token의 유형을 나타내는 식별자다. 요청에서 유형을 지정하지 않으면 authorization server가 재량으로 발급할 토큰의 유형을 정한다. resource 또는 audience 매개변수가 가리키는 서비스나 리소스의 요구사항을 알고 있다면, 그 요구사항에 따라 유형이 결정될 수도 있다.¶
subject_token
REQUIRED. 요청자가 대리하는 당사자의 신원을 나타내는 security token이다. 일반적으로 이 토큰의 대상은 요청에 응답하여 발급되는 security token의 대상이 된다.¶
subject_token_type
REQUIRED. 3절에 설명된 대로, subject_token 매개변수의 security token 유형을 나타내는 식별자다.¶
actor_token
OPTIONAL. 실제로 행위하는 당사자의 신원을 나타내는 security token이다. 일반적으로 이 당사자는 요청한 security token을 사용해 토큰의 대상을 대신하여 행동할 권한을 부여받는다.¶
actor_token_type
3절에 설명된 대로, actor_token 매개변수의 security token 유형을 나타내는 식별자다. 이 식별자가 필수인 경우(REQUIRED)는 요청에 actor_token 매개변수가 있을 때다. 그렇지 않으면 포함해서는 안 된다(MUST NOT).¶

authorization server는 요청을 처리할 때 표시된 토큰 유형에 적합한 검증 절차를 수행해야 한다(MUST). actor token이 있는 경우에는 그 토큰에 대해 표시된 유형에 적합한 검증 절차도 수행해야 한다. 개별 토큰의 유효성 판단 기준과 세부 사항은 이 문서의 범위를 벗어나며, 각 토큰의 유형과 내용에 따라 달라진다.¶

일회용이라는 조건이나 토큰 유형에 고유한 다른 의미 규칙이 없다면, 토큰 교환을 수행하는 것 자체는 subject token이나 actor token의 유효성에 영향을 주지 않는다. 또한 각 토큰 교환은 일회성 처리이며 입력 토큰과 출력 토큰을 긴밀히 연결하지 않는다. 예를 들어 출력 토큰의 만료 시각이 입력 토큰의 만료 시각에 영향을 받을 수는 있지만, 입력 토큰을 갱신하거나 그 유효 기간을 연장해도 그 변경이 출력 토큰의 속성에 반영된다고 기대할 수는 없다. 토큰 철회 이벤트를 전파하는 것이 적절하거나 바람직할 수는 있다. 다만 이는 STS 프로토콜의 일반적인 특성이 아니며, 특정 구현, 토큰 유형 또는 배포 환경에 따르는 동작이다.¶

2.1.1. resource, audience, scope의 관계

토큰을 요청할 때 client는 audience 및 resource 매개변수로 토큰을 사용하려는 대상 서비스를 지정할 수 있고, scope 매개변수로 요청하는 토큰에 원하는 scope를 지정할 수 있다. 이 요청에서 client가 요구하는 것은 요청한 scope를 가지면서 요청에 지정된 모든 대상 서비스에서 사용할 수 있는 토큰이다. 따라서 토큰에 대해 요청한 접근 권한은 사실상 모든 scope와 모든 대상 서비스의 데카르트 곱이다.¶

authorization server는 어떤 토큰 요청이든 받아들이지 않거나 처리할 수 없을 수 있지만, 매우 광범위한 접근 권한을 요청하면 요청을 충족할 수 없을 가능성이 훨씬 높아진다. 따라서 배포 환경 내 시스템 간의 관계를 구체적으로 알지 못한다면, client는 요청할 접근 범위, 특히 대상 서비스의 수를 신중하게 정하는 것이 좋다. authorization server는 invalid_target 오류 코드를 사용해 너무 많은 대상 서비스에 대한 접근을 한꺼번에 요청했음을 client에 알릴 수 있다. 이 오류 코드는 2.2.2절에서 정의한다.¶

2.2. 응답

authorization server는 토큰 교환 요청에 대해 5절([RFC6749])에 명시된 대로 token endpoint에서 일반적인 OAuth 2.0 응답을 반환한다. 자세한 내용과 설명은 다음 하위 절에서 다룬다.¶

2.2.1. 성공 응답

요청이 유효하고 authorization server의 모든 정책과 기타 기준을 충족하면 성공 토큰 응답을 구성한다. [RFC8259]에 명시된 "application/json" 미디어 유형을 사용해 다음 매개변수를 HTTP 응답의 엔티티 본문에 추가하고, HTTP 상태 코드는 200으로 설정한다. 각 매개변수를 최상위 수준에 추가하여 JavaScript Object Notation(JSON) 구조로 직렬화한다. 매개변수 이름과 문자열 값은 JSON 문자열로, 수치 값은 JSON 숫자로 넣는다. 매개변수의 순서는 중요하지 않으며 달라질 수 있다.¶

access_token
REQUIRED. 토큰 교환 요청에 대한 응답으로 authorization server가 발급한 security token이다. 여기서는 access_token 매개변수에 요청된 토큰을 담는다. 이 매개변수는 5.1절([RFC6749])에 나온다. 이렇게 하면 이 토큰 교환 프로토콜은 token endpoint에 대해 이미 정의된 OAuth 2.0 요청 및 응답 구조를 사용할 수 있다. access_token 식별자는 역사적인 이유로 사용하며, 발급된 토큰이 OAuth access token일 필요는 없다.¶
issued_token_type
REQUIRED. 3절에서 설명하는 바와 같이, 발급된 security token의 표현 형식을 나타내는 식별자다.¶
token_type
REQUIRED. 7.1절([RFC6749])에 명시된 대로, 발급된 access token의 사용 방법을 지정하는 대소문자 구분 없는 값이다. client는 이 값으로 보호된 리소스에 접근할 때 access token을 어떻게 사용해야 하는지 알 수 있다. 예를 들어 Bearer 값([RFC6750]에 명시됨)은 발급된 security token이 bearer token임을 뜻한다. 이 경우 client는 토큰 자체의 내용 외에 별도로 자격을 증명하지 않고 토큰을 그대로 제시하면 된다. 이 매개변수의 뜻은 발급된 security token의 표현 형식을 선언하는 issued_token_type 매개변수의 뜻과 다르다. 일반적으로 "토큰 유형"이란 security token의 구조적 또는 구문적 표현 형식을 뜻하며, 이 명세의 모든 *_token_type 매개변수에서도 같은 뜻으로 쓰인다. 발급된 토큰이 access token에 해당하지 않고 access token으로 사용할 수도 없다면, token_type에 N_A 값을 사용하여 해당 맥락에는 OAuth 2.0 token_type 식별자가 적용되지 않음을 나타낸다.¶
expires_in
RECOMMENDED. authorization server가 발급한 토큰의 유효 기간을 초 단위로 나타낸다. client는 토큰 내용을 검사할 필요성을 느끼지 못하거나 검사할 능력이 없는 경우가 많다. 이 매개변수는 토큰 유형에 관계없이 토큰이 얼마 동안 유효할 것으로 예상되는지를 일관된 방식으로 나타낸다. 예를 들어 값 1800은 응답이 생성된 시점으로부터 30분 뒤에 토큰이 만료된다는 뜻이다.¶
scope
발급된 security token의 scope가 client가 요청한 scope와 같으면 선택 사항(OPTIONAL)이며, 그렇지 않으면 필수 사항(REQUIRED)이다.¶
refresh_token
OPTIONAL. 임시 자격 증명 하나(subject_token)를 다른 맥락에서 사용할 별도의 임시 자격 증명(발급된 토큰)으로 교환하는 경우에는 일반적으로 refresh token(갱신 토큰)을 발급하지 않는다. 원래의 자격 증명이 더 이상 유효하지 않아도 토큰 교환을 수행한 client가 리소스에 접근할 수 있어야 한다면 refresh token을 발급할 수 있다. 예를 들어 사용자가 자리를 비웠거나 오프라인이어서 client와 활성 세션을 유지하는 사용자가 더 이상 없는 경우가 이에 해당한다. 이 명세를 적용하는 프로파일이나 배포 환경에서는 urn:ietf:params:oauth:grant-type:token-exchange grant type의 요청에 대해 client가 어떤 조건에서 refresh token을 받을 것으로 예상할 수 있는지 명확히 문서화하는 것이 좋다.¶

2.2.2. 오류 응답

요청 자체가 유효하지 않거나, subject_token 또는 actor_token 중 하나라도 어떤 이유로든 유효하지 않거나 정책상 수용할 수 없는 경우, authorization server는 반드시(MUST) 5.2절([RFC6749])에 명시된 대로 오류 응답을 구성해야 한다. error 매개변수의 값은 반드시(MUST) invalid_request 오류 코드여야 한다.¶

resource 또는 audience 매개변수로 지정한 대상 서비스 중 어느 하나에 대해 authorization server가 토큰을 발급할 의사가 없거나 발급할 수 없는 경우, 오류 응답에는 invalid_target 오류 코드를 사용하는 것이 권고된다(SHOULD).¶

authorization server는 오류 원인에 관한 정보를 추가할 수 있다(MAY). 이때 error_description을 사용하며, 그 사용법은 5.2절([RFC6749])에서 설명한다.¶

필요에 따라 다른 오류 코드를 사용할 수도 있다.¶

2.3. 토큰 교환 예시

다음은 OAuth resource server가 교환 과정에서 client 역할을 맡는 가상의 토큰 교환 예시다. resource server는 보호된 리소스에 대한 요청에서 받은 access token을 백엔드 서비스를 호출하는 데 사용할 새 토큰으로 교환한다. 예시에 추가된 줄바꿈과 들여쓰기는 표시를 위한 것일 뿐이다.¶

그림 1은 resource server가 보호된 리소스에 대한 요청을 받는 모습을 보여 준다. 이 요청의 Authorization 헤더에는 2.1절([RFC6750])에 명시된 대로 OAuth access token이 들어 있다.¶

그림 2에서 resource server는 토큰 교환을 위한 client 역할을 맡는다. 그림 1의 요청에서 받은 access token은 2.1절에 명시된 요청을 통해 authorization server로 전송된다. subject_token 매개변수의 값에 access token을 담고, subject_token_type 매개변수의 값으로 이 토큰이 OAuth 2.0 access token임을 나타낸다. client 역할을 하는 resource server는 자신의 식별자와 시크릿으로 HTTP Basic 인증 방식을 사용해 authorization server에 자신의 신원을 증명한다. resource 매개변수는 발급된 토큰을 사용할 백엔드 서비스의 위치인 <https://backend.example.com/api> 주소를 나타낸다.¶

authorization server는 client의 자격 증명과 토큰 교환 요청에 제시된 subject_token을 검증한다. authorization server는 resource 매개변수에서 요청에 적용할 적절한 정책을 판단할 수 있으며, <https://backend.example.com> 주소에서 사용하기에 적합한 토큰을 발급한다. 응답의 access_token 매개변수에는 새 토큰이 들어 있다(그림 3 참조). 이 토큰은 그 자체로 1분 동안 유효한 bearer 방식의 OAuth access token이다. 이 토큰은 마침 JWT이지만, client는 그 구조와 형식을 알 수 없으므로 issued_token_type에는 access token이라는 점만 표시된다.¶

이제 resource server는 그림 4와 같이 새로 얻은 access token을 백엔드 서버에 요청을 보낼 때 사용할 수 있다.¶

추가 예시는 부록 A에서 볼 수 있다.¶

3. 토큰 유형 식별자

이 명세의 여러 매개변수는 해당 토큰을 설명하는 식별자를 값으로 사용한다. 구체적으로는 요청의 requested_token_type, subject_token_type 및 actor_token_type 매개변수와 응답의 issued_token_type 멤버가 이에 해당한다. 토큰 유형 식별자는 URI다. 토큰 교환에는 다른 주체가 발급한 토큰과 해당 authorization server가 발급한 토큰을 모두 사용할 수 있다. 전자의 경우 토큰 유형 식별자는 authorization server가 토큰을 파싱할 수 있도록 구문 형식(예: JWT 또는 SAML 2.0)을 나타낸다. 후자의 경우에는 해당 authorization server가 토큰을 어떤 용도로 발급했는지(예: access_token 또는 refresh_token)를 나타낸다.¶

이 명세에서는 다음 토큰 유형 식별자를 정의한다. 다른 토큰 유형을 나타내기 위해 다른 URI를 사용할 수 있다(MAY).¶

urn:ietf:params:oauth:token-type:access_token
해당 authorization server가 발급한 OAuth 2.0 access token임을 나타낸다.¶
urn:ietf:params:oauth:token-type:refresh_token
해당 authorization server가 발급한 OAuth 2.0 refresh token임을 나타낸다.¶
urn:ietf:params:oauth:token-type:id_token
2절([OpenID.Core])에 정의된 ID Token임을 나타낸다.¶
urn:ietf:params:oauth:token-type:saml1
base64url로 인코딩된 SAML 1.1 [OASIS.saml-core-1.1] 어설션임을 나타낸다.¶
urn:ietf:params:oauth:token-type:saml2
base64url로 인코딩된 SAML 2.0 [OASIS.saml-core-2.0-os] 어설션임을 나타낸다.¶

urn:ietf:params:oauth:token-type:jwt 값은 9절([JWT])에 정의되어 있으며, 해당 토큰이 JWT임을 나타낸다.¶

access token과 JWT의 차이는 미묘하다. access token은 위임된 인가 결정을 나타내지만, JWT는 토큰 형식이다. access token은 JWT 형식일 수 있지만 반드시 그럴 필요는 없다. JWT가 access token일 수는 있지만, 모든 JWT가 access token인 것은 아니다. 이 명세에서 urn:ietf:params:oauth:token-type:access_token은 해당 authorization server가 발급한 일반적인 OAuth access token임을 나타내기 위한 것이다. client는 이 토큰의 내부 내용을 알 수 없으며, 같은 authorization server에서 얻은 다른 access token과 똑같은 방식으로 사용할 수 있다. (토큰이 실제로 JWT일 수 있지만, client는 그 사실을 알지 못하며 알 필요도 없다.) 반면 urn:ietf:params:oauth:token-type:jwt는 요청하거나 보내는 토큰이 구체적으로 JWT임을 나타내기 위한 것이다(가령 [RFC7523]이 지원하는 것처럼, 다른 authorization server에서 access token을 얻기 위한 인가 부여 수단으로 JWT를 사용하는 도메인 간 사례가 이에 해당할 수 있다).¶

바이너리 형태의 토큰을 전달하는 데 쓰는 URI는 base64 또는 HTTP와 OAuth에서 사용하기에 적합한 다른 인코딩 방식을 적용한다는 의미와 연결되어 있어야 한다.¶

4. JSON Web Token claim 및 Introspection 응답 매개변수

토큰 안에 delegation을 표현하고, delegation 또는 impersonation을 할 권한을 나타내는 방법을 정의해 두면 유용하다. 이 문서에서 설명하는 토큰 교환 프로토콜은 모든 유형의 토큰에 사용할 수 있지만, 이 절에서는 특히 JWT와 OAuth 2.0 Token Introspection [RFC7662] 응답에서 이러한 의미를 표현할 claim을 정의한다. 다른 유형의 토큰에도 비슷한 정의를 마련할 수 있지만, 이는 이 명세의 범위를 벗어난다.¶

iss, sub, exp 등 이 문서에서 새로 정의하지 않고 예시와 설명에 사용하는 claim은 [JWT]에 정의되어 있다.¶

4.1. "act"(actor) claim

act(actor) claim은 JWT에서 delegation이 이루어졌음을 나타내고 권한을 위임받아 행동하는 당사자를 식별하는 수단이다. act claim의 값은 JSON 객체이며, 이 객체의 멤버는 actor를 식별하는 claim이다. act claim을 구성하는 claim은 actor를 식별하고, 경우에 따라 actor에 관한 추가 정보를 제공한다. 예를 들어 actor를 고유하게 식별하려면 iss와 sub 두 claim을 함께 사용해야 할 수도 있다.¶

그러나 act claim 안의 claim은 actor의 신원에만 관련되며, 최상위 claim과 달리 이를 포함한 JWT의 유효성과는 관련되지 않는다. 따라서 신원과 무관한 claim(예: exp, nbf, aud)은 act claim 안에서 의미가 없으므로 사용하지 않는다.¶

그림 5는 JWT claim 집합에 포함된 act(actor) claim의 예를 보여 준다. 토큰 자체의 claim은 user@example.com에 관한 것이고, act claim은 admin@example.com이 현재 actor임을 나타낸다.¶

한 act claim을 다른 것 안에 중첩하면 delegation이 이어진 과정을 표현할 수 있다. 가장 바깥쪽의 act claim은 현재 actor를 나타내고, 안에 중첩된 act claim은 이전 actor를 나타낸다. 가장 오래된 actor는 가장 깊은 곳에 중첩된다. 중첩된 act claim은 최초 요청과 토큰이 대표하는 당사자에서 출발해, 여러 delegation 단계를 거쳐 현재 actor에 이르기까지의 이력을 보여 준다. 이런 의미에서 현재 actor가 인가 및 delegation 이력 전체를 포함한다고 볼 수 있으며, 여기서 설명하는 중첩 구조는 그에 자연스럽게 따른다.¶

토큰을 사용하는 쪽이 접근 제어 정책을 적용할 때는 다음 요건을 따라야 한다(MUST). 토큰의 최상위 claim과 act claim이 현재 actor로 식별한 당사자만 고려해야 한다. 중첩된 act claim으로 식별되는 이전 actor는 정보 제공용일 뿐이며, 접근 제어 결정에서 고려하지 않는다.¶

그림 6의 예는 JWT claim 집합에 중첩된 act(actor) claim을 보여 준다. 토큰 자체의 claim은 user@example.com에 관한 것이고, act claim은 시스템 <https://service16.example.com>가 현재 actor이고 <https://service77.example.com>는 이전 actor였음을 나타낸다. 예를 들어 service16이 service77의 호출에서 토큰을 받아 service26을 호출하는 데 적합한 토큰으로 교환하고, authorization server가 이 상황을 새로 발급한 토큰에 기록하면 이러한 토큰이 만들어질 수 있다.¶

OAuth 토큰 Introspection 응답에 act 항목이 최상위 멤버로 포함되면, 이 항목의 의미와 형식은 같은 이름의 claim과 같다.¶

4.2. "scope"(scope) claim

scope claim의 값은 해당 토큰에 연결된 scope를 공백으로 구분해 나열한 JSON 문자열이며, 3.3절([RFC6749])에 설명된 형식을 따른다.¶

그림 7은 JWT claim 집합에 포함된 scope claim의 예를 보여 준다.¶

OAuth 2.0 Token Introspection [RFC7662]은 해당 토큰에 연결된 scope를 전달하는 매개변수 scope를 이미 정의하고 있다.¶

4.3. "client_id"(client 식별자) claim

client_id claim은 해당 토큰을 요청한 OAuth 2.0 [RFC6749] client의 식별자를 전달한다.¶

그림 8은 JWT claim 집합에 포함된 client_id claim의 예를 보여 준다. 이 claim은 식별자가 "s6BhdRkqt3"인 OAuth 2.0 client를 나타낸다.¶

OAuth 2.0 Token Introspection [RFC7662]은 client_id 매개변수를 해당 토큰을 요청한 OAuth 2.0 client의 식별자로 이미 정의하고 있다.¶

4.4. "may_act"(인가된 actor) claim

may_act claim은 한 당사자가 actor가 되어 다른 당사자를 대신해 행동할 권한이 있음을 명시한다. 예를 들어 토큰 교환 요청에서 subject_token이 token endpoint에 제시되면, authorization server는 subject token의 may_act claim을 사용해 client(또는 actor_token으로 식별되는 당사자)에게 요청된 delegation 또는 impersonation을 수행할 권한이 있는지 판단할 수 있다. 이 claim의 값은 JSON 객체이며, 객체의 멤버는 이 claim을 포함한 JWT가 식별하는 당사자를 대신해 행동할 자격이 있다고 명시된 당사자를 식별하는 claim이다. may_act claim을 구성하는 claim은 인가된 actor를 식별하고, 경우에 따라 그 actor에 관한 추가 정보를 제공한다. 예를 들어 인가된 actor를 고유하게 식별하려면 iss와 sub 두 claim을 함께 사용해야 하는 경우가 있으며, email claim으로 그 당사자에 관한 유용한 추가 정보를 제공할 수도 있다.¶

그러나 may_act claim 안의 claim은 그 당사자의 신원에만 관련되며, 최상위 claim과 달리 이를 포함한 JWT의 유효성과는 관련되지 않는다. 따라서 exp, nbf, aud 등의 claim은 may_act claim 안에서 의미가 없으므로 사용하지 않는다.¶

그림 9는 JWT claim 집합에 포함된 may_act claim의 예를 보여 준다. 토큰 자체의 claim은 user@example.com에 관한 것이고, may_act claim은 admin@example.com에게 user@example.com을 대신해 행동할 권한이 있음을 나타낸다.¶

OAuth 토큰 Introspection 응답에 may_act 항목이 최상위 멤버로 포함되면, 이 항목의 의미와 형식은 같은 이름의 claim과 같다.¶

5. 보안 고려사항

The OAuth 2.0 Authorization Framework의 보안 고려사항을 담은 10절([RFC6749]) 지침은 상당 부분 이 명세에도 적용된다. 또한 [RFC6819]는 OAuth의 추가 보안 고려사항을 제시하며, [OAUTH-SECURITY]에는 배포 경험과 OAuth 2.0 최초 발행 이후 등장한 새로운 위협을 반영해 갱신한 보안 지침이 담겨 있다.¶

[JWT]에서 다루는 일반적인 보안 문제는 모두 이 명세에도 적용되며, 특히 URI를 비교하거나 인식할 수 없는 값을 처리할 때 그렇다.¶

이와 별도로 delegation과 impersonation은 둘 다 특유의 보안 문제를 일으킨다. 한 principal이 다른 principal의 권한을 위임받을 때는 늘 남용 가능성을 우려해야 한다. scope claim은 위임된 권한을 행사할 수 있는 상황을 제한하므로, 남용 가능성을 줄이기 위해 토큰 수명 제한과 같은 일반적인 제약에 더해 이 claim을 사용하는 것이 제안된다.¶

6. 개인정보 보호 고려사항

이 문서에서 설명하는 기능에 쓰이는 토큰에는 개인정보 보호 측면에서 민감한 정보가 들어 있을 수 있다. 이러한 정보가 의도하지 않은 당사자에게 공개되지 않도록, 토큰은 Transport Layer Security(TLS)와 같이 암호화된 채널을 통해서만 전송해야 한다(MUST). 특정 정보가 client에 공개되지 않도록 하는 것이 바람직하다면, 지정된 수신자용으로 토큰을 암호화해야 한다(MUST). 배포 환경에서는 필요한 최소한의 데이터가 무엇인지 정하고, 발급하는 토큰에는 그 정보만 포함하는 것이 권고된다(SHOULD). 경우에 따라서는 익명 또는 가명 사용자만을 나타내는 방식도 데이터 최소화에 포함될 수 있다.¶

부록 A. 추가 토큰 교환 예시

다음 절에서는 impersonation과 delegation을 각각 보여 주는 두 가지 토큰 교환 예시를 제시한다(추가 줄바꿈과 들여쓰기는 표시를 위한 것일 뿐이다).¶

A.1. impersonation 토큰 교환 예시

A.1.1. 토큰 교환 요청

다음 토큰 교환 요청에서 client는 impersonation 방식으로 사용할 토큰을 요청한다(subject_token만 있고 actor_token이 없으면 delegation은 불가능하다). client는 논리 이름이 urn:example:cooperation-context인 대상 서비스에서 사용할 토큰이 필요하다고 authorization server에 알린다.¶

A.1.3. 토큰 교환 응답

access_token 매개변수는 아래에 제시한 토큰 교환 응답의 일부이며, client가 요청한 새 토큰을 담고 있다. 응답의 다른 매개변수는 이 토큰이 1시간 후 만료되는 bearer access token임을 나타낸다.¶

A.1.4. 발급된 토큰의 claim

발급된 토큰의 JWT Claims Set을 디코딩한 결과는 아래와 같다. 새 JWT는 authorization server가 발급하며, 논리 이름이 urn:example:cooperation-context인 시스템 주체가 만료 전까지 언제든 사용할 수 있도록 만들어졌다. JWT의 대상(sub)은 요청에 사용한 토큰의 대상과 같다. 따라서 client는 이 토큰을 사용해 논리 이름이 urn:example:cooperation-context인 시스템 주체에서 해당 대상인 것처럼 행동할 수 있다(impersonation).¶

A.2. delegation 토큰 교환 예시

A.2.1. 토큰 교환 요청

다음 토큰 교환 요청에서 client는 토큰을 요청하면서 subject_token과 actor_token을 모두 제공한다. client는 논리 이름이 urn:example:cooperation-context인 대상 서비스에서 사용할 토큰이 필요하다고 authorization server에 알린다. authorization server의 정책에 따라 발급되는 토큰은 composite token이어야 한다.¶

A.2.2. subject token의 claim

앞선 요청의 subject_token은 JWT이며, 디코딩한 JWT Claims Set을 여기에 제시한다. 이 JWT는 정해진 만료 시각 전에 authorization server가 사용하도록 만들어졌다. 새 토큰은 JWT의 대상(user@example.net)을 대신하여 요청한 것이다.¶

A.2.3. actor token의 claim

앞선 요청의 actor_token은 JWT이며, 디코딩한 JWT Claims Set을 여기에 제시한다. 이 JWT 역시 정해진 만료 시각 전에 authorization server가 사용하도록 만들어졌다. JWT의 대상(admin@example.net)은 요청 중인 security token을 사용할 actor다.¶

A.2.4. 토큰 교환 응답

access_token 매개변수는 아래에 제시한 토큰 교환 응답의 일부이며, client가 요청한 새 토큰을 담고 있다. 응답의 다른 매개변수는 이 토큰이 1시간 후 만료되는 JWT이며, 발급된 토큰이 access token이 아니므로 access token 유형은 적용되지 않음을 나타낸다.¶

A.2.5. 발급된 토큰의 claim

발급된 토큰의 JWT Claims Set을 디코딩한 결과는 아래와 같다. 새 JWT는 authorization server가 발급하며, 논리 이름이 urn:example:cooperation-context인 시스템 주체가 만료 전까지 언제든 사용할 수 있도록 만들어졌다. JWT의 대상(sub)은 요청에 사용한 subject_token의 대상과 같다. JWT의 actor(act)는 요청에 사용한 actor_token의 대상과 같다. 이는 delegation을 나타내며, 현재 actor인 admin@example.net에게 user@example.net을 대신해 행동할 권한이 위임되었음을 보여 준다.¶
