초록

이 명세는 OAuth 2.0 access token(접근 토큰)을 요청하거나 client authentication을 수행할 때 JSON Web Token (JWT) Bearer Token을 사용하는 방법을 정의한다.

1. 소개

JSON Web Token (JWT) [JWT]는 JSON 기반 [RFC7159] security token 인코딩으로, 서로 다른 보안 도메인 사이에서 신원 및 보안 정보를 공유할 수 있게 한다. security token은 일반적으로 Identity Provider가 발급하고 Relying Party가 사용한다. Relying Party는 보안 관련 목적에 따라 token의 내용을 바탕으로 그 subject를 식별한다.

OAuth 2.0 Authorization Framework [RFC6749]는 access token을 사용해 리소스에 인증된 HTTP 요청을 보내는 방법을 제공한다. authorization server(인가 서버)(AS)는 resource owner(리소스 소유자)의 승인(때로는 묵시적 승인)을 받아 제3자 client(클라이언트)에게 access token을 발급한다. OAuth에서 authorization grant는 resource owner의 인가를 나타내는 중간 credentials를 일컫는 추상적인 용어다. client는 authorization grant를 사용해 access token을 얻는다. 여러 유형의 client와 다양한 사용자 경험을 지원하기 위해 여러 authorization grant 유형이 정의되어 있다. 또한 OAuth에서는 다른 client를 지원하거나 OAuth를 다른 신뢰 프레임워크와 연계하기 위해 새로운 확장 grant 유형을 정의할 수 있다. 마지막으로 OAuth에서는 client가 authorization server와 상호작용할 때 사용할 추가 인증 방식도 정의할 수 있다.

"Assertion Framework for OAuth 2.0 Client Authentication and Authorization Grants" [RFC7521]는 OAuth 2.0의 추상적인 확장으로, OAuth 2.0에서 assertion(증명 정보)(즉, security token)을 client credentials, authorization grant 또는 두 용도로 사용하는 일반적인 프레임워크를 제공한다. 이 명세는 OAuth Assertion Framework [RFC7521]의 프로파일을 만들어, JWT Bearer Token을 사용해 OAuth 2.0 access token을 요청하는 확장 grant 유형을 정의하고 JWT Bearer Token을 client credentials로 사용하는 방법도 정의한다. 이 명세에서 정의하는 JWT의 형식과 처리 규칙은 밀접하게 관련된 명세인 "Security Assertion Markup Language (SAML) 2.0 Profile for OAuth 2.0 Client Authentication and Authorization Grants" [RFC7522]의 규칙과 의도적으로 유사하지만 동일하지는 않다. 차이는 JWT와 SAML assertion의 구조와 의미가 다른 지점에서 생긴다. 예를 들어 JWT에는 SAML assertion의 <SubjectConfirmation> 또는 <AuthnStatement> 요소에 직접 대응하는 요소가 없다.

이 문서는 client가 JWT의 의미 체계로 표현된 기존 신뢰 관계를 활용하여 authorization server에서 사용자가 직접 승인하는 단계 없이 access token을 요청하려 할 때, JWT Bearer Token을 사용하는 방법을 정의한다. 또한 JWT를 client authentication 수단으로 사용하는 방법도 정의한다. security token을 client authentication에 사용하는 것과 authorization grant로 사용하는 것은 서로 독립적이며 분리할 수 있다. 두 방식은 함께 사용할 수도, 따로 사용할 수도 있다. JWT를 이용한 client authentication은 client가 token endpoint(토큰 엔드포인트)에 자신의 신원을 인증하는 또 하나의 방법일 뿐이다. 완전하고 의미 있는 프로토콜 요청을 구성하려면 어떤 grant 유형과 반드시 함께 사용해야 한다. JWT authorization grant는 client authentication이나 client 식별을 수반할 수도, 수반하지 않을 수도 있다. JWT authorization grant와 함께 client authentication이 필요한지, 어떤 유형의 client authentication을 지원할지는 authorization server가 재량으로 정하는 정책이다.

client가 JWT를 authorization server와 교환하거나 client authentication에 사용하기 전에 그 JWT를 어떻게 얻는지는 이 문서의 범위를 벗어난다.

1.1. 표기 규칙

이 문서의 키워드 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", "OPTIONAL"는 RFC 2119 [RFC2119]에 명시된 대로 해석한다.

별도로 명시하지 않는 한, 모든 프로토콜 parameter의 이름과 값은 대소문자를 구분한다.

1.2. 용어

모든 용어는 다음 명세의 정의를 따른다. "The OAuth 2.0 Authorization Framework" [RFC6749], OAuth Assertion Framework [RFC7521], "JSON Web Token (JWT)" [JWT].

2. assertion 전송을 위한 HTTP parameter binding

OAuth Assertion Framework [RFC7521]는 token endpoint와 상호작용할 때 assertion(즉, security token)을 전송하기 위한 범용 HTTP parameter를 정의한다. 이 절에서는 JWT Bearer Token에 사용할 구체적인 parameter와 처리 방법을 정의한다.

2.1. JWT를 authorization grant로 사용

Bearer JWT를 authorization grant로 사용하려는 client는 OAuth Assertion Framework [RFC7521] 4절에 정의된 access token 요청에 다음 parameter 값과 인코딩을 적용한다.

"grant_type"의 값은 "urn:ietf:params:oauth:grant- type:jwt-bearer"이다.

복사용 urn:ietf:params:oauth:grant-type:jwt-bearer · §8.1 등록값

"assertion" parameter의 값에는 JWT를 정확히 하나만 포함해야 한다(MUST).

OAuth Assertion Framework [RFC7521]에 정의된 대로, 요청하는 범위를 나타내기 위해 "scope" parameter를 사용할 수 있다.

OAuth 2.0 [RFC6749] 3.2.1절에 명시된 대로 client authentication은 선택 사항이다. 따라서 "client_id"는 해당 parameter에 의존하는 client authentication 방식을 사용할 때만 필요하다.

다음 예시는 JWT를 authorization grant로 사용하는 access token 요청을 보여 준다(추가 줄바꿈은 표시를 위한 것일 뿐이다).

예제의 오른쪽은 좌우로 스크롤해서 볼 수 있습니다.

     POST /token.oauth2 HTTP/1.1
     Host: as.example.com
     Content-Type: application/x-www-form-urlencoded

     grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Ajwt-bearer
     &assertion=eyJhbGciOiJFUzI1NiIsImtpZCI6IjE2In0.
     eyJpc3Mi[...omitted for brevity...].
     J9l-ZhwP[...omitted for brevity...]

2.2. JWT를 client authentication에 사용

JWT Bearer Token을 client authentication에 사용하려는 client는 다음 parameter 값과 인코딩을 사용한다.

"client_assertion_type"의 값은 "urn:ietf:params:oauth:client-assertion-type:jwt-bearer"이다.

"client_assertion" parameter의 값에는 JWT가 하나 들어간다. JWT를 둘 이상 포함해서는 안 된다(MUST NOT).

다음 예시는 access token 요청에서 authorization code grant를 제시할 때 JWT를 이용해 client authentication을 수행하는 방법을 보여 준다(추가 줄바꿈은 표시를 위한 것일 뿐이다).

예제의 오른쪽은 좌우로 스크롤해서 볼 수 있습니다.

     POST /token.oauth2 HTTP/1.1
     Host: as.example.com
     Content-Type: application/x-www-form-urlencoded

     grant_type=authorization_code&
     code=n0esc3NRze7LTCu7iYzS6a5acc3f0ogp4&
     client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3A
     client-assertion-type%3Ajwt-bearer&
     client_assertion=eyJhbGciOiJSUzI1NiIsImtpZCI6IjIyIn0.
     eyJpc3Mi[...omitted for brevity...].
     cC4hiUPo[...omitted for brevity...]

3. JWT 형식 및 처리 요구사항

2026년 업데이트 · RFC 10070 §4

아래 번역과 예제는 2015년 발행본을 따릅니다. 최신 규칙에서는 client authentication용 JWT의 aud에 authorization server의 issuer identifier만 유일한 값으로 넣어야 합니다(MUST). token endpoint URL은 사용할 수 없고, 서버는 자기 issuer identifier가 유일한 값이 아닌 JWT를 거부해야 합니다(MUST).

authorization grant용 JWT는 다릅니다. 대상 서버를 적절히 식별하는 issuer identifier 또는 token endpoint URL을 사용할 수 있습니다(MAY). RFC 10070은 client authentication JWT의 typ 명시를 권고하고(SHOULD), §4의 예제도 업데이트합니다.

OAuth 2.0 [RFC6749]에 명시된 대로 access token 응답을 발행하거나 JWT를 client authentication의 근거로 삼으려면, authorization server는 아래 기준에 따라 JWT를 검증해야 한다(MUST). 추가 제한과 정책을 적용할지는 authorization server의 재량에 따른다.

1. JWT에는 해당 JWT를 발급한 개체의 고유 식별자를 담은 "iss"(issuer) claim이 있어야 한다(MUST). 달리 규정하는 애플리케이션 프로파일이 없다면, 이 명세를 준수하는 애플리케이션은 RFC 3986 [RFC3986] 6.2.1절에 정의된 Simple String Comparison 방식으로 issuer 값을 비교해야 한다(MUST).
2. JWT에는 그 JWT의 subject인 주체를 식별하는 "sub"(subject) claim이 있어야 한다(MUST). 다음 두 경우를 구분해야 한다.
A. authorization grant에서 subject는 대개 누구를 위해 access token을 요청하는지를 나타내며, 접근 권한이 있는 주체(즉, resource owner 또는 권한을 위임받은 자)를 식별한다. 다만 경우에 따라 가명 식별자 또는 익명 사용자를 나타내는 다른 값일 수도 있다.
B. client authentication에서 subject는 OAuth client의 "client_id"여야 한다(MUST).
3. JWT에는 authorization server가 의도된 audience임을 식별하는 값을 담은 "aud"(audience) claim이 있어야 한다(MUST). authorization server를 그 JWT의 의도된 audience로 식별하기 위해, 해당 서버의 token endpoint URL을 "aud" 요소의 값으로 사용할 수 있다(MAY). authorization server는 자신을 의도된 audience로 식별하는 값이 들어 있지 않은 JWT를 모두 거부해야 한다(MUST). 달리 규정하는 애플리케이션 프로파일이 없다면, 이 명세를 준수하는 애플리케이션은 RFC 3986 [RFC3986] 6.2.1절에 정의된 Simple String Comparison 방식으로 audience 값을 비교해야 한다(MUST). 5절에서 언급하듯, 특정 authorization server의 audience로 사용할 정확한 문자열은 authorization server와 JWT 발급자가 이 프로토콜 외부에서 설정해야 한다.
4. JWT에는 그 JWT를 사용할 수 있는 시간 범위를 제한하는 "exp"(expiration time) claim이 있어야 한다(MUST). authorization server는 시스템 간에 허용되는 clock skew를 감안하여 이미 만료 시각이 지난 JWT를 모두 거부해야 한다(MUST). 또한 "exp" claim의 값이 지나치게 먼 미래의 시각을 가리키는 JWT는 authorization server가 거부할 수 있다.
5. JWT에는 "nbf"(not before) claim을 포함할 수 있다(MAY). 이 claim이 가리키는 시각 전에는 token을 처리 대상으로 받아들여서는 안 된다(MUST NOT).
6. JWT에는 해당 JWT의 발급 시각을 나타내는 "iat"(issued at) claim을 포함할 수 있다(MAY). 또한 "iat" claim의 값이 지나치게 먼 과거의 시각을 가리키는 JWT는 authorization server가 거부할 수 있다.
7. JWT에는 token의 고유 식별자를 제공하는 "jti"(JWT ID) claim을 포함할 수 있다(MAY). authorization server는 해당 "exp" 시점을 기준으로 JWT가 유효하다고 간주되는 기간 동안 이미 사용한 "jti" 값의 집합을 유지하여 JWT의 replay를 방지할 수 있다(MAY).
8. JWT에는 다른 claim을 포함할 수 있다(MAY).
9. issuer는 JWT에 digital signature를 붙이거나 Message Authentication Code(MAC)를 적용해야 한다(MUST). authorization server는 signature 또는 MAC이 유효하지 않은 JWT를 거부해야 한다(MUST).
10. authorization server는 "JSON Web Token (JWT)" [JWT]에 따른 나머지 유효성 요건 중 하나라도 충족하지 못하는 JWT를 거부해야 한다(MUST).

3.1. authorization grant 처리

JWT authorization grant는 client authentication이나 client 식별을 수반하는지와 관계없이 사용할 수 있다. JWT authorization grant와 함께 client authentication이 필요한지 여부와 지원할 client authentication 유형은 authorization server가 재량에 따라 정책으로 결정한다. 다만 요청에 client credentials가 있으면 authorization server는 이를 검증해야 한다(MUST).

JWT가 유효하지 않거나 현재 시각이 token을 사용할 수 있는 유효 시간 범위를 벗어나면, authorization server는 OAuth 2.0 [RFC6749]에 정의된 대로 error response를 구성한다. "error" parameter의 값은 "invalid_grant" error code여야 한다(MUST). authorization server는 "error_description" 또는 "error_uri" parameter를 사용해 JWT를 유효하지 않다고 판단한 이유에 관한 추가 정보를 포함할 수 있다(MAY).

예를 들면 다음과 같다:

예제의 오른쪽은 좌우로 스크롤해서 볼 수 있습니다.

     HTTP/1.1 400 Bad Request
     Content-Type: application/json
     Cache-Control: no-store

     {
      "error":"invalid_grant",
      "error_description":"Audience validation failed"
     }

3.2. client authentication 처리

client의 JWT가 유효하지 않으면 authorization server는 OAuth 2.0 [RFC6749]에 정의된 대로 error response를 구성한다. "error" parameter의 값은 "invalid_client" error code여야 한다(MUST). authorization server는 "error_description" 또는 "error_uri" parameter를 사용해 JWT를 유효하지 않다고 판단한 이유에 관한 추가 정보를 포함할 수 있다(MAY).

4. authorization grant 예시

2015년 발행본 예제. 현재 명세의 갱신 예제는 RFC 10070 §4를 참고하세요.

다음은 이 명세를 준수하는 JWT와 access token 요청의 예시다.

이 예시는 "https://jwt-idp.example.com"로 식별되는 시스템 개체가 발급하고 서명한 JWT를 보여 준다. JWT의 subject는 이메일 주소 "mike@example.com"으로 식별된다. 이 JWT가 대상으로 하는 audience는 "https://jwt-rp.example.net"이며, 이는 authorization server가 자신을 식별하는 데 사용하는 식별자다. 이 JWT는 access token 요청의 일부로 authorization server의 token endpoint인 "https://authz.example.net/ token.oauth2"에 전송된다.

예제 주소 복사용 https://authz.example.net/token.oauth2

다음은 JWT Claims Set을 만들기 위해 인코딩할 수 있는 JSON 객체의 예다:

예제의 오른쪽은 좌우로 스크롤해서 볼 수 있습니다.

     {"iss":"https://jwt-idp.example.com",
      "sub":"mailto:mike@example.com",
      "aud":"https://jwt-rp.example.net",
      "nbf":1300815780,
      "exp":1300819380,
      "http://claims.example.com/member":true}

다음 JSON 객체는 JWT의 header 예시다. 이 header는 "kid" 값 "16"으로 식별되는 key를 사용해 Elliptic Curve Digital Signature Algorithm (ECDSA) P-256 SHA-256으로 JWT에 서명했음을 나타낸다.

예제의 오른쪽은 좌우로 스크롤해서 볼 수 있습니다.

     {"alg":"ES256","kid":"16"}

앞의 예시에 나온 claim과 header를 담은 JWT를 access token 요청의 일부로 제시하려면, client는 예를 들어 다음과 같은 HTTPS 요청을 보낼 수 있다(추가 줄바꿈은 표시용일 뿐이다):

예제의 오른쪽은 좌우로 스크롤해서 볼 수 있습니다.

     POST /token.oauth2 HTTP/1.1
     Host: authz.example.net
     Content-Type: application/x-www-form-urlencoded

     grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Ajwt-bearer
     &assertion=eyJhbGciOiJFUzI1NiIsImtpZCI6IjE2In0.
     eyJpc3Mi[...omitted for brevity...].
     J9l-ZhwP[...omitted for brevity...]

5. 상호운용성 고려 사항

2026년 업데이트. client authentication용 JWT에는 더 이상 audience 식별자를 사전 합의할 필요가 없습니다. RFC 10070 §4

이 profile을 배포한 시스템들이 서로 연동하려면 시스템 개체 간에 식별자, key, endpoint에 대한 합의가 필요하다. 구체적으로 합의해야 할 항목은 issuer 및 audience 식별자의 값, token endpoint의 위치, JWT에 digital signature 또는 MAC을 적용하고 검증하는 데 사용하는 key, JWT의 일회 사용 제한, 허용되는 JWT의 최대 유효 기간, JWT의 subject 및 claim에 대한 구체적인 요건이다. 이러한 정보의 교환은 명시적으로 이 명세의 범위에 포함되지 않는다. 경우에 따라 이러한 값을 제한하거나 규정하는 추가 profile을 만들거나, 해당 값을 교환하는 방법을 추가 profile에서 정할 수 있다. 이러한 profile의 예로는 OAuth 2.0 Dynamic Client Registration Core Protocol [OAUTH-DYN-REG], OpenID Connect Dynamic Client Registration 1.0 [OpenID.Registration], OpenID Connect Discovery 1.0 [OpenID.Discovery]가 있다.

[JWA]의 "RS256"은 이 profile에서 반드시 구현해야 하는 JSON Web Signature 알고리즘이다.

6. 보안 고려 사항

다음 명세에 기술된 보안 고려 사항은 모두 이 문서에도 적용된다. "Assertion Framework for OAuth 2.0 Client Authentication and Authorization Grants" [RFC7521], "The OAuth 2.0 Authorization Framework" [RFC6749], "JSON Web Token (JWT)" [JWT].

이 명세는 JWT를 authorization grant에 사용하든 client authentication에 사용하든 replay protection을 의무화하지 않는다. replay protection은 각 구현에서 재량에 따라 적용할 수 있는 선택 기능이다.

7. 개인정보 보호 고려 사항

JWT에는 프라이버시 측면에서 민감한 정보가 들어 있을 수 있으므로, 그런 정보가 의도하지 않은 상대에게 공개되지 않도록 Transport Layer Security (TLS)와 같은 암호화 채널로만 전송하는 것이 바람직하다. 특정 정보를 client에게 공개하지 않는 편이 바람직한 경우에는 authorization server를 수신 대상으로 하여 JWT를 암호화하는 것이 바람직하다.

각 배포 환경에서는 교환을 완료하는 데 필요한 최소한의 정보를 정하고, 이에 해당하는 claim만 JWT에 포함하는 것이 바람직하다. 경우에 따라 OAuth Assertion Framework [RFC7521]의 6.3.1절에 설명된 것처럼, "sub"(subject) claim에 익명 또는 가명 사용자를 나타내는 값을 쓸 수 있다.

8. IANA 고려 사항

8.1. urn:ietf:params:oauth:grant-type:jwt-bearer 하위 namespace 등록

이 절에서는 "An IETF URN Sub-Namespace for OAuth" [RFC6755]에서 신설한 IANA의 "OAuth URI" registry에 "grant-type:jwt-bearer" 값을 등록한다.

o URN: urn:ietf:params:oauth:grant-type:jwt-bearer

o 일반 명칭: JWT Bearer Token Grant Type Profile for OAuth 2.0

o 변경 관리 주체: IESG

o 명세 문서: RFC 7523

8.2. urn:ietf:params:oauth:client-assertion-type:jwt-bearer 하위 namespace 등록

이 절에서는 "An IETF URN Sub-Namespace for OAuth" [RFC6755]에서 신설한 IANA의 "OAuth URI" registry에 "client-assertion-type:jwt-bearer" 값을 등록한다.

o URN: urn:ietf:params:oauth:client-assertion-type:jwt-bearer

o 일반 명칭: JWT Bearer Token Profile for OAuth 2.0 Client Authentication

o 변경 관리 주체: IESG

o 명세 문서: RFC 7523
