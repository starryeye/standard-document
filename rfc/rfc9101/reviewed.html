초록

RFC 6749에서 설명하는 OAuth 2.0 인가 요청은 쿼리 매개변수 직렬화를 사용한다. 즉, 인가 요청 매개변수를 요청 URI에 인코딩한 뒤 웹 브라우저와 같은 user agent(사용자 에이전트)를 통해 전송한다. 구현하기는 쉽지만, a) user agent를 거치는 통신의 무결성이 보호되지 않아 매개변수가 변조될 수 있고, b) 통신 출처가 인증되지 않으며, c) user agent를 거치는 통신이 감시될 수 있다. 이러한 약점 때문에 이 프로토콜에 대한 여러 공격이 제기되었다.¶

이 문서는 그 대신 요청 매개변수를 JSON Web Token(JSON 웹 토큰) (JWT)에 담아 전송하는 방식을 도입한다. 요청에 JSON Web Signature(JSON 웹 서명) (JWS)로 서명하고 JSON Web Encryption(JSON 웹 암호화) (JWE)으로 암호화할 수 있으므로 인가 요청의 무결성, 출처 인증 및 기밀성을 확보할 수 있다. 요청은 값으로 전달하거나 참조로 전달할 수 있다.¶

1. 소개

OAuth 2.0 [RFC6749]의 인가 요청은 쿼리 매개변수를 직렬화하는 방식을 사용하며, 일반적으로 웹 브라우저와 같은 user agent를 통해 전송된다.¶

예를 들어 response_type, client_id, state 및 redirect_uri 매개변수는 다음과 같이 요청 URI에 인코딩된다.¶

    GET /authorize?response_type=code&client_id=s6BhdRkqt3&state=xyz
    &redirect_uri=https%3A%2F%2Fclient%2Eexample%2Ecom%2Fcb HTTP/1.1
    Host: server.example.com
¶

URI에 인코딩하는 방식은 구현하기 쉽지만, 기밀성과 무결성을 보장하기 위해 애플리케이션 계층 보안을 적용할 수는 없다. TLS는 client와 user agent 사이, 그리고 user agent와 authorization server 사이의 통신을 보호하지만, TLS 세션은 user agent에서 종단된다. 또한 일부 중간 장비(예: 로드 밸런서)에서 TLS 세션이 더 일찍 종단될 수도 있다.¶

그 결과 [RFC6749]의 인가 요청에는 다음과 같은 한계가 있다.¶

(a)
user agent를 거치는 통신은 무결성이 보호되지 않아 매개변수가 변조될 수 있다(무결성 보호 실패).¶
(b)
통신의 출처가 인증되지 않는다(출처 인증 실패).¶
(c)
user agent를 거치는 통신은 감시될 수 있다(노출 방지 및 기밀성 보호 실패).¶

이러한 구조적 약점으로 인해 redirect URI(리디렉션 URI) 재작성 등 프로토콜을 대상으로 하는 여러 공격이 확인되었다.¶

애플리케이션 계층 보안을 적용하면 이러한 문제를 완화할 수 있다.¶

애플리케이션 계층 보안을 적용하면 신뢰할 수 있는 제3자가 요청을 준비하여, client 애플리케이션이 사전에 합의한 범위를 넘어서는 권한을 요청하지 못하도록 할 수 있다.¶

또한 요청을 참조로 전달하면 네트워크 전송 오버헤드를 줄일 수 있다.¶

JWT [RFC7519] 인코딩을 선택한 이유는 다음과 같다.¶

(1)
OAuth 응답 형식으로 쓰이는 JSON과 밀접하게 연관되어 있다.¶
(2)
텍스트 기반이므로 개발자가 다루기 쉽다.¶
(3)
XML보다 상대적으로 간결하다.¶
(4)
관련 서명 및 암호화 방식과 함께 Proposed Standard(제안 표준) 단계에 있다. [RFC7515] [RFC7516]¶
(5)
JWS와 JWE는 XML 서명 및 암호화 방식보다 상대적으로 사용하기 쉽다.¶

request와 request_uri는 OAuth 2.0 [RFC6749] 흐름에 인가 요청 매개변수로 추가된다. request 매개변수는 JSON Web Token (JWT) [RFC7519]이며, 그 JWT Claims Set(JWT 클레임 집합)에는 JSON으로 인코딩된 OAuth 2.0 인가 요청 매개변수가 담긴다. RFC 7519와 달리, 이 JWT Claims Set의 요소는 인코딩된 OAuth 요청 매개변수 [IANA.OAuth.Parameters]에 IANA가 관리하는 JSON Web Token 클레임 [IANA.JWT.Claims] 중 몇 가지(특히 iss와 aud)만 보탠 것이다. JWS를 사용해 request 매개변수에 담긴 JWT의 무결성을 보호하고 출처를 인증한다.¶

JWT [RFC7519]를 authorization endpoint(인가 엔드포인트)에 참조로 전달할 수도 있다. 이 경우에는 request_uri 매개변수를 사용하며 request 매개변수는 사용하지 않는다.¶

쿼리 매개변수 대신 JWT [RFC7519]로 요청을 인코딩하면 다음과 같은 이점이 있다.¶

(a)
무결성 보호. 요청에 서명하여 요청의 무결성을 확인할 수 있다.¶
(b)
출처 인증. 요청에 서명하여 서명자를 인증할 수 있다.¶
(c)
기밀성 보호. 요청을 암호화하면 TLS 연결이 경로상의 어느 지점에서 종단되더라도(user agent나 그에 이르기 전의 지점을 포함) 종단 간 기밀성을 보장할 수 있다.¶
(d)
수집 최소화. 신뢰할 수 있는 제3자가 요청에 서명하여 인가 요청이 특정 정책을 준수한다는 사실을 증명할 수 있다. 예를 들어, 신뢰할 수 있는 제3자가 요청을 사전에 검토해 요청된 모든 개인정보가 최종 사용자가 요청한 절차를 수행하는 데 반드시 필요한지 확인한 뒤 해당 요청에 서명할 수 있다. 그러면 authorization server가 서명을 검증하고 정책 준수 여부를 최종 사용자에게 표시한다. 최종 사용자는 이를 통해 요청을 인가할 때 그 정당성에 대해 어느 정도 확신할 수 있다. 상황에 따라서는 이 경우 인가 대화 상자를 아예 생략하는 것이 바람직할 수도 있다.¶

다음과 같은 경우에는 요청을 참조로 전달하는 방식이 유용하다.¶

  1. 전송할 요청의 크기를 줄이는 것이 바람직한 경우. 애플리케이션 계층 보안을 적용하면 요청이 커지며, 공개 키 암호 기술을 사용할 때 특히 그렇다.¶
  2. client가 애플리케이션 계층의 암호 처리를 직접 수행하고 싶지 않은 경우. 이 경우 authorization server는 client와 직접 통신하여 인가 요청을 받는 엔드포인트를 제공할 수 있다. 이렇게 하면 client는 인증되고 통신 채널은 TLS로 보호된다.¶

OpenID Connect [OpenID.Core]에서 이 기능을 사용한다.¶

1.1. 요구사항 표현

이 문서에서 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY" 및 "OPTIONAL"이라는 키워드들은 BCP 14 [RFC2119] [RFC8174]에 명시된 대로 해석하되, 여기서처럼 모두 대문자로 표기된 경우에만 그렇게 해석한다.¶

2. 용어

이 명세에서는 OAuth 2.0 프레임워크 [RFC6749], JSON Web Signature [RFC7515] 및 JSON Web Encryption [RFC7516]에 정의된 내용에 더해 다음 용어와 정의를 적용한다.¶

2.1. Request Object

Request Object는 JSON Web Token (JWT) [RFC7519]이며, 그 JWT Claims Set에는 JSON으로 인코딩된 OAuth 2.0 인가 요청 매개변수가 담긴다.¶

2.2. Request Object URI

Request Object URI는 OAuth 2.0 인가 요청을 구성하는 매개변수 집합을 참조하는 절대 URI이다. 이 URI가 참조하는 리소스의 내용은 Request Object(2.1절)이다. 다만 그 URI를 소비하는 authorization server가 client에 해당 URI를 직접 제공했다면, 그 내용은 해당 authorization server가 재량에 따라 정할 구현 세부사항이다. 내용을 Request Object로 정한 것은 request_uri의 제공자와 소비자가 서로 다른 주체일 때 상호운용성을 보장하기 위해서다. 예를 들어 client가 자신의 백엔드 서비스에 저장해 HTTPS로 접근할 수 있게 한 Request Object를 가리키는 URI를 제공하는 경우가 이에 해당한다. 반대로 authorization server가 Request Object를 받아 그 대가로 URI를 발급하는 엔드포인트를 제공하는 등 URI의 제공자이자 소비자라면, 이러한 상호운용성 문제는 적용되지 않는다.¶

4. Request Object

Request Object(2.1절)는 OAuth 2.0 인가 요청에 필요한 인가 요청 매개변수를 제공하는 데 사용된다. 이 객체에 적용되는 필수 요건(MUST)은 OAuth 2.0 [RFC6749] 인가 요청을 처리하는 데 쓰이는 모든 매개변수(확장 매개변수 포함)를 담되, 이 문서에서 정의하는 request와 request_uri 매개변수는 제외하는 것이다. 각 매개변수는 객체의 JWT 클레임으로 표현된다. 매개변수 이름과 문자열 값은 JSON 문자열로 포함해야 한다(MUST). Request Object는 여러 도메인에 걸쳐 처리되며 폐쇄된 생태계 바깥에서도 처리될 수 있으므로, 8.1절([RFC8259])에 따라 이 JSON 문자열은 반드시(MUST) UTF-8 [RFC3629]로 인코딩해야 한다. 수치는 JSON 숫자로 포함해야 한다(MUST). Request Object에는 어떤 확장 매개변수든 포함할 수 있다(MAY). 이 JSON [RFC8259] 객체는 JWT [RFC7519]에 정의된 JWT Claims Set을 이룬다. 그런 다음 JWT Claims Set에 서명하거나, 서명한 뒤 암호화한다.¶

서명에는 JSON Web Signature (JWS) [RFC7515]를 사용한다. 그 결과는 JWS로 서명된 JWT [RFC7519]다. 인가 요청의 Request Object에 서명하는 경우, 권장 사항(SHOULD)은 그 멤버로 iss(issuer(발급자))와 aud(audience(의도된 수신자)) 클레임을 포함하는 것이다. 두 클레임의 의미는 JWT [RFC7519] 명세에서 정의하는 의미와 같다. aud의 값은 authorization server(AS)의 issuer 값으로 하는 것이 바람직하다. 이 값은 RFC 8414 [RFC8414]에서 정의한다.¶

암호화에는 JWE [RFC7516]를 사용한다. 서명과 암호화를 모두 적용할 경우 JWT를 반드시(MUST) 먼저 서명한 뒤 암호화해야 한다. 이 절차는 11.2절([RFC7519])에 설명되어 있다. 그 결과는 Nested JWT이며, 이는 [RFC7519]에서 정의한다.¶

client는 Request Object를 서명하고 암호화하는 데 사용할 알고리즘을 결정한다. 선택한 알고리즘은 client와 authorization server가 모두 지원해야 한다. client는 동적 client 등록 메타데이터 [RFC7591], 구체적으로 request_object_signing_alg, request_object_encryption_alg, request_object_encryption_enc 메타데이터 값을 통해 자신이 지원하는 알고리즘을 authorization server에 알릴 수 있다. 마찬가지로 authorization server는 authorization server 메타데이터 [RFC8414], 구체적으로 request_object_signing_alg_values_supported, request_object_encryption_alg_values_supported, request_object_encryption_enc_values_supported 메타데이터 값을 통해 자신이 지원하는 알고리즘을 client에 알릴 수 있다.¶

Request Object는 두 방식으로 보낼 수 있다(MAY). 5.1절에서 설명하는 것처럼 값으로 전달하거나, 5.2절에서 설명하는 것처럼 참조로 전달한다. request와 request_uri 매개변수는 Request Object에 포함해서는 안 된다(MUST NOT).¶

5. 인가 요청

client는 authorization endpoint URI의 쿼리 구성 요소에 다음 매개변수를 application/x-www-form-urlencoded 형식으로 추가해 인가 요청 URI를 구성한다.¶

request
필수(REQUIRED) 매개변수다. 단, request_uri를 지정한 경우는 예외다. 이 매개변수의 값은 Request Object(2.1절)이며, 4절([RFC6749])(OAuth 2.0)에 명시된 인가 요청 매개변수를 담는다. 인가 요청에 이 매개변수가 있으면 request_uri는 포함해서는 안 된다(MUST NOT).¶
request_uri
필수(REQUIRED) 매개변수다. 단, request를 지정한 경우는 예외다. 이 값은 RFC 3986 [RFC3986]에서 정의하는 절대 URI로, Request Object URI(2.2절)에 해당한다. 이 URI는 4절([RFC6749])(OAuth 2.0)에 명시된 인가 요청 매개변수를 참조한다. 인가 요청에 이 매개변수가 있으면 request는 포함해서는 안 된다(MUST NOT).¶
client_id
필수(REQUIRED) 매개변수다. OAuth 2.0 [RFC6749]의 client_id다. 이 값은 반드시(MUST) request 또는 request_uri에 해당하는 Request Object(2.1절)의 client_id 값과 일치해야 한다.¶

client는 HTTP 리디렉션 응답이나 user agent를 통해 이용할 수 있는 다른 수단을 사용해, 앞서 구성한 URI로 resource owner(리소스 소유자)를 안내한다.¶

예를 들어 client는 최종 사용자의 user agent가 다음 HTTPS 요청을 보내도록 한다.¶

GET /authz?client_id=s6BhdRkqt3&request=eyJhbG..AlMGzw HTTP/1.1
Host: server.example.com
¶

간결하게 보여 주기 위해 request 매개변수의 값은 줄여 표시했다.¶

인가 요청의 Request Object는 반드시(MUST) 다음 중 하나여야 한다.¶

(a)
JWS로 서명됨¶
(b)
JWS로 서명되고 JWE로 암호화됨¶

6. JWT 기반 요청 검증

6.1. JWE로 암호화한 Request Object

Request Object가 암호화되어 있다면 authorization server는 반드시(MUST) JSON Web Encryption [RFC7516] 명세에 따라 JWT를 복호화해야 한다.¶

그 결과는 서명된 Request Object다.¶

복호화에 실패하면 authorization server는 반드시(MUST) 인가 요청에 대한 응답으로 invalid_request_object 오류를 client에 반환해야 한다.¶

6.2. JWS로 서명한 Request Object

authorization server는 반드시(MUST) JWS로 서명한 [RFC7515] Request Object의 서명을 검증해야 한다. kid 헤더 매개변수가 있으면, 이 매개변수가 가리키는 키를 반드시(MUST) 사용해야 하며 그 키는 반드시(MUST) client와 연결된 키여야 한다. 서명은 반드시(MUST) client와 연결된 키와 alg 헤더 매개변수에 지정된 알고리즘을 사용해 검증해야 한다. 알고리즘도 반드시(MUST) 제3.1절 및 제3.2절([RFC8725])의 규정에 따라 검증해야 한다.¶

키가 client와 연결되어 있지 않거나 서명 검증에 실패하면, authorization server는 인가 요청에 대한 응답으로 반드시(MUST) client에 invalid_request_object 오류를 반환해야 한다.¶

6.3. 요청 매개변수 구성 및 검증

authorization server는 반드시(MUST) Request Object 값에서 인가 요청 매개변수의 집합을 추출해야 한다. 쿼리 매개변수로 같은 매개변수가 제공되더라도 authorization server는 반드시(MUST) Request Object의 매개변수만 사용해야 한다. client_id 요청 매개변수와 Request Object의 client_id 클레임에 담긴 client ID 값은 반드시(MUST) 일치해야 한다. 그런 다음 authorization server는 OAuth 2.0 [RFC6749]의 규정에 따라 요청을 검증한다.¶

client ID 확인이나 요청 검증에 실패하면, authorization server는 반드시(MUST) 제5.2절 ([RFC6749])(OAuth 2.0)의 규정에 따라 인가 요청에 대한 응답으로 client에 오류를 반환해야 한다.¶

7. authorization server의 응답

authorization server는 제4절 ([RFC6749])(OAuth 2.0)의 절차에 따라 응답을 생성하여 client에 보낸다.¶

이 문서는 다음 오류 값도 사용한다.¶

invalid_request_uri
인가 요청의 request_uri가 오류를 반환하거나 유효하지 않은 데이터를 담고 있다.¶
invalid_request_object
request 매개변수에 유효하지 않은 Request Object가 들어 있다.¶
request_not_supported
authorization server가 request 매개변수 사용을 지원하지 않는다.¶
request_uri_not_supported
authorization server가 request_uri 매개변수 사용을 지원하지 않는다.¶

8. TLS 요구사항

Request Object URI 방식을 지원하는 client 구현은 반드시(MUST) "Recommendations for Secure Use of Transport Layer Security (TLS) and Datagram Transport Layer Security (DTLS)" [RFC7525]의 권고에 따라 TLS를 지원해야 한다.¶

정보 노출과 변조를 막으려면 반드시(MUST) 기밀성과 무결성을 보호하는 암호 스위트를 갖춘 TLS를 사용해 기밀성을 보호해야 한다.¶

HTTP client는 중간자 공격을 방지하기 위해 반드시(MUST) DNS-ID [RFC6125]를 사용해 TLS 서버 인증서도 검증해야 한다. 여기에는 [RFC6125]에 정의된 규칙과 지침이 적용되며, 다음 사항을 고려한다.¶

  • DNS-ID 식별자 유형(즉, subjectAltName 확장의 dNSName 식별자)은 반드시 지원해야 한다(REQUIRED). 서버 인증서를 발급하는 인증 기관은 반드시(MUST) DNS-ID 식별자 유형을 지원해야 하며, 서버 인증서에는 반드시(MUST) DNS-ID 식별자 유형이 포함되어야 한다.¶
  • 서버 인증서의 DNS 이름에는 다음 와일드카드 문자가 포함될 수 있다(MAY): *.¶
  • client는 CN-ID 식별자를 사용해서는 안 된다(MUST NOT). 서버 인증서의 주체 이름에 Common Name 필드(CN 필드)가 있을 수 있지만, 인증에는 이 필드를 사용해서는 안 된다(MUST NOT). 이는 [RFC7525]에 기술된 규칙의 범위에서 적용된다.¶
  • 제6.5절 ([RFC6125])에 기술된 SRV-ID와 URI-ID는 비교에 사용해서는 안 된다(MUST NOT).¶

10. 보안 고려사항

OAuth 2.0에서 논의한 보안 고려사항 [RFC6819]을 모두 검토하고, [RFC7515], [RFC7516], [RFC7518], [RFC8725]의 보안 고려사항도 검토해야 한다. 또한 [BASIN] 등 여러 학술 논문은 OAuth와 같은 프로토콜의 보안 특성을 이해하는 데 유용한 통찰을 제공한다.¶

이상을 바탕으로 이 문서는 다음과 같은 보안 고려사항을 검토할 것을 권고한다.¶

10.1. 알고리즘 선택

request 매개변수로 Request Object를 보낼 때는 다음 두 방식 중 하나를 반드시 적용해야 한다(MUST). JWS [RFC7515]로 서명하거나, JWS [RFC7515]로 서명한 뒤 JWE [RFC7516]로 암호화한다. 이때 각 작업에는 당시 적절하다고 여겨지는 알고리즘을 사용한다.¶

10.2. 요청 출처 인증

인가 요청의 출처는 항상 검증해야 한다(MUST). 검증하는 방법은 여러 가지다.¶

(a)
Request Object의 JWS 서명을 검증한다.¶
(b)
JWE가 대칭키 암호화를 사용한다면 JWE 암호화에 쓰인 대칭키가 올바른지 검증한다. 다만 공개 키 암호화를 사용하는 경우에는 누구나 공개 키로 암호화할 수 있으므로 암호화만으로는 출처를 인증할 수 없다.¶
(c)
Request Object URI에 해당하는 TLS 서버의 신원을 검증한다. 이 경우 authorization server는 client가 해당 Request Object URI를 사용하며 그 TLS 인증서가 해당 client에만 적용된다는 사실을 별도 경로로 알고 있어야 한다(MUST). 일반적으로 이 방법은 신뢰하기 어렵다.¶
(d)
authorization server가 Request Object를 받아 그 대가로 Request Object URI를 반환하는 서비스를 구현하는 경우, Request Object를 수락하려면 client authentication(클라이언트 인증)을 수행하고 제공하는 Request Object URI에 client 식별자를 연결해야 한다(MUST). 또한 (a)에 따라 서명을 검증해야 한다(MUST). Request Object URI는 재사용될 수 있으므로 유효 기간을 짧게 해야 하며(MUST), 가급적 한 번만 사용할 수 있게 한다. Request Object URI의 엔트로피는 충분히 커야 한다(MUST). 유효 기간을 얼마나 짧게 해야 하는지와 Request Object URI에 필요한 엔트로피는 보호할 리소스의 가치를 바탕으로 산정한 위험도에 따라 달라진다. 일반적으로 유효 기간은 1분 미만으로 하고, 이 명세를 작성하는 시점의 기준으로 Request Object URI에는 128비트 이상의 암호학적 난수를 포함한다.¶
(e)
신뢰할 수 있는 제3자 서비스가 Request Object를 받아 그 대가로 Request Object URI를 반환하는 경우, 이 서비스는 (a)에 따라 서명을 검증해야 한다(MUST). 또한 authorization server는 해당 제3자 서비스의 신뢰를 받아야 하며(MUST), 그 서비스가 client 역시 신뢰한다는 사실을 별도 경로로 알고 있어야 한다(MUST).¶

10.3. 명시적 엔드포인트

이 명세에서 요구하는 것은 아니지만, [BASIN] 등의 연구는 상호작용에 사용할 엔드포인트와 교환 순서에서 메시지가 차지하는 위치를 변조 여부를 알아낼 수 있는 방식으로 명시하면, 상호작용을 시작한 주체의 의도를 모호하지 않게 전달할 수 있다고 지적한다. 이 명세는 이 관행을 적용할 것을 권고한다(RECOMMENDED). 그 대상은 [RFC6749], [RFC6750], [RFC8414]에 정의된 다음 엔드포인트다:¶

(a)
보호된 리소스(protected_resources)¶
(b)
authorization endpoint(authorization_endpoint)¶
(c)
redirect URI(redirect_uri)¶
(d)
token endpoint(토큰 엔드포인트)(token_endpoint)¶

또한 동적 검색을 사용하는 경우 이 관행은 검색 관련 엔드포인트에도 적용된다.¶

[RFC6749]에서는 redirect URI가 인가 요청에 포함되지만 다른 엔드포인트는 포함되지 않는다. 따라서 Request Object에도 동일하게 적용된다.¶

10.4. request_uri 관련 위험

request_uri를 도입하면 여러 유형의 공격이 가능해진다. URI 관련 위험을 자세히 알아보려면 7절([RFC3986])의 보안 고려사항을 참조한다.¶

10.4.1. authorization server에 대한 DDoS 공격

여러 악성 client가 request_uri가 매우 큰 콘텐츠를 반환하거나 응답이 매우 느린 URI를 가리키도록 하여 authorization server에 DoS 공격을 가할 수 있다. 이런 공격을 받으면 서버 리소스가 고갈되어 장애가 발생하기 시작할 수 있다.¶

이와 비슷하게 악성 client는 request_uri 값이 다시 request_uri를 사용하는 인가 요청 URI를 가리키도록 지정하여 재귀 조회를 일으킬 수 있다.¶

이러한 공격을 막으려면 서버는 a) request_uri 매개변수의 값이 예상하지 않은 위치를 가리키지 않는지 확인하고, b) 응답의 미디어 유형이 application/oauth-authz-req+jwt인지 확인하며, c) request_uri의 콘텐츠를 가져오는 작업에 시간 제한을 두고, d) request_uri에 대해 재귀적으로 GET을 수행하지 않는 것이 좋다.¶

10.4.2. 요청 URI 재작성

request_uri 값은 서명되지 않으므로 브라우저 내부에서 개입하는 공격자(man-in-the-browser)가 이를 변조할 수 있다. 이 때문에 여러 유형의 공격이 가능하다. 예를 들어, a) 공격자는 재작성된 URI가 가리키는 다른 파일을 만들어 추가 범위(scope)를 요청할 수 있게 하거나, b) request_uri 값에 피해 사이트의 URI를 설정하여 그 사이트에 DoS 공격을 가할 수 있다.¶

이러한 공격을 막으려면 서버는 a) request_uri 매개변수의 값이 예상하지 않은 위치를 가리키지 않는지 확인하고, b) 응답의 미디어 유형이 application/oauth-authz-req+jwt인지 확인하며, c) request_uri의 콘텐츠를 가져오는 작업에 시간 제한을 두는 것이 좋다.¶

10.5. 다운그레이드 공격

client와 서버가 사용하는 프로토콜에서 OAuth의 JWT로 보호하는 인가 요청(JAR)만 사용하도록 제한하지 않으면, 공격자는 RFC 6749 요청을 사용해 이 명세가 제공하는 모든 보호 조치를 우회할 수 있다.¶

이러한 유형의 공격을 방지하기 위해 이 명세는 client와 서버의 메타데이터에 각각 새 항목을 정의한다. 두 항목 모두 이름은 require_signed_request_object이고, 값은 불리언이다.¶

client 메타데이터에 이 값이 true로 설정되어 있으면, 해당 client가 보낸 인가 요청이 이 명세를 준수하지 않을 때 서버는 이를 거부해야 한다(MUST). 다음 경우에도 서버는 요청을 거부해야 한다(MUST). Request Object의 alg 값이 none이고 이 서버 메타데이터 값이 true인 경우다. 생략 시 기본값은 false다.¶

서버 메타데이터에 이 값이 true로 설정되어 있으면, 어느 client가 보냈든 이 명세를 준수하지 않는 인가 요청을 서버는 거부해야 한다(MUST). 이 설정에서는 다음 경우에도 서버가 요청을 거부해야 한다(MUST). Request Object의 alg 값이 none인 경우다. 생략 시 기본값은 false다.¶

require_signed_request_object 메타데이터 값이 없어도, client와 서버가 공통으로 지원하는 서명 알고리즘이 있다면 client는 서명된 Request Object를 사용할 수 있다(MAY). 서명 알고리즘 메타데이터의 사용 방법은 4절에서 설명한다.¶

10.6. TLS 보안 고려사항

현재의 보안 고려사항은 ‘Recommendations for Secure Use of Transport Layer Security (TLS) and Datagram Transport Layer Security (DTLS)’ [RFC7525]에서 확인할 수 있다. 이 문서는 OAuth 2.0 [RFC6749]의 TLS 버전 권고를 대체한다.¶

10.7. 매개변수 불일치

OAuth 매개변수 값은 일반 OAuth 매개변수와 Request Object의 클레임이라는 두 곳에서 전송되므로, 구현에서는 서로 일치하지 않는 매개변수 값을 이용해 의도하지 않은 결과를 얻으려는 공격을 막아야 한다. 따라서 두 client ID 값은 일치해야 하고(MUST), Request Object의 매개변수 값만 사용해야 하며, request와 request_uri는 모두 Request Object에 나타날 수 없다.¶

10.8. Cross-JWT Confusion

2.8절([RFC8725])에서 설명하듯, 공격자는 특정 목적으로 발급된 JWT를 원래 의도하지 않은 맥락에서 사용하려 할 수 있다. 이 공격에 대해 제시된 완화책은 Request Object에도 적용할 수 있다.¶

공격자가 Request Object를 다른 용도로 전용하는 한 가지 방법은 이를 client authentication JWT로 사용해 보는 것이다. client authentication JWT는 2.2절([RFC7523])에서 설명한다. 이를 막는 간단한 방법은 client ID를 Request Object의 sub 값으로 절대 사용하지 않는 것이다.¶

Cross-JWT Confusion을 방지하는 또 다른 방법은 3.11절([RFC8725])에서 설명하는 것처럼 타입을 명시하는 것이다. Request Object의 타입을 명시하려면 typ 헤더 매개변수를 포함하고 그 값을 oauth-authz-req+jwt(9.4.1절에서 등록한 값)로 설정한다. 다만 기존 authorization server에서 Request Object의 타입 명시를 의무화하면 기존 배포 환경 대부분이 제대로 작동하지 않게 된다. 특히 OpenID Connect [OpenID.Core]를 사용하는 경우, 기존 client는 이미 타입을 명시하지 않은 Request Object를 널리 사용하고 있기 때문이다. 반면 기존 배포 환경과의 호환성을 고려할 필요가 없는 새로운 OAuth 배포 프로파일에서는 타입 명시를 의무화하는 편이 좋다.¶

마지막으로 Cross-JWT Confusion을 방지하는 또 다른 방법은 Request Object에 서명하는 키를 다른 용도의 키와 명확히 구별할 수 있는 키 관리 체계를 사용하는 것이다. 그러면 공격자가 Request Object를 다른 맥락에서 다른 용도로 사용하려 하더라도 키가 일치하지 않아 공격을 막을 수 있다.¶

11. 개인정보 보호 고려사항

client에 개인정보가 포함된 보호 리소스에 대한 접근 권한을 부여할 때는 client와 authorization server 모두 개인정보 보호 원칙을 준수해야 한다. "Privacy Considerations for Internet Protocols" [RFC6973]는 프로토콜의 설계와 구현을 개선하는 데 유용한 지침을 제공한다. 그 문서에 열거된 규정을 따르는 것이 바람직하다.¶

이들 규정의 대부분은 "The OAuth 2.0 Authorization Framework" [RFC6749]와 "The OAuth 2.0 Authorization Framework: Bearer Token Usage" [RFC6750]에도 적용되며, 이 명세에만 해당하지는 않는다. 이하에서는 이 명세에만 해당하는 규정만 다룬다.¶

11.1. 수집 제한

client에 개인정보가 포함된 보호 리소스에 대한 접근 권한을 부여할 때, client는 적용 법률이 허용하는 범위에서 명시된 목적을 달성하는 데 반드시 필요한 개인정보만 수집하는 것이 바람직하다(SHOULD).¶

사용자는 요청받은 개인정보가 반드시 필요한지 알아내기 어려운 경우가 많다. 신뢰할 수 있는 제3자 서비스는 client의 요청을 검토하고, 이 요청을 client가 제안한 처리 방식과 대조한 뒤 요청을 인증함으로써 사용자를 도울 수 있다. 인증 후 client는 인가 요청을 할 때 신뢰할 수 있는 제3자 서비스에 인가 요청을 제출하여 Request Object URI를 받을 수 있다. 이 과정은 두 단계로 이루어진다.¶

(1)
(인증 절차) 신뢰할 수 있는 제3자 서비스는 client의 업무 절차를 검토하여 client에게 어떤 클레임이 필요한지 판단한다. 이것이 인증 절차다. 인증을 마친 client에게는 client 자격 증명이 발급된다. client는 이 자격 증명으로 신뢰할 수 있는 제3자 서비스에 자신의 신원을 증명하여 Request Object를 제출하고 request_uri를 받을 수 있다.¶
(2)
(변환 절차) client는 발급받은 client 자격 증명을 사용해 신뢰할 수 있는 제3자 서비스에 Request Object를 제출하여 request_uri를 받는다. 신뢰할 수 있는 제3자 서비스는 또한 Request Object가 앞 단계에서 해당 client에 허용된 클레임과 일치하는지 검증한다.¶

인가 요청에 포함된 이러한 Request Object URI를 받으면 authorization server는 먼저 Request Object URI의 authority 부분이 신뢰할 수 있는 제3자 서비스에 정당하게 속하는지 검증한다. 그런 다음 authorization server는 Request Object URI로 HTTP GET 요청을 보낸다. 연결이 수립되면 authorization server는 TLS 인증서에 표시된 서버 신원이 Request Object URI에 대해 유효한지 반드시 검증해야 한다(MUST). 그러면 authorization server는 client를 나타내는 client_id가 포함된 Request Object를 얻을 수 있다.¶

동의 화면에는 client를 반드시 표시해야 한다(MUST). 또한 신뢰할 수 있는 제3자 서비스가 수집 제한 원칙의 준수 여부를 확인하기 위해 요청을 심사했다는 사실을 표시하는 것이 바람직하다(SHOULD).¶

11.2. 공개 제한

11.2.1. 요청 공개

이 명세는 확장 매개변수를 허용한다. 이러한 매개변수에는 민감할 수 있는 정보가 포함될 수 있다. URI 쿼리 매개변수는 여러 경로로, 특히 referrer와 브라우저 방문 기록을 통해 유출될 수 있다. 따라서 인가 요청에 민감할 수 있는 매개변수가 포함되어 있다면 client가 Request Object를 암호화하는 것이 바람직하며(SHOULD), 암호화에는 JWE [RFC7516]를 사용한다.¶

Request Object URI 방식에서 Request Object에 개인을 식별할 수 있는 정보나 민감한 정보가 포함되어 있다면, request_uri는 한 번만 사용하고 유효 기간을 짧게 두는 것이 바람직하다(SHOULD). 또한 적용되는 보안 정책을 충족할 만큼 충분한 엔트로피를 반드시 갖추어야 한다(MUST). 이 엔트로피 요구사항은 Request Object 자체를 JWE [RFC7516]로 암호화한 경우에는 적용되지 않는다. Request Object URI의 유효 기간이 얼마나 짧아야 하고 엔트로피가 얼마나 커야 하는지는 보호 대상 리소스의 가치에 따라 산정한 위험에 달려 있다. 일반적인 지침으로는 유효 기간을 1분 미만으로 두는 것이 좋으며, 이 명세를 작성하는 시점의 기준으로 Request Object URI에는 128비트 이상의 암호학적 난수 값을 포함한다.¶

11.2.2. Request Object URI를 이용한 추적

보호 리소스에 개인을 식별할 수 있는 정보가 없더라도, 사용자별로 고정된 Request Object URI를 지속적으로 사용하면 이를 통해 사용자를 식별할 수 있는 경우가 있다. 제3자는 브라우저 방문 기록 등을 통해 해당 URI를 알아내고, 이를 이용해 사용자의 활동 내역을 서로 연결하기 시작할 수 있다. 이 역시 일종의 데이터 공개이므로 피하는 것이 바람직하다.¶

따라서 사용자별로 동일한 Request Object URI를 지속적으로 사용하는 것은 피하는 것이 바람직하다. 한 가지 대안은 일회용 Request Object URI를 사용하는 것이다.¶
