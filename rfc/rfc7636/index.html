초록

Authorization Code Grant(인가 코드 부여)를 사용하는 OAuth 2.0 public client(공개 클라이언트)는 authorization code(인가 코드) 가로채기 공격에 취약합니다. 이 명세는 이 공격과 함께 Proof Key for Code Exchange(PKCE, "pixy"로 발음)를 사용하여 이 위협을 완화하는 기법을 설명합니다.

1. 서론

OAuth 2.0 [RFC6749] public client는 authorization code 가로채기 공격에 취약합니다.

이 공격에서 공격자는 client 운영 체제 내의 애플리케이션 간 통신과 같이 Transport Layer Security (TLS)로 보호되지 않는 통신 경로에서 authorization endpoint(인가 엔드포인트)가 반환하는 authorization code를 가로챕니다.

공격자는 authorization code에 접근할 수 있게 되면 이를 사용해 access token(접근 토큰)을 얻을 수 있습니다.

그림 1은 이 공격을 도식으로 보여 줍니다. 단계 (1)에서는 스마트폰과 같은 최종 장치에서 실행 중인 native application이 브라우저/운영 체제를 통해 OAuth 2.0 Authorization Request를 보냅니다. 이 경우 Redirection Endpoint URI는 일반적으로 사용자 정의 URI scheme을 사용합니다. 단계 (1)은 가로챌 수 없는 안전한 API를 통해 이루어지지만, 고도화된 공격 시나리오에서는 관찰할 수 있을 가능성이 있습니다. 이어서 단계 (2)에서 요청이 OAuth 2.0 authorization server(인가 서버)로 전달됩니다. OAuth는 TLS 사용을 요구하므로 이 통신은 TLS로 보호되며 가로챌 수 없습니다. 단계 (3)에서 authorization server는 authorization code를 반환합니다. 단계 (4)에서는 단계 (1)에서 제공한 Redirection Endpoint URI를 통해 Authorization Code가 요청자에게 반환됩니다.

정상적인 OAuth 2.0 앱 외에 악성 앱도 해당 사용자 정의 scheme의 handler로 자신을 등록할 수 있다는 점에 유의해야 합니다. 이렇게 등록하면 악성 앱은 단계 (4)에서 authorization code를 가로챌 수 있게 됩니다. 이에 따라 공격자는 단계 (5)에서 access token을 요청하고 단계 (6)에서 이를 얻을 수 있습니다. 

    +~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~+
    | End Device (e.g., Smartphone)  |
    |                                |
    | +-------------+   +----------+ | (6) Access Token  +----------+
    | |Legitimate   |   | Malicious|<--------------------|          |
    | |OAuth 2.0 App|   | App      |-------------------->|          |
    | +-------------+   +----------+ | (5) Authorization |          |
    |        |    ^          ^       |        Grant      |          |
    |        |     \         |       |                   |          |
    |        |      \   (4)  |       |                   |          |
    |    (1) |       \  Authz|       |                   |          |
    |   Authz|        \ Code |       |                   |  Authz   |
    | Request|         \     |       |                   |  Server  |
    |        |          \    |       |                   |          |
    |        |           \   |       |                   |          |
    |        v            \  |       |                   |          |
    | +----------------------------+ |                   |          |
    | |                            | | (3) Authz Code    |          |
    | |     Operating System/      |<--------------------|          |
    | |         Browser            |-------------------->|          |
    | |                            | | (2) Authz Request |          |
    | +----------------------------+ |                   +----------+
    +~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~+

이 공격이 성립하려면 다음과 같은 여러 전제 조건이 충족되어야 합니다.

1. 공격자가 client 장치에 악성 애플리케이션을 등록하는 데 성공하고, 다른 애플리케이션도 사용하는 사용자 정의 URI scheme을 등록합니다. 운영 체제는 여러 애플리케이션이 하나의 사용자 정의 URI scheme을 등록할 수 있도록 허용해야 합니다.
2. OAuth 2.0 authorization code grant가 사용됩니다.
3. 공격자가 OAuth 2.0 [RFC6749]의 "client_id"와 "client_secret"(제공된 경우)에 접근할 수 있습니다. 모든 OAuth 2.0 native app client instance는 동일한 "client_id"를 사용합니다. Client 바이너리 애플리케이션에 제공된 secret은 기밀로 간주할 수 없습니다.
4. 다음 조건 중 하나가 충족됩니다.

4a. 공격자가 설치된 애플리케이션을 통해 authorization endpoint의 응답만 관찰할 수 있습니다. "code_challenge_method" 값이 "plain"이면 이 공격만 완화됩니다.

4b. 더 고도화된 공격 시나리오에서는 공격자가 authorization endpoint의 응답뿐 아니라 이 endpoint로 향하는 요청도 관찰할 수 있습니다. 다만 공격자가 man in the middle로 동작할 수는 없습니다. 이러한 상황은 OS에서 http log 정보가 유출되어 발생했습니다. 이를 완화하려면 "code_challenge_method" 값을 "S256" 또는 암호학적으로 안전한 "code_challenge_method" 확장에서 정의한 값으로 설정해야 합니다.

전제 조건이 이처럼 많지만, 여기서 설명한 공격은 실제 환경에서 관찰되었으므로 OAuth 2.0 배포 시 고려해야 합니다. OAuth 2.0 위협 모델([RFC6819]의 4.4.1절)은 완화 기법을 설명하지만, 안타깝게도 이 기법들은 client instance별 secret이나 client instance별 redirect URI에 의존하므로 적용할 수 없습니다.

이 공격을 완화하기 위해 이 확장은 "code verifier(코드 검증값)"라는, 동적으로 생성되는 암호학적 난수 키를 사용합니다. Authorization request마다 고유한 code verifier를 생성하고, 이를 변환한 값인 "code challenge(코드 챌린지)"를 authorization server에 보내 authorization code를 얻습니다. 이렇게 얻은 authorization code를 "code verifier"와 함께 token endpoint(토큰 엔드포인트)로 보내면, 서버는 이를 앞서 수신한 요청 코드와 비교하여 client가 "code verifier"를 소유하고 있음을 증명할 수 있습니다. 이 일회성 키는 TLS를 통해 전송되어 가로챌 수 없으므로 공격자가 이를 알 수 없다는 점에서 공격 완화가 가능합니다.

1.1. Protocol 흐름 

                                                 +-------------------+
                                                 |   Authz Server    |
       +--------+                                | +---------------+ |
       |        |--(A)- Authorization Request ---->|               | |
       |        |       + t(code_verifier), t_m  | | Authorization | |
       |        |                                | |    Endpoint   | |
       |        |<-(B)---- Authorization Code -----|               | |
       |        |                                | +---------------+ |
       | Client |                                |                   |
       |        |                                | +---------------+ |
       |        |--(C)-- Access Token Request ---->|               | |
       |        |          + code_verifier       | |    Token      | |
       |        |                                | |   Endpoint    | |
       |        |<-(D)------ Access Token ---------|               | |
       +--------+                                | +---------------+ |
                                                 +-------------------+

이 명세는 그림 2에 추상적인 형태로 나타낸 OAuth 2.0 Authorization Request와 Access Token Request에 추가 parameter를 도입합니다.

A. Client는 "code_verifier"라는 secret을 생성하고 기록한 뒤, 이를 변환한 "t(code_verifier)"("code_challenge"라고 함)를 도출합니다. 이 값은 변환 방식 "t_m"과 함께 OAuth 2.0 Authorization Request에 포함되어 전송됩니다.
B. Authorization Endpoint는 평소와 같이 응답하되, "t(code_verifier)"와 변환 방식을 기록합니다.
C. 이어서 client는 평소와 같이 Access Token Request에 authorization code를 담아 보내되, (A)에서 생성한 "code_verifier" secret도 포함합니다.
D. Authorization server는 "code_verifier"를 변환하여 (B)의 "t(code_verifier)"와 비교합니다. 두 값이 같지 않으면 접근을 거부합니다.

(B)에서 authorization code를 가로챈 공격자는 "code_verifier" secret을 가지고 있지 않으므로 이를 access token으로 교환할 수 없습니다.

2. 표기 규칙

이 문서에서 사용하는 핵심어 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", "OPTIONAL"은 "Key words for use in RFCs to Indicate Requirement Levels" [RFC2119]에 설명된 대로 해석해야 합니다. 이 단어들이 대문자 표기 없이 사용되면 자연어에서의 의미로 해석해야 합니다.

이 명세는 [RFC5234]의 Augmented Backus-Naur Form (ABNF) 표기법을 사용합니다.

STRING은 0개 이상의 ASCII [RFC20] 문자로 이루어진 시퀀스를 나타냅니다.

OCTETS는 0개 이상의 octet으로 이루어진 시퀀스를 나타냅니다.

ASCII(STRING)은 STRING의 ASCII [RFC20] 표현에 해당하는 octet들을 나타내며, 여기서 STRING은 0개 이상의 ASCII 문자로 이루어진 시퀀스입니다.

BASE64URL-ENCODE(OCTETS)는 부록 A에 따라 OCTETS를 base64url(URL 안전 Base64) encoding하여 STRING을 생성하는 것을 나타냅니다.

BASE64URL-DECODE(STRING)은 부록 A에 따라 STRING을 base64url decoding하여 octet 시퀀스를 생성하는 것을 나타냅니다.

SHA256(OCTETS)는 OCTETS의 SHA2 256-bit hash [RFC6234]를 나타냅니다.

3. 용어

이 명세는 OAuth 2.0 [RFC6749]에서 정의한 용어 외에 다음 용어를 정의합니다.

code verifier
Authorization request와 token request를 연결하는 데 사용하는 암호학적 난수 문자열.
code challenge
Code verifier에서 도출하여 authorization request(인가 요청)에 담아 보내고, 이후 검증 시 비교 기준으로 사용하는 challenge.
code challenge method(코드 챌린지 방식)
Code challenge를 도출하는 데 사용한 방식.
Base64url Encoding
[RFC4648]의 5절에서 정의한 URL과 파일 이름에 안전한 문자 집합을 사용하는 Base64 encoding. 끝에 붙는 '=' 문자를 모두 생략하며([RFC4648]의 3.2절에서 허용), 줄바꿈, 공백 또는 그 밖의 추가 문자를 일절 포함하지 않습니다. (Padding 없는 base64url encoding 구현 시 참고 사항은 부록 A를 참조합니다.)

4. Protocol

4.1. Client가 code verifier를 생성함

Client는 먼저 각 OAuth 2.0 [RFC6749] Authorization Request에 사용할 code verifier인 "code_verifier"를 다음과 같이 생성합니다.

code_verifier = [RFC3986]의 2.3절에 정의된 비예약 문자 [A-Z] / [a-z] / [0-9] / "-" / "." / "_" / "~"를 사용하는, entropy가 높은 암호학적 난수 STRING. 길이는 최소 43자, 최대 128자입니다.

"code_verifier"의 ABNF는 다음과 같습니다. 

   code-verifier = 43*128unreserved
   unreserved = ALPHA / DIGIT / "-" / "." / "_" / "~"
   ALPHA = %x41-5A / %x61-7A
   DIGIT = %x30-39

참고: code verifier는 값을 추측하는 것이 현실적으로 불가능할 만큼 충분한 entropy를 갖는 것이 좋습니다(SHOULD). 적절한 난수 생성기의 출력을 사용하여 32-octet 시퀀스를 생성할 것을 권장합니다(RECOMMENDED). 이어서 이 octet 시퀀스를 base64url encoding하여 code verifier로 사용할 43-octet의 URL 안전 문자열을 생성합니다.

4.2. Client가 code challenge를 생성함

그런 다음 client는 code verifier에 다음 변환 중 하나를 적용하여 code verifier에서 도출한 code challenge를 생성합니다. 

   plain
      code_challenge = code_verifier

   S256
      code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))

Client가 "S256"을 사용할 수 있다면 반드시 "S256"을 사용해야 합니다(MUST). 서버에서 "S256"은 Mandatory To Implement (MTI)이기 때문입니다. Client는 기술적인 이유로 "S256"을 지원할 수 없고, 서버가 "plain"을 지원한다는 사실을 out-of-band 설정을 통해 알고 있는 경우에만 "plain"을 사용할 수 있습니다.

plain 변환은 기존 배포 환경과의 호환성 및 S256 변환을 사용할 수 없는 제약된 환경을 위한 것입니다.

"code_challenge"의 ABNF는 다음과 같습니다. 

   code-challenge = 43*128unreserved
   unreserved = ALPHA / DIGIT / "-" / "." / "_" / "~"
   ALPHA = %x41-5A / %x61-7A
   DIGIT = %x30-39

4.3. Client가 authorization request와 함께 code challenge를 보냄

Client는 다음 추가 parameter를 사용하여 OAuth 2.0 Authorization Request([RFC6749]의 4.1.1절)의 일부로 code challenge를 보냅니다.

code_challenge
필수(REQUIRED). Code challenge.
code_challenge_method
선택 사항(OPTIONAL)이며, 요청에 없으면 기본값은 "plain"입니다. Code verifier 변환 방식은 "S256" 또는 "plain"입니다.

4.4. 서버가 code를 반환함

서버는 authorization response에 authorization code를 발급할 때 나중에 검증할 수 있도록 "code_challenge"와 "code_challenge_method" 값을 해당 authorization code와 반드시 연결해야 합니다(MUST).

일반적으로 "code_challenge"와 "code_challenge_method" 값은 "code" 자체에 암호화된 형태로 저장되지만, code와 연결하여 서버에 저장할 수도 있습니다. 서버는 다른 개체가 추출할 수 있는 형태로 "code_challenge" 값을 client 요청에 포함해서는 안 됩니다(MUST NOT).

서버가 발급된 "code"에 "code_challenge"를 연결하는 구체적인 방식은 이 명세의 범위를 벗어납니다.

4.4.1. 오류 응답

서버가 OAuth public client에 Proof Key for Code Exchange (PKCE)를 요구하는데 client가 요청에 "code_challenge"를 보내지 않으면, authorization endpoint는 "error" 값을 "invalid_request"로 설정한 authorization 오류 응답을 반환해야 합니다(MUST). "error_description" 또는 "error_uri"의 응답은 오류의 성격(예: code challenge가 필요함)을 설명하는 것이 좋습니다(SHOULD).

PKCE를 지원하는 서버가 요청된 변환을 지원하지 않으면, authorization endpoint는 "error" 값을 "invalid_request"로 설정한 authorization 오류 응답을 반환해야 합니다(MUST). "error_description" 또는 "error_uri"의 응답은 오류의 성격(예: 변환 알고리즘이 지원되지 않음)을 설명하는 것이 좋습니다(SHOULD).

4.5. Client가 Authorization Code와 Code Verifier를 Token Endpoint에 전송

Authorization Code를 받으면 client는 token endpoint에 Access Token Request를 보냅니다. OAuth 2.0 Access Token Request([RFC6749]의 4.1.3절)에 정의된 매개변수에 더하여 다음 매개변수를 보냅니다.

code_verifier
필수(REQUIRED). Code verifier

Authorization Code가 발급될 때 "code_challenge_method"가 해당 Authorization Code에 결합됩니다. token endpoint는 이 방식을 사용하여 "code_verifier"를 검증해야 합니다(MUST).

4.6. 서버가 Token을 반환하기 전에 code_verifier를 검증

token endpoint에서 요청을 받으면 서버는 수신한 "code_verifier"를 먼저 client가 지정한 "code_challenge_method" 방식에 따라 변환하여 code challenge를 계산하고, 이를 앞서 연결해 둔 "code_challenge"와 비교하여 요청을 검증합니다.

4.3절의 "code_challenge_method"가 "S256"이면 수신한 "code_verifier"를 SHA-256으로 hashing하고 base64url로 encoding한 다음 "code_challenge"와 비교합니다. 즉, 다음과 같습니다.

   BASE64URL-ENCODE(SHA256(ASCII(code_verifier))) == code_challenge

4.3절의 "code_challenge_method"가 "plain"이면 두 값을 직접 비교합니다. 즉, 다음과 같습니다.

   code_verifier == code_challenge.

두 값이 같으면 token endpoint는 정상적인 처리를 계속해야 합니다(MUST)(OAuth 2.0 [RFC6749]에 정의된 대로). 두 값이 다르면 [RFC6749]의 5.2절에 설명된 "invalid_grant"를 나타내는 오류 응답을 반환해야 합니다(MUST).

5. 호환성

이 명세의 서버 구현은 이 확장을 구현하지 않은 OAuth2.0 client를 받아들여도 됩니다(MAY). Authorization Request에서 client로부터 "code_verifier"를 받지 못하면, 하위 호환성을 지원하는 서버는 이 확장을 사용하지 않는 OAuth 2.0 [RFC6749] protocol로 돌아갑니다.

이 명세는 OAuth 2.0 [RFC6749] 서버 응답을 변경하지 않으므로, 이 명세의 client 구현은 서버가 이 명세를 구현했는지 알 필요가 없으며 4절에 정의된 추가 매개변수를 모든 서버에 보내는 것이 좋습니다(SHOULD).

이 명세는 "PKCE Code Challenge Methods" registry를 신설합니다. 새 registry는 "OAuth Parameters" registry의 하위 registry가 되는 것이 좋습니다.

authorization endpoint에서 사용할 추가 "code_challenge_method" 유형은 Specification Required 정책 [RFC5226]에 따라 등록하며, 이 정책에는 한 명 이상의 Designated Expert(지정 전문가) (DE)가 요청을 검토하는 절차가 포함됩니다. DE들은 oauth-ext-review@ietf.org mailing list에서 요청을 최소 2주 동안 검토하고, 요청에 답변하기 전에 해당 list의 논의가 수렴하도록 보장합니다. 문서가 발행되기 전에 값을 할당할 수 있도록, Designated Expert는 수용 가능한 명세가 발행될 것이라고 확신하면 등록을 승인할 수 있습니다.

oauth-ext-review@ietf.org mailing list의 등록 요청과 논의에는 "Request for PKCE code_challenge_method: example"과 같은 적절한 제목을 사용하는 것이 좋습니다.

Designated Expert는 등록 요청을 평가할 때 mailing list의 논의와 challenge 방식의 전반적인 보안 속성을 함께 고려하는 것이 좋습니다. 새로운 방식은 Authorization endpoint로 보내는 요청에서 code_verifier 값을 노출하지 않는 것이 좋습니다. 거절 시에는 설명을 포함하고, 해당하는 경우 요청이 승인되도록 하는 방법에 관한 제안도 포함하는 것이 좋습니다.

7. 보안 고려 사항

7.1. code_verifier의 Entropy

보안 모델은 공격자가 code verifier를 알아내거나 추측하지 못한다는 사실에 의존합니다. 이 원칙을 지키는 것은 대단히 중요합니다. 따라서 code verifier는 암호학적으로 무작위이며 entropy가 높아 공격자가 추측하는 것이 현실적으로 불가능하도록 생성해야 합니다.

client는 최소 256 bits의 entropy를 가진 "code_verifier"를 생성하는 것이 좋습니다(SHOULD). 적절한 난수 생성기로 32-octet 시퀀스를 생성하여 이를 달성할 수 있습니다. 그런 다음 이 octet 시퀀스를 base64url로 encoding하여, 필요한 entropy를 갖춘 "code_challenge"로 사용할 43-octet URL-safe 문자열을 만들 수 있습니다.

7.2. 도청자에 대한 보호

client는 "S256" 방식을 시도한 후 "plain"으로 downgrade해서는 안 됩니다(MUST NOT). PKCE를 지원하는 서버는 "S256"을 지원해야 하며, PKCE를 지원하지 않는 서버는 알 수 없는 "code_verifier"를 단순히 무시합니다. 따라서 "S256"을 제시했을 때 오류가 발생한다면 서버에 결함이 있거나 MITM 공격자가 downgrade attack(다운그레이드 공격)을 시도하고 있다는 의미일 수밖에 없습니다.

"S256" 방식은 verifier 없이는 challenge를 사용할 수 없으므로, "code_challenge"를 관찰하거나 가로채는 도청자로부터 보호합니다. "plain" 방식에서는 공격자가 기기나 http 요청에서 "code_challenge"를 관찰할 가능성이 있습니다. 이 경우 code challenge가 code verifier와 같으므로 "plain" 방식은 초기 요청의 도청으로부터 보호하지 못합니다.

"S256"을 사용하면 "code_verifier" 값이 공격자에게 노출되는 것을 막을 수 있습니다.

따라서 "plain"은 사용하지 않는 것이 좋으며(SHOULD NOT), 요청 경로가 이미 보호되는 기존 배포 구현과의 호환성만을 위해 존재합니다. 새로운 구현에서는 기술적인 이유로 "S256"을 지원할 수 없는 경우가 아니라면 "plain" 방식을 사용하지 않는 것이 좋습니다(SHOULD NOT).

"S256" code challenge method 또는 그 밖의 암호학적으로 안전한 code challenge method 확장을 사용하는 것이 좋습니다(SHOULD). "plain" code challenge method는 요청이 공격자에게 노출되지 않도록 운영체제와 전송 보안에 의존합니다.

code challenge method가 "plain"이고 stateless 서버를 구현하기 위해 code challenge를 authorization "code" 안에 넣어 반환하려는 경우, 서버만 이를 복호화하여 추출할 수 있도록 암호화해야 합니다(MUST).

7.3. code_challenge에 Salt 적용

code verifier에는 brute-force attack을 방지하기에 충분한 entropy가 있으므로, 구현 복잡도를 줄이기 위해 code challenge 생성에는 salting을 사용하지 않습니다. (256 bits의 entropy를 가진) code verifier에 공개적으로 알려진 값을 이어 붙인 다음 SHA256으로 hashing하여 code challenge를 생성하더라도, 유효한 code verifier 값을 brute force로 알아내는 데 필요한 시도 횟수는 늘어나지 않습니다.

"S256" 변환은 password를 hashing하는 것과 비슷하지만 중요한 차이가 있습니다. password는 비교적 entropy가 낮은 단어인 경우가 많으며, offline으로 hashing하고 그 hash를 dictionary에서 조회할 수 있습니다. hashing 전에 공개된 값이라도 고유한 값을 각 password에 이어 붙이면 공격자가 검색해야 할 dictionary 공간이 크게 확장됩니다.

이제 최신 graphics processor를 이용하면 공격자는 disk에서 hash를 조회하는 것보다 더 빠르게 실시간으로 hash를 계산할 수 있습니다. 이로 인해 entropy가 낮은 password의 경우에도 brute-force attack의 복잡도를 높이는 salt의 가치가 사라집니다.

7.4. OAuth 보안 고려 사항

[RFC6819]에 제시된 OAuth 보안 분석이 모두 적용되므로, 독자는 이를 주의 깊게 따르는 것이 좋습니다(SHOULD).

7.5. TLS 보안 고려 사항

현재의 보안 고려 사항은 "Recommendations for Secure Use of Transport Layer Security (TLS) and Datagram Transport Layer Security (DTLS)" [BCP195]에서 확인할 수 있습니다. 이는 OAuth 2.0 [RFC6749]의 TLS 버전 권고를 대체합니다.

부록 A. Padding 없는 Base64url 인코딩 구현 참고 사항

이 부록에서는 padding을 사용하는 표준 base64 인코딩 함수를 바탕으로, padding 없는 base64url 인코딩 함수를 구현하는 방법을 설명합니다.

구체적인 설명을 위해 이 함수들을 구현한 C# 예제 코드를 아래에 제시합니다. 다른 언어에서도 유사한 코드를 사용할 수 있습니다. 

     static string base64urlencode(byte [] arg)
     {
       string s = Convert.ToBase64String(arg); // Regular base64 encoder
       s = s.Split('=')[0]; // Remove any trailing '='s
       s = s.Replace('+', '-'); // 62nd char of encoding
       s = s.Replace('/', '_'); // 63rd char of encoding
       return s;
     }

인코딩 전 값과 인코딩된 값의 대응 예는 다음과 같습니다. 아래 octet sequence를 인코딩하면 그 아래의 문자열이 되며, 이 문자열을 디코딩하면 원래 octet sequence가 재현됩니다. 

   3 236 255 224 193

   A-z_4ME

부록 B. S256 code_challenge_method의 예

client는 적절한 난수 생성기의 출력을 사용하여 32-octet sequence를 만듭니다. 이 예의 값을 나타내는 octet은 다음과 같습니다(JSON 배열 표기법 사용). 

      [116, 24, 223, 180, 151, 153, 224, 37, 79, 250, 96, 125, 216, 173,
      187, 186, 22, 212, 37, 77, 105, 214, 191, 240, 91, 88, 5, 88, 83,
      132, 141, 121]

이 octet sequence를 base64url로 인코딩하면 code_verifier 값이 됩니다. 

       dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

이어서 code_verifier에 SHA256 hash function을 적용하면 다음 결과가 나옵니다. 

     [19, 211, 30, 150, 26, 26, 216, 236, 47, 22, 177, 12, 76, 152, 46,
      8, 118, 168, 120, 173, 109, 241, 68, 86, 110, 225, 137, 74, 203,
      112, 249, 195]

이 octet sequence를 base64url로 인코딩하면 code_challenge 값이 됩니다. 

       E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM

authorization request에는 다음이 포함됩니다. 

       code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
       &code_challenge_method=S256

이어서 authorization server는 client에 부여한 code와 함께 code_challenge 및 code_challenge_method를 기록합니다.

client는 token_endpoint로 보내는 요청에 authorization response에서 받은 code와 다음 추가 parameter를 포함합니다. 

       code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

authorization server는 code grant에 대한 정보를 조회합니다. 기록된 code_challenge_method가 S256이므로, 이어서 code_verifier 값을 hashing한 후 base64url로 인코딩합니다. 

   BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))

이어서 계산한 값을 "code_challenge" 값과 비교합니다. 

   BASE64URL-ENCODE(SHA256(ASCII(code_verifier))) == code_challenge

두 값이 같으면 authorization server는 요청에 다른 오류가 없는 한 token을 제공할 수 있습니다. 두 값이 다르면 요청을 거부하고 오류를 반환해야 합니다.
